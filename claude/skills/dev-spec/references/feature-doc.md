# 機能設計書 (docs/features/) の書き方 (dev-spec フェーズ 7)

- 種別: テンプレート + 記入基準
- 生成者: dev-spec フェーズ 7。更新者: dev-impl (実装詳細レベルの乖離補正のみ。契約レベルは人間にエスカレーション)
- 消費者: issue の `## 設計` 節から参照される / dev-impl の implementer・review-impl が実装と突合する / 人間・AI が「この機能の設計はどうなっているか」をローカルで引く

## 単位と命名

**1 機能 = 1 ファイル、機能名で命名する** (例: `docs/features/export.md`、`docs/features/tag-search.md`)。UC 番号では命名しない — 人間にも AI にも機能名の方が引きやすい (`rg export docs/` で当たる)。UC との対応は冒頭メタ情報の 1 行で保つ。複数 issue が同じ機能設計書を参照してよい。

機能の切り方は UC を出発点にする (1 UC = 1〜2 機能が目安)。UC を持たない構成 (クイックモード) ではタスク説明から機能を切り出す。

## テンプレート

```markdown
# <機能名>

- 種別: 機能設計書
- 対象 UC: UC-<n> (docs/USECASES.md)   <!-- UC が無い構成では「なし (タスク説明から起こした)」 -->

## 何を作るか

<機能の要約 (2〜5 行)。満たすべき UC の規則 (BR) があればここで言及する>

## 入出力と振る舞い

<データ系: 入力と出力の形式 (フィールド名・順序・形式の決定)。
 UI 系: 操作 → 画面に起きることの表 + UI_SKETCH.html の該当画面参照>

## API (該当時)

<この機能が持つエンドポイント。メソッド・パス・リクエスト/レスポンスの形・主要なエラー応答。
 API 全体の一覧と共通規約 (認証・エラー形式) は docs/DESIGN.md 側に置き、ここには本機能の分だけ書く>

## 実装の配置

| 処理 | 層 | 実装先ファイル |
| --- | --- | --- |

<テーブルに触るならテーブル名を「処理」列に含める (例: `タグの保存 → tags, map_tags`)。
 テーブル定義そのものは docs/DESIGN.md「データスキーマ」が正本>

## エッジケースの決定

<該当するものだけを書く。下の観点リストは書くときのチェック用で、全観点の記載は必須ではない>

## テスト方針

<何をどのレベル (単体 / 結合 / E2E) で確かめるか。E2E は golden path のみ (テストピラミッド)。
 UI がある機能は golden path の Playwright E2E を実装時に書く前提で、その対象動線をここに 1 行で指定する>
```

## 記入基準

- **エッジケースの観点リスト** (書くときに一巡すること): 空・最小データ / 上限・境界値 (件数・長さ・日付・数値の端) / エラー時に利用者へ見えるもの (未認証・失敗応答) / 並行操作・二重実行 (往復中の別操作、二重送信) / 再表示時の整合 (他画面から戻ったとき何を根拠に最新になるか)。該当するものだけ決定を書き、書かなかった観点は「検討して該当なし」とみなされる — 迷ったら「該当なし (<理由>)」を残す
- **決めが要る点はその場で聞く**: プロダクト判断 (仕様の決め) が必要になったら、書き終えてからまとめて聞くのではなく、その場で AskUserQuestion で確認して決定を書き込む。変更コストの高い決定 (データの持ち方・API の外部契約・削除の扱い) を優先し、数時間で直せる細部 (UI 文言・並び順) は書き手が決めて明記する
- **横断事項を書かない**: テーブル定義・API 共通規約・エラー形式・認証は docs/DESIGN.md が正本。ここに重複させると改訂時に食い違う。本機能からの参照は「DESIGN.md「<節名>」参照」と書く
- **技術検証待ちの未確定要素**は `<!-- POC_NEEDED: id=<id>, scope=<検証対象>, risk=<high|medium|low>, blocker=<true|false> -->` マーカーで残す (書式・解決時の除去規定とも docs/DESIGN.md = design-doc.md の記入基準と共通。dev-impl が開始時に blocker=true の残存を検査する)

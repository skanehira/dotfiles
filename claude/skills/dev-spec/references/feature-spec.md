# 機能仕様の生成 (dev-spec フェーズ 7.5)

## 責務

UC (振る舞いの規則) と実装の間にある**機能単位の詳細設計**を成果物にする。1 UC = 1 ファイルで `docs/features/UC-<n>.md` に書く。DESIGN_DETAIL_APP.md は横断関心事 (API / スキーマ / エラー / UX) で編成されるため、機能がどういうバイト列・振る舞いになるかの契約はどの節にも居場所が無い。本フェーズがその居場所になる。

- **生成者**: 本フェーズ。**更新者**: フェーズ 8 (`要判断:` 行の解消)、実装中の設計加筆 (`/dev-impl` の P1/P2 動的修正)
- **消費者**: フェーズ 10 (TODO.md の参照 docs に載る)、フェーズ 10.5 (`review-spec-compliance` mode: pre-approval の Step 8 が監査する)、`/dev-impl` (PHASE_CONTEXT の `feature_spec` として implementer に全文が渡り、`SPEC_TEXT` としてリスク面の一次算出が読む)

### SSOT の線引き

機能仕様の新設で「同じ機能を語るファイル」が 3 つになる。責務を重ねない:

| ファイル | 持つもの | 持たないもの |
| --- | --- | --- |
| USECASES.md | BR の定義、フロー、事前・事後条件 | 実現方法 |
| `docs/features/UC-<n>.md` | バイト級契約、エッジケースの決定、責務配置、BR の精緻化 | BR の定義そのもの (原文引用のみ。再定義しない)、横断関心事 |
| DESIGN_DETAIL_APP.md | 横断関心事 (API 一覧・スキーマ・エラー戦略・共通 UX 仕様) | 機能単体の詳細契約 |

## 実行条件

**`docs/USECASES.md` が存在するときのみ実行する** (機能仕様の単位が UC なので、UC が無ければ定義できない)。クイックモードはフェーズ 3 を通らず USECASES.md が無いため、この条件で自動的にスキップになる。**cli モードは実行する** (CLI の機能にも入出力契約とエッジケースはある)。

## コアワークフロー

### ステップ1: 対象 UC の列挙

`rg -n '^## UC-[0-9]+:' docs/USECASES.md` で UC を全件列挙する。この時点で TODO.md はまだ無いので、フェーズへの割当ではなく **UC 全件**が対象。

**再実行 (docs/features/ が既に存在する場合) では、不足している UC の分だけを生成し、既存ファイルは保持する** — フェーズ 8 の書き戻しや実装中の更新を上書きしないため。全件揃っているかは UC 見出しの件数と `ls docs/features/UC-*.md | wc -l` の突合で判定する。

### ステップ2: UC ごとに機能仕様を書く

UC の節 (フロー・BR 表)・DESIGN_DETAIL_APP.md の関連節・UI_SKETCH.html (webapp のみ)・DOMAIN_MODEL.md を読み、下のテンプレートに従って `docs/features/UC-<n>.md` を書く。

### ステップ3: 期待出力の固定 (データ出力系のみ)

出力がデータそのもの (書き出しファイル・API 応答・CLI の stdout 等) の機能は、正準フィクスチャに対する期待出力を `docs/features/fixtures/uc-<n>/` に**ファイルとしてコミットする**。フェーズ 10 の DoD がこのファイルとの `cmp` になり、期待値の作者 (設計) とテストの作者 (実装) が分離される。

**入力 (正準フィクスチャ) も同じディレクトリにファイルとして置くか、決定的に再現できる生成手順 1 本を機能仕様に書く。** 入力の構築が実装者の解釈に依存すると、期待出力との突合が成立しない。

### ステップ4: 埋められない行の残し方

設計者が単独で決められない行 (プロダクト判断が要るもの) は、固定リテラル **`要判断: <質問文>`** で残す。フェーズ 8 (深掘りインタビュー) が `rg -n '要判断:' docs/features/` で回収して人間に質問し、回答を書き戻す。**書式を崩すと回収されない。** フェーズ 10.5 の `feature_spec_unresolved` も同じリテラルを rg するため、書式が崩れた未決定行は**どの検査にも掛からない** — 網は書式の遵守そのものにしか無い。

| BR | 原文 |

## 2. 入出力契約

<データ出力系: 正準フィクスチャ (入力) と期待出力。期待出力の実体は
docs/features/fixtures/uc-<n>/ のファイルで、ここには入力の定義と期待ファイルへの

## 3. 責務配置

| 処理 | 層 (server / browser / CLI) | 実装先ファイル |
| --- | --- | --- |

## 4. エッジケース表

| 観点 | 決定 |
| --- | --- |
| async_roundtrip: この機能の往復の最中に利用者が別の操作をしたら何が起きるか。中断・再試行・二重要求の扱いは | |
| persistence_limit: 入力や対象データが上限 (件数・長さ・深さ) に達したとき何が起きるか | |

| BR | 確かめ方 (テスト・fixture) |
| --- | --- |

## 記入基準

- **エッジケース表の各行は 3 択で埋める**: 決定を書く / `該当なし (<理由>)` / `要判断: <質問文>`。**空欄・行の削除は不可** — 空欄は「検討して該当なしと判断した」と「検討していない」の区別が付かない。この表の存在理由は、仕様の**沈黙を設計時に可視化する**ことにある (実測: mind の run では「往復中の編集をどうするか」が設計時に問われないまま実装へ渡り、規則 BR-1004 が実装中に新設されて 1 フェーズが run 全体の 40% を消費した)
- 必須 7 行のうち先頭 5 行は `/dev-impl` のリスク面 (定義と二次シグナルの SSOT は `claude/skills/dev-impl/references/phase-execution.md` の `## 4.2c: リスク面の表`) と同じ集合。**この 5 面は 1 run の実測 18 findings から seed した初期集合であり、run の実測に応じて育てる。** 面を足すときは SSOT の表を起点に、追従箇所 3 つ — 本テンプレートのエッジケース表 (先頭 5 行) / phase-execution.md の 4.1 一次算出の語彙 / phase-context.md の `risk_faces` の値一覧 — へ同時に足す (追従が欠けると設計時の問いと実装時の検知がずれる)
- **BR は原文を引用する。要約・言い換えは禁止** — 消費者 (フェーズ 10.5 の `br_not_traced`、`/dev-impl` の `traces_to` 照合) が `rg -F` で実在を機械照合するため。照合できない引用は、存在しない条文のでっち上げと区別が付かない
- **期待値ファイルを実装の出力から生成しない** — 実装が何を出力しても一致するため、検査が意味を失う。期待出力は本フェーズで USECASES / UI_SKETCH から**手で**書き起こす
- **バイト固定はデータ出力系のみ**。UI・視覚系の機能に期待バイト列を要求しない (振る舞い表 + UI_SKETCH 参照で足りる。全機能に要求すると設計フェーズが実装の先取りに膨らむ)
- 該当しない節 (例: CLI に UI 系の契約は無い) は削除せず `該当なし (<理由>)` と明記する — 無言の省略は「書き漏れ」と区別できない
- 技術検証次第で変わる未確定要素は `<!-- POC_NEEDED: ... -->` マーカーで残してよい (書式と運用は `analyzing-requirements.md` と同じ)。**ただしエッジケース表の行の値には使わない** — 行は 3 択のみで、マーカーは節の本文側に置く (プロダクト判断の未決定は `要判断:`、技術検証の未確定は POC_NEEDED、と残し方を分ける)

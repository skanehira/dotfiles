## 概要

承認済みの詳細設計書（`docs/DESIGN_DETAIL_APP.md` + `docs/DESIGN_DETAIL_INFRA.md`）を読み込み、TDD（テスト駆動開発）に準拠した TODO.md を作成する。生成される TODO.md は実装ループ (`/dev-impl`) で直接使用できる形式となる。

**前提条件**: フェーズ 7 (analyzing-requirements) で作成された DESIGN.md / DESIGN_DETAIL_APP.md / DESIGN_DETAIL_INFRA.md が存在し、ユーザーに承認されていること。

詳細設計 2 ファイルが無い既存プロジェクトの場合は、ステップ 1 のフォールバックで対話的に生成・移行を行う。

## コアワークフロー

### ステップ1: 設計書の確認

詳細設計 2 ファイルと DESIGN.md (概要との整合確認用) を読み込む：

```javascript
Read(file_path="docs/DESIGN_DETAIL_APP.md")
Read(file_path="docs/DESIGN_DETAIL_INFRA.md")
Read(file_path="docs/DESIGN.md")
```

#### フォールバック A: 旧形式の単一 DESIGN_DETAIL.md がある場合

`docs/DESIGN_DETAIL.md` (旧形式) が存在し APP / INFRA が無い場合、AskUserQuestion で確認:

```javascript
AskUserQuestion({
  questions: [{
    question: "旧形式の docs/DESIGN_DETAIL.md が見つかりました。DESIGN_DETAIL_APP.md / DESIGN_DETAIL_INFRA.md に分割して進めますか？",
    header: "詳細設計の移行",
    options: [
      { label: "分割して進める", description: "境界基準 (analyzing-requirements.md 参照) で APP / INFRA に振り分けて 2 ファイルを生成し、旧ファイルを削除してからタスク分解へ進む" },
      { label: "中止", description: "ユーザーが手動で整えてから再実行" }
    ],
    multiSelect: false
  }]
})
```

「分割して進める」の場合: 境界基準 (変更に IaC・クラウドコンソール操作・環境設定変更が要るか) で各セクションを振り分けて 2 ファイルに書き出し、旧 `docs/DESIGN_DETAIL.md` を削除し、DESIGN.md 内のリンクを更新する。ユーザーに分割後のファイルを確認してもらい承認を取得後、ステップ 2 へ進む。

#### フォールバック B: DESIGN.md しかない場合

既存プロジェクトで DESIGN.md だけある場合、AskUserQuestion で確認:

```javascript
AskUserQuestion({
  questions: [{
    question: "詳細設計 (DESIGN_DETAIL_APP.md / DESIGN_DETAIL_INFRA.md) が見つかりません。docs/DESIGN.md から詳細部分 (API・スキーマ・エラーパス・実装ガイド・CI/CD 等) を抽出して生成しますか？",
    header: "詳細設計の抽出",
    options: [
      { label: "抽出して進める", description: "DESIGN.md から詳細を切り出して APP / INFRA の 2 ファイルを生成し、全ファイルを更新後にタスク分解へ進む" },
      { label: "中止", description: "ユーザーが手動で詳細設計を整えてから再実行" }
    ],
    multiSelect: false
  }]
})
```

「抽出して進める」を選択された場合:

1. DESIGN.md から「API 設計」「データスキーマ詳細」「データフロー詳細」「エラー戦略 (具体)」「テスト戦略 (具体)」「実装ガイド」に該当する内容を `docs/DESIGN_DETAIL_APP.md` に、「リソース定義」「CI/CD」「監視」「シークレット管理」に該当する内容を `docs/DESIGN_DETAIL_INFRA.md` に抽出 (振り分けは境界基準に従う)
2. DESIGN.md からは詳細部分を削除し、概要 (共通 / アプリ概要 / インフラ概要) のみ残す
3. DESIGN.md の該当箇所には `詳細は [DESIGN_DETAIL_APP.md](./DESIGN_DETAIL_APP.md#section) を参照` 等のリンクを追加
4. ユーザーに分割後の全ファイルを確認してもらい承認を取得
5. 承認後、ステップ2 へ進む

「中止」の場合: 「詳細設計 2 ファイルを作成してから再実行してください」と表示して終了。

設計書の全セクションを把握し、タスク分解に必要な情報を抽出する。

### ステップ2: タスク分解

設計書から実装タスクを抽出し、TDDサイクルに従って分解する：

#### 分解の原則

1. **機能単位で分割**: 1つの機能 = 1つのTDDサイクル
2. **依存関係を考慮**: 基盤 → コア機能 → 拡張機能の順
3. **テストファースト**: 各機能でRED→GREEN→REFACTORを明示
4. **フェーズ1 (基盤構築) は DESIGN_DETAIL_APP.md の「プロジェクトセットアップ」から起こす**: スキャフォールド・テンプレート整理・初回起動確認の手順をそのままタスク化する
5. **インフラタスクは DESIGN_DETAIL_INFRA.md から起こす**: CI/CD workflow 作成・リソースプロビジョニング・シークレット設定等。IaC / 設定ファイルは宣言的でテスト対象外のため TDD サイクル ([RED]/[GREEN]) は付けず、代わりに検証手順 (INFRA 側) を [CHECK] タスクにする
6. **各フェーズに依存宣言 (`deps`) を付ける**: 下記「フェーズ依存の宣言」に従い、フェーズ見出しに `<!-- deps: ... -->` を必ず書く

#### タスクの粒度

- 1タスク = 1-4時間で完了可能
- テスト1つ + 実装1つ = 1セット
- リファクタリングは独立したタスク

#### フェーズ依存の宣言 (dev-impl の並列実行に使う)

フェーズ見出しの末尾に、そのフェーズが**先行完了を要求するフェーズの識別子**を機械可読な HTML コメントで書く:

```markdown
### フェーズ1: 基盤構築 <!-- deps: none -->
### フェーズ2: 記事投稿機能の実装 <!-- deps: 1 -->
### フェーズ3: 通知機能の実装 <!-- deps: 1,2 -->
### フェーズ4-a: インフラ構築 <!-- deps: 2,3 -->
### フェーズ4-b: 品質保証 <!-- deps: 2,3,4-a -->
```

- **識別子**は見出しの `フェーズ` 直後からコロンまでの文字列 (`1` / `3` / `4-a` のように接尾辞を含む)。複数依存はカンマ区切り、空白は入れない
- 識別子は**フェーズ 12 が作る issue のタイトル (`フェーズ<識別子>: <名前>`) にそのまま入り、dev-impl はそこから識別子を切り出す**ため、使えるのは**半角英数字とハイフンのみ**。見出しの区切りは半角コロン + 半角スペース (`### フェーズ4-a: 名前`) にする (全角コロンや空白入りの識別子は抽出を壊す)
- 依存が無いフェーズは `<!-- deps: none -->` と**明示する** (書式は省略不可)。フェーズ 12.4.2 がこれを `Depends on #N` に変換し、dev-impl の Step 2 が着手順の決定に使う。無記入だと依存なしと誤変換され、依存先が未完成のまま着手される
- 参照できるのは**自分より前に出現するフェーズのみ** (前方参照・循環は禁止)。フェーズ 12.4.2 が出現順に issue を作りながら識別子 → issue 番号の対応表を埋めるため、前方参照があると番号を解決できない

**依存ありと判定する基準** (1 つでも該当すれば依存を書く):

| 基準 | 例 |
| --- | --- |
| 同一ファイル・同一モジュールを編集する | フェーズ2 と 3 がともに `src/routes/index.ts` にルートを追加する |
| 型・API・関数の生産者と消費者の関係 | フェーズ2 が定義する `User` 型をフェーズ4 が import する |
| DB スキーマ・マイグレーションへの依存 | フェーズ3 がフェーズ2 の追加したテーブルを参照する |
| 前フェーズの成果物なしでは検証できない | 全機能フェーズ完了が前提の E2E・品質保証 |

**迷ったら依存ありに倒す** (依存を書けば直列化されるだけで安全。逆に独立と誤宣言すると並列実行時に同一ファイルを取り合って壊れる)。

定型フェーズの既定値:

| フェーズ | deps |
| --- | --- |
| フェーズ1 (基盤構築) | `none` |
| 機能フェーズ (フェーズ2 以降) | 最低でも `1` (基盤)。加えて上表に該当する先行機能フェーズ |
| フェーズN-a (インフラ構築) | 全機能フェーズの識別子 |
| フェーズN-b (品質保証) | 全機能フェーズ + `N-a` |
| フェーズN-c (UI/UX 仕上げ) | 全機能フェーズ + `N-b` |

#### 対応ゴールの宣言 (`goals`)

deps に続けて、そのフェーズが**寄与するゴール**を機械可読な HTML コメントで書く:

```markdown
### フェーズ1: 基盤構築 <!-- deps: none --> <!-- goals: none -->
### フェーズ2: 記事投稿機能の実装 <!-- deps: 1 --> <!-- goals: G1 -->
### フェーズ4-b: 品質保証 <!-- deps: 2,3,4-a --> <!-- goals: G1,G2,G_E2E -->
```

- 識別子は `DESIGN.md` の `- G<n>: ...` 行 (および `G_E2E`) から取る。複数はカンマ区切り、空白なし。抽出: `rg -n '^- G[0-9]+:|^G[0-9]+:|^- G_E2E:|^G_E2E:' docs/DESIGN.md` (ハイフンの有無どちらの記法も拾う。承認スタンプの GOALS_SHA と同じパターン)
- 寄与するゴールが無いフェーズ (基盤構築・純粋な構造整理など) は `<!-- goals: none -->` と**明示する** (書式は省略不可)
- **deps と違い前方参照を許す**。ゴールは設計時に全件確定しており、フェーズの出現順とは独立だからである
- 1 ゴールが複数フェーズにまたがってよい (フェーズ 2 と 3 の両方が `G1` に寄与する等)

**`goals` は追跡可能性であって DoD ではない。** `DESIGN_DETAIL_*.md` の `G<n> 検証` コマンドは、そのゴールに寄与する**全フェーズが揃うまで実行できない**ことがある。したがって各フェーズは `goals` とは別に、**そのフェーズ単独で実行できる DoD** を持つ (次節)。`goals` の用途は、実装者が「このフェーズは最終的に何のためにあるか」を辿れるようにすることと、全ゴールがどこかのフェーズでカバーされているかを検証すること。

#### 対応ユースケースの宣言 (`ucs`)

`docs/USECASES.md` がある場合、goals に続けて、そのフェーズが**属するユースケース**を機械可読な HTML コメントで書く:

```markdown
### フェーズ1: 基盤構築 <!-- deps: none --> <!-- goals: none --> <!-- ucs: none -->
### フェーズ2: 記事投稿機能の実装 <!-- deps: 1 --> <!-- goals: G1 --> <!-- ucs: UC-001 -->
### フェーズ4-b: 品質保証 <!-- deps: 2,3,4-a --> <!-- goals: G_E2E --> <!-- ucs: none -->
```

- 識別子は `docs/USECASES.md` の `## UC-<n>: <名前>` 見出しから取る (抽出: `rg -n '^## UC-[0-9]+:' docs/USECASES.md`)
- **書けるのは 1 つだけ** (`UC-001` の形式)、または `none`。カンマ区切りの複数指定は禁止 — フェーズ 12 がこの宣言を GitHub の sub-issue 紐付けに使い、**1 つの子 issue が持てる親 issue は 1 つ**という GitHub 側の制約があるため。複数 UC にまたがるフェーズは主担当の UC を 1 つ選ぶか `none` にする (UC への寄与の追跡は goals が担う)
- 属する UC が無いフェーズ (基盤構築・インフラ構築・品質保証など) は `<!-- ucs: none -->` と**明示する**。フェーズ 12 はこれらを「横断: UC に属さないフェーズ」という 1 つの親 issue にまとめる
- goals と同じく**前方参照を許す** (UC は設計時に全件確定しており、フェーズの出現順とは独立のため)
- **`docs/USECASES.md` が無い場合は本宣言を書かない。** クイックモード (フェーズ 3 を通らない) や既存プロジェクトからの再開では USECASES.md が無く、その場合フェーズ 12 は親 issue を作らずフラットな issue 構造で生成する

**`ucs` は俯瞰のための束ね方であって、実装の順序や範囲を変えない。** 着手順は deps、実装範囲はメタ情報の非スコープが決める。

#### 各フェーズが持つメタ情報 (必須)

フェーズ見出しの直後に、チェックボックス群の**前**として次の 5 項目を書く。**これがそのまま GitHub issue の本文になり (フェーズ 12)、`/dev-impl` は実装中この issue しか読まない**ため、ここに書かれていない情報は失われる。

| 項目 | 要件 | 典型的な失敗 |
| --- | --- | --- |
| **ゴール** | ユーザー視点で観測可能な 1 文 | 「記事投稿機能の実装」は作業の名前であってゴールではない。「ログイン済みユーザーが記事を投稿し、一覧に反映される」と書く |
| **DoD** | **原則は実行可能コマンド + 期待 exit code または完全一致の出力**。このフェーズ単独で実行できるものに限る。自動化できない検証は下記「手動系 DoD」に従う | 「テストが通ること」は散文。`deno test src/post_test.ts` が exit 0、と書く |
| **参照 docs** | 節名まで指定する (ファイル名だけでは足りない) | `docs/DESIGN_DETAIL_APP.md` だけでは実装者がどこを読むか分からない |
| **変更想定ファイル** | 作成・編集するファイルのパス一覧 | 並列実装時の衝突を事前検出する材料になる。省くと同一ファイルの取り合いが実行時まで分からない |
| **非スコープ** | このフェーズで**やらない**ことと、その担当フェーズ | 書かないと実装者が善意で隣接機能まで作り込み、他フェーズと衝突する |

**DoD が空虚になる 2 パターンは、書いた時点で潰す** (いずれもパイロットで実測):

- **出力比較は比較方法まで書く。** シェルのコマンド置換 (`ACT=$(cmd)`) は**末尾改行を捨てる**ため、「出力が完全一致」と書いても末尾改行の欠落を原理的に検出できない。実際に `console.log` を `Deno.stdout.write` に変異させたところ DoD を通過した。`cmp` / `diff` によるバイト比較を指定する:

  ```bash
  cmd > /tmp/actual.txt
  printf 'expected\n' > /tmp/expected.txt
  cmp /tmp/actual.txt /tmp/expected.txt
  ```

- **エントリポイントを実行グラフに入れる。** `main.ts` のように**どのテストからも import されない**ファイルは、テストコマンドの対象にも型検査グラフにも入らない。結線を壊して型エラーにしても green のまま通る。変更想定ファイルにエントリポイントが含まれるなら、DoD に結合テストか型検査 (`deno check main.ts` 等) を必ず含める

#### 手動系 DoD (すべてがコマンドになるわけではない)

DoD は 3 種類ある。**まず 1 に落とせないか、次に 2 に落とせないかを順に検討し、どうしても無理なものだけ 3 にする。**

| 種別 | 書式 | 例 | 誰が判定するか |
| --- | --- | --- | --- |
| **1. 自動系** | `DoD: <bash コマンド>` + 期待 exit code / バイト比較 | `deno test src/post_test.ts` が exit 0 | 実装ループ (`/dev-impl`) が実行する |
| **2. 自動化した UI 検証** | 同上 (テストコードに落とす) | `npx playwright test e2e/post.spec.ts` が exit 0 | 同上 |
| **3. 手動系** | `DoD (手動): <操作手順と期待結果>` | 「登録メールが受信箱に届く」「配色が UI_SKETCH と一致して見える」 | 人間 (`/dev-impl` はエスカレーションして判断を仰ぐ) |

**2 を飛ばして 3 にしない。** ブラウザ操作の検証は Playwright のテストコードに落とせば自動系になる (CLAUDE.md「動作検証」の方針: 検証フローが複数ある・修正 → 確認のループを回す場合はテストコードを書き exit code で検証する)。`chrome-devtools` MCP の逐次操作を DoD にすると、リーダーが受け入れ判定のたびに実行することになりトークンを食う。

**3 に該当するのは、原理的に機械判定できないものだけ**である: 外部サービスの受信確認、視覚的な印象の一致、実機デバイスでの体感。a11y の属性有無やレスポンシブの DOM 構造は 2 で自動化できるので 3 に入れない。

**終了しないコマンドを DoD にしない。** dev サーバ・watch モードは常駐するため、受け入れ判定の再実行がハングする。起動確認が要るなら「バックグラウンド起動 → `curl` でヘルスチェック → 停止」を 1 本のスクリプトにして exit code で判定する。

1 つのフェーズが自動系と手動系の両方を持ってよい (`DoD` と `DoD (手動)` を並べて書く)。その場合リーダーは自動系を再実行して判定し、**手動系だけを人間 PO にエスカレーションする** — 手動系があること自体は `needs-human` の理由にならない。

**DoD がどの種別にも落とせない (何をもって完了とするか書けない) フェーズ**は、フェーズ分解そのものが曖昧である。ゴールを問い直してフェーズを切り直す。それでも書けなければ、**固定書式 `DoD (未定義): <なぜ書けないか>`** でメタ情報に明記する。この文字列は `/dev-spec` フェーズ 12 が機械判定に使い (`rg -n 'DoD \(未定義\):'`)、該当フェーズの issue には `ready` ではなく `needs-human` を貼って人間の判断に回す。**書式を崩すと検出されず、判定不能な受入基準のまま `ready` になる。**

### ステップ3: TODO.md生成

以下の形式でTODO.mdを生成する。フェーズ見出しの 3 つ目のコメント (ucs) は `docs/USECASES.md` がある場合だけ書き、無ければコメントごと省く。

**テンプレートの説明文をそのまま生成物に残さない。** とくに ucs のコメント記法を含む注記を TODO.md 本文に書き写すと、dev-spec のフェーズ 12.0 がその 1 行だけで「階層あり」と誤判定し、`...` のような非 UC 文字列を親 issue の候補として拾う (実測済み)。

```markdown
# TODO: [プロジェクト名]

#### deps 宣言の検証

deps は dev-impl が**並列実装の可否判定にそのまま使う**ため、誤りは並列実行時の破壊 (同一ファイルの取り合い・未完成 API への依存) に直結する。以下を機械 + 目視で確認する:

```bash
rg -n '^### フェーズ' docs/TODO.md   # 全フェーズ見出しと deps 宣言を一覧化
```

1. **全フェーズに宣言があるか**: 上記出力の全行に `<!-- deps: ... -->` があること。1 つでも欠けると dev-impl は全フェーズを逐次実行にフォールバックする
2. **DAG になっているか**: 各 deps の参照先が実在する識別子で、かつ自分より前に出現していること (前方参照・循環はエラー)
3. **並列になる組の衝突チェック**: deps 上で互いに依存しないフェーズ組 (= dev-impl が同時に実装する組) を洗い出し、それぞれが**編集対象ファイル・モジュールで重ならない**ことを確認する。判定材料は詳細設計書 (DESIGN_DETAIL_APP.md の実装ガイド・ディレクトリ構造) から起こす。**重なる、または重なるか判断できない場合は deps を足して直列化する** (誤って並列化すると実装が衝突して壊れるが、余分に直列化しても遅くなるだけで壊れない)
4. **識別子の文字種**: 全識別子が半角英数字とハイフンのみで構成されていること (ブランチ名・ディレクトリ名に使われるため)

#### goals / ucs 宣言とメタ情報の検証

```bash
rg -n '^### フェーズ' docs/TODO.md                    # 全フェーズの deps / goals / ucs 宣言を一覧化
rg -n '^- G[0-9]+:|^G[0-9]+:|^- G_E2E:|^G_E2E:' docs/DESIGN.md   # 宣言されているゴールの全集合
rg -n '^## UC-[0-9]+:' docs/USECASES.md              # 宣言されているユースケースの全集合 (ファイルが無ければ ucs 検証はスキップ)
```

1. **全フェーズに `<!-- goals: ... -->` があるか** (寄与ゴールが無いなら `none` と明示)
2. **参照先が実在するか**: 各 `goals` の識別子が DESIGN.md のゴール一覧に存在すること
3. **全ゴールがカバーされているか**: DESIGN.md の各ゴールが、少なくとも 1 つのフェーズの `goals` に現れること。**現れないゴールは実装計画から漏れている** (このフェーズ分解では達成されない)
4. **メタ情報 5 項目が全フェーズに揃っているか**: ゴール / DoD / 参照 docs / 変更想定ファイル / 非スコープ
5. **DoD が判定可能な形になっているか**: 自動系は実行可能コマンド + 期待結果 (exit code または完全一致の出力)、手動系は `DoD (手動):` の書式で操作手順と期待結果。「テストが通ること」のような、どちらでもない散文が残っていないこと
5b. **手動系に逃げていないか**: `DoD (手動):` が付いたフェーズについて、Playwright 等のテストコードで自動化できないかを再検討する。自動化できるものが手動系のまま残っていると、リーダーの受け入れ判定のたびに人間へのエスカレーションが発生する
6. **空虚な DoD が無いか** (「各フェーズが持つメタ情報」節の 2 パターン):
   - 出力の完全一致を求める DoD が `$(...)` で比較していないか → `cmp` / `diff` に直す
   - 変更想定ファイルにエントリポイントが含まれるのに DoD がテストコマンドだけになっていないか → 結合テストか型検査を足す
7. **変更想定ファイルの衝突**: deps 上で並列になるフェーズ組の「変更想定ファイル」が重なっていないこと (3. の deps 検証と同じ判定を、推測ではなくこの一覧で行う)

#### ucs 宣言の検証 (`docs/USECASES.md` がある場合のみ)

USECASES.md が無い経路 (クイックモード等) では ucs 宣言自体を書かないので、本項をスキップする。

1. **全フェーズに `<!-- ucs: ... -->` があるか** (属する UC が無いなら `none` と明示)
2. **参照先が実在するか**: 各 `ucs` の識別子が USECASES.md の `## UC-<n>:` 見出しに存在すること
3. **単一指定になっているか**: カンマ区切りの複数 UC を書いていないこと (フェーズ 12 の sub-issue 紐付けは 1 子 issue = 1 親 issue のため)
4. **全 UC がカバーされているか**: USECASES.md の各 UC が、少なくとも 1 つのフェーズの `ucs` に現れること。**現れない UC は実装計画から漏れている** (そのユースケースはこのフェーズ分解では実現されない)
5. **テンプレートの説明文が混入していないか**: 抽出コマンドの出力に `UC-<n>` でも `none` でもない値 (`...` 等) が現れないこと

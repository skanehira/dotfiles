# TDD（テスト駆動開発）ルール

すべてのプロダクションコードは Kent Beck の TDD 方法論に従って記述する。

RED (失敗テスト) → GREEN (最小実装) → REFACTOR (グリーン時のみ) のサイクル順序を強制する機械ゲートは無い。順序は自律遵守し、実装が一段落したら `review-tdd` subagent (fresh context) でテスト品質を事後検証する (dev-impl / dev-impl-quick はフロー内にこのゲートを持つ)。本ドキュメントは順序と、レビューが判定する「質」の基準を定める。

## 各フェーズの質

- **RED**: 機能の小さな増分を定義する最もシンプルな失敗テストから始める。テスト名は動作を説明する意味のあるものにし、失敗を明確で情報量のあるものにする。テストは追加直後に実行して**失敗を観測する**。書いた直後に通ってしまうテストは機能の増分を定義しておらず RED として無効 (典型例: 「エラーが投げられないこと」「要素が存在しないこと」だけを検証する否定形・不在アサーションのテストは、対象が未実装の空実装でも green になる。→ `rules/core/testing.md` の「リトマス試験 B」と「アサーション」の否定形 3 条件)。本規定は**新しい振る舞いを追加する**テストに適用する。既存実装に対するシナリオ補完テスト・回帰の characterization テスト (`rules/core/testing.md`「シナリオ不足の能動検出」) は定義上 RED を経ないため対象外で、その旨を出力に明示すれば追加してよい
- **GREEN**: 現在のテストを通過させる最小限のコードのみ書く。それ以上は書かない
- **REFACTOR**: 重複を排除し、命名と構造で意図を表現し、メソッドを小さく単一責任に保つ。動作する最もシンプルな解決策を使う

## バグ修正プロセス

1. まずバグを示す API レベルの失敗テストを書く
2. 問題を再現する最小のテストを書く
3. 最小限のコード変更で両方のテストを通過させる

## 違反パターン（禁止）

- ❌ 失敗するテストなしにプロダクションコードを書く
- ❌ 追加直後に失敗を観測していないテストを、新しい振る舞いの RED とみなす
- ❌ テストを通過させるために必要以上のコードを書く
- ❌ テストがグリーンでないときにリファクタリングする
- ❌ 「後で追加する」意図でテストをスキップする
- ❌ 同じコミットで構造的変更と動作的変更を混ぜる

**覚えておくこと: テストなしにコードなし。これは交渉の余地がない。**

## Tidy First アプローチ

すべての変更を 2 タイプに分離し、同じコミットで混ぜない：

- **構造的変更 (STRUCTURAL)**: 動作を変更しない再配置 (リネーム・抽出・移動・フォーマット)。変更前後にテストを実行して動作が変わっていないことを検証する
- **動作的変更 (BEHAVIORAL)**: 機能追加・バグ修正・ロジック変更。最初に失敗するテストによって駆動する

両方が必要な場合は常に構造的変更を先に行う。

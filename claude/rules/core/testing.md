# テスト共通ルール

詳細なコード例 → `rules/core/references/testing-examples.md`、言語別テスト命名 → `references/test-naming.md`、テストダブルの使い分け → `references/test-doubles.md`（必要になったら Read する）。

## テスト戦略（上位方針）

- **テストピラミッド**: 単体・結合テストで詳細ロジックを網羅（IO は DI で差し替えて高速実行）。E2E は壊れたら業務に致命傷の golden path だけに絞り、増やさない。単体・結合で代替できる E2E は積極的に削除する
- **シナリオ不足の能動検出**: ユーザに指摘される前に、実装が一段落したら自発的に (1) 実装からユーザシナリオを書き起こし (2) 既存テストのカバレッジマップを作り (3) シナリオ × カバレッジ表で漏れを明示し (4) Critical / Major / Minor で優先度付けして提示する
- **テスト改善は方針が先**: 「何を厚く何を薄くするか」「削除・追加候補リスト」を文書化してから実装に着手する

## 基本原則

- テストは仕様であり実行可能なドキュメント。セーフティネットとして、失敗すべき時にのみ失敗する
- **実装ではなく振る舞いをテストする**。リトマス試験 A:「このテストが失敗した時、ユーザーにとって何が壊れたか説明できるか」。リファクタリングで壊れるテストは実装詳細をテストしている（設定値のアサーションは NG、ユーザーに見える出力のアサーションは OK）
- **空虚なテストを書かない**。リトマス試験 B:「テスト対象を no-op（何もしない関数・何も描画しないコンポーネント）に置き換えてもこのテストは通るか」。通るなら仕様を何も検証していない。**これが空虚性の唯一の判定**であり、後述の否定形 3 条件はリトマス B を満たすための十分条件チェックリストにすぎない（リトマス B に合格するテストを 3 条件の形式不備だけで不合格にはしない）
- テストの独立性: 実行順序に依存しない / 可変状態を共有しない / 作成したリソースを cleanup する / 一意のテストデータを使う

## セルフレビューチェックリスト（テスト実装後に必須）

1. **振る舞いのテストか？** 失敗時にユーザーへの影響を説明できるか
2. **トートロジーではないか？** getter が set した値を返すだけ等は無意味
3. **冗長なヘルパーはないか？** 1 行で済むものを抽出しない
4. **既存パターンを盲目的に踏襲していないか？** コピー元を評価せずに使わない
5. **空実装でも通るテストではないか？** 基本原則のリトマス試験 B（no-op に置き換えても通るか）を各テストに適用する。否定形・不在アサーション（エラーが投げられない / 要素が存在しない / undefined である）だけのテストが典型

いずれかに失敗したら、先に進む前にテストを修正する。

## アサーション

- 文字列は**完全一致**（`contains` 等の部分一致は禁止）。メッセージフォーマットの意図しない変更を検出し、期待出力を正確にドキュメント化するため
- 構造体は**全体比較**（個別フィールドのアサーションは禁止）。欠落・余剰・変更されたフィールドを検出するため
- 否定形・不在アサーション（`not.toThrow` / `queryByText(...)` が null / `undefined` であること等）は**単独では禁止**。「何が起きないか」は無限にあり、対象が未実装でも通ってしまうため。使うなら次の 3 条件を満たす。(b) は必須（これがリトマス B そのもの）、(a)(c) は品質シグナルで、欠けていれば否定形が妥当か再考する:
  - (a) 仕様自体が「〜しないこと」を要求している（例: disabled なボタンでは submit されない）
  - (b) **必須**。テスト本体に、**テスト対象を no-op に置き換えたら失敗する正のアサーション**が 1 つ以上ある。状態の assert（`expect(button).toBeDisabled()`）でも、対象が無ければ throw する取得クエリ（`getByRole(...)`）でもよい。`queryBy*` のように不在でも throw しないクエリは (b) を満たさない
  - (c) 対になる正の振る舞い（enabled なら submit される）が同一または隣接テストで検証されている
- ここでいう否定形とは「何かが起きない・存在しない」ことだけを述べるアサーションを指す。**戻り値や状態の期待値として `null` / `false` / 空配列を完全一致で assert するのは正のアサーション**であり対象外（例: 仕様「未登録キーは null を返す」に対する `expect(store.get('missing')).toBeNull()`、`expect(isValidEmail('')).toBe(false)`）
- 3 条件を満たさない否定形は「何が起きるか」の正のアサーションに書き換える（例: `not.toThrow()` → 戻り値の期待値を完全一致で assert）。コード例 → `rules/core/references/testing-examples.md`

## モックと外部依存

可能な限り実際の実装を使う。モックは 外部ネットワーク呼び出し / 分離が必要なファイルシステム操作 / 時間依存の振る舞い / 非決定的な操作 のみ。

## パラメータ化テスト

同じ関数に対しテスト構造が同一（setup → execute → assert）で入力と期待値だけが異なるテストが 2 つ以上できたら、REFACTOR フェーズで変換する。セットアップロジックや検証する振る舞い自体が異なる場合は変換しない。

## テスト構造・命名

- すべてのテストは AAA (Arrange-Act-Assert) パターンに従う
- テスト名は「何を・どういう条件で・どうなるか」の 3 要素を含める（例: `test_parse_version_with_invalid_input_returns_error`）

# finding の報告粒度 (族の全数走査)

`claude/agents/review-*.md` の 4 観点 (tdd / quality / product-readiness / adversarial) が
検査結果を報告する前に従う共通規範。**検査を始める前に Read する。**

## 列挙可能な族は必ず一括で走査する

**finding が「列挙可能な集合の 1 インスタンス」なら、報告する前に集合全体を走査し、1 件の finding にまとめる。**
1 インスタンスだけを報告すると、修正器は最小実装の原則に従ってその 1 件だけを直すため、兄弟が必ず生き残る。
すると次のラウンドで同じ型の指摘が出て、**修正ラウンド数が族の要素数と等しくなる**
(実測: 述語関数の比較項 7 個の被覆を 1 件ずつ報告したことで、1 フェーズが 4 ラウンドを消化した)。

族かどうかは「同じ判定を機械的に繰り返し適用できる対象が他にもあるか」で決める。典型:

| 族の例 | 走査する範囲 |
| --- | --- |
| 述語関数・比較関数の項が未 pin | その関数のすべての比較項 |
| 列挙型・union の一分岐が未処理 | その型のすべての分岐 |
| ある層のファイルが下位層を import | その層のすべてのファイル |
| ある API のエラー経路が未検証 | その API のすべてのエラーコード |
| 同じ形のフィクスチャが 1 属性しか動かしていない | その構造体のすべての属性 |
| ある画面の操作が二度押しを弾いていない | その画面のすべての送信操作 |
| ある往復の応答待ち中に別操作が通る | その往復が締め出すべきすべての操作 |

走査した結果は `evidence` に**全要素の判定を並べて書く**
(例: 「比較項 7 個を変異させ、parentId / body / sortOrder は killed、origin / kind / x / y が survived」)。
1 件だけ確かめて残りを推測で書かない — **走査していない要素は `evidence` にそう明記する**。
「族かもしれないが走査していない」と「走査して他は問題なかった」は、書き分けないと区別が付かない。

`fix_proposal` も族全体を一度に塞ぐ形で書く (個別のフィクスチャいじりではなく、
`rules/core/testing.md`「パラメータ化テスト」に沿った 1 本のパラメータ化テスト等)。

## この規範が効く相手

修正器 (`dev-impl-implementer` の `mode: fix`) は**ラウンド 1 から族単位で閉じる**規約になっている
(`skills/dev-impl/references/phase-execution.md` の `## 4.2d: 修正ラウンドの implementer 起動`)。
検査側が族を 1 件にまとめて出さないと、修正器は閉じるべき族の範囲を知る手段が無く、
指摘された箇所だけの局所修正に戻る。**報告粒度と修正粒度は対になっている。**

## finding を仕様条文に紐づける (traces_to)

**すべての finding に `traces_to` を必ず入れる。** 値は次のいずれか:

```json
"traces_to": { "id": "BR-1004", "quote": "履歴の移動中はノードの追加・削除を受け付けない" }
"traces_to": null
```

- `id`: issue の DoD 項目 / BR 番号 / DESIGN_DETAIL の節見出しのいずれか
- `quote`: **その条文の原文をそのまま引用した 1 文**。要約・言い換えをしない
- 紐づく条文が見つからなければ `null` にする。**探さずに `null` を書かない**

**`quote` を必須にするのは、呼び出し側が `rg -F` で実在を機械照合できるようにするためである。**
照合に失敗した `traces_to` は `null` として扱われる。ID だけを書かせると、
存在しない条文名をでっち上げれば「仕様に根拠がある」ことにでき、判定が骨抜きになる。

`null` は欠陥ではなく**情報**である。「実装が仕様から外れている」(条文あり) と
「仕様がその状況を何も定めていない」(条文なし) は、直す相手が違う。前者は実装、後者は仕様で、
呼び出し側 (dev-impl) はこの区別で修正ループを続けるか設計へ差し戻すかを決める
(`skills/dev-impl/SKILL.md` の 4.2d 手順 3)。**面倒がって `null` を返すと、
実装で直せる指摘まで仕様の欠陥として差し戻され、逆に条文をでっち上げると
仕様の穴が実装ループの中で溶けて見えなくなる。** どちらの方向にも壊れる。

# 決定台帳: AI が自律で issue を整理・設計・実装する開発フロー

- 種別: 決定台帳 (追記専用の作業記憶)
- 議題: 人は設計の確認だけを行い、issue の整理・設計・実装・merge を AI が自律で進める開発フローへ変える
- 開始: 2026-11-05 (業務のリポジトリで `/dev-impl` を実行中の議論から)

## 全体の流れ

- [決定] 新規開発は `/dev-spec` でユーザーストーリー・ユースケース・UI スケッチ・機能設計書を作り、`/dev-impl` で依存順に実装する — スクラッチ開発の初期段階は `/dev-spec` の役割のままにするため
- [決定] 機能追加は「人が issue を作る → AI が整理する → `dev-feat-spec` が設計 PR を出す → 人が PR をレビューして merge する → issue が ready になる → `/dev-impl` が実装・PR・merge まで進める → merge で close」とする — 人の作業を設計の確認に絞るため
- [決定] 人の役割は設計の確認だけとする。実装 PR は人が確認せず AI が merge する — 設計が正しければ、ハーネスが設計どおりに実装すると信用する運用にするため
- [決定] Deploy は人が実行する — 本番のデータに影響する変更 (例: あるテーブルの全行の削除) があるため
- [決定] 実装の merge で issue を自動 close する。`Closes #N` のまま使う — 人の確認を設計に絞ったので、merge 後の確認の状態は要らないため
- [棄却] merge 後に `verify` の状態を置いて人が結果を確認してから close する — 確認待ちがたまり (試したリポジトリでは直近 7 日の close が 91 件)、設計の確認に絞る方針とも合わないため
- [棄却] 実装 PR を人が確認して merge する — 人の作業が増え、自律で回す目的に反するため

## 設計 (dev-feat-spec)

- [決定] 機能追加専用のスキル `dev-feat-spec` を新設する。`/dev-spec` は新規開発の初期段階の役割に残す — ユーザーストーリーから作る初期段階と、既存の設計に足す機能追加では工程が違うため
- [決定] `dev-feat-spec` はユーザーに質問せず、ユーザー目線の UI/UX と、既存の実装と設計を踏まえたアーキテクチャ・コード設計を、人と同じ目線で書いて PR を出す — 既存の `/dev-spec` は設計中に質問が来るので自律で回らないため
- [決定] 判断できない点は質問せず、仮定を PR に明記して確認点として並べる。顧客の回答が要るものは `needs-human` で止める — 人の確認を PR のレビューに集めるため
- [決定] 設計書の変更が要らない issue (バグなど) は、設計 PR を出さず、issue に修正方針を書き、人の承認で ready にする — 小さな修正に PR の確認を求めると負担が大きいため
- [棄却] すべての issue に設計 PR を通す — 流れは 1 本になるが、小さな修正でも PR の確認が要るため

## 状態の管理

- [決定] ラベルは状態の管理、Project は人が状況を把握する目的で使う — AI が読むものと人が見るものの役割を分けるため
- [決定] `ready` は「人が仕様を承認した」印とする — 自律で実装を始める条件を、人の承認に結びつけるため
- [棄却] `ready` を「順位を見て人が今着手するものに付ける」印にする — 人が毎回選ぶ作業が残り、自律で回らないため
- [決定] 設計 PR の merge で `ready` を付ける処理は GitHub Actions で行う — AI の定期実行に頼るより確実なため
- [決定] Project に「設計レビュー」の列を足す — AI が検討中のものと人の確認待ちを分けるため
- [決定] リポジトリ作成時にラベルと Project を用意するセットアップスキルを新設し、用意された状態で `/dev-spec` を実行する — 状態の管理の前提を揃えるため

## 優先度

- [決定] 緊急枠に当たらない issue を 11 観点で採点する。観点は 影響 / 必須度 / 価値 / 運用 / 開発 / リスク / 期日 / 後続 / 広さ / 人の手間 / 確度 — バグ・機能開発・開発基盤を同じ物差しで比べるため
- [決定] スコア = (影響 + 必須度 + 価値 + 運用 + 開発 + リスク + 期日 + 後続) × 広さ ÷ 人の手間 × 確度 — 効果の広さと実装以外の負担と根拠の確かさを反映するため
- [決定] スコアの差が 2 割以内は同順位として人が決める — 点数の間隔は定まらず、小さな差には根拠がないため
- [決定] 枠組みと計算式はスキルに置き、プロジェクト固有の定義は各リポジトリの `docs/ISSUE_TRIAGE.md` に置く — スキルは全プロジェクト共通で、要件の表などはプロジェクトごとに違うため
- [決定] スコアの正本は issue 本文の `## 優先度` とし、順位表は本文から作る — AI が読むので 1 か所にまとめ、2 か所の更新の食い違いを防ぐため
- [決定] 採点は親 issue の単位で行い、子は親のスコアを引き継ぐ — 子に分けると土台の issue の点が下がるため
- [決定] `/dev-spec` が作る issue は採点しない — 初期段階はすべて実装する前提で、依存順で足りるため
- [棄却] 高・中・低の 3 段階 — 粒度が粗く、バグと機能開発を多角的に比べられないため
- [棄却] 点数をやめて上から順に問う判定にする — 基準を明確にして溜まった issue を整理するという目的には、観点ごとの定義のほうが合うため
- [棄却] 観点を重ねたまま 9 観点で数える — 「業務への影響と代替策の無さ」「目的の未達と利用者への価値」が同じ事実を二重に数えるため

## 実装 (/dev-impl)

- [決定] `/dev-impl` は依存を守ってスコアの高い順に着手する — スコアが高くても、依存先を先に実装する必要があるため
- [決定] 依存先は、依存元の高いほうのスコアを引き継ぐ — 低いスコアの依存先が後回しになり、高い issue が塞がれるのを防ぐため
- [決定] スコアが無い issue は従来どおり依存順に進める — `/dev-spec` の issue と、優先度を使わないプロジェクトの動きを変えないため
- [棄却] `/dev-impl` は優先度を読まず、人が `ready` の件数を絞って調整する — `ready` を人の承認に使うので、順位の調整に使えないため

## 作る順序

- [決定] 基準の確定と状態のラベルの定義 → セットアップスキル → `dev-feat-spec` → 整理スキル → `/dev-impl` の変更 → 定期起動 の順に作り、1 つずつ確かめる — 一度に自動化すると、問題の切り分けができないため

## 保留

- [保留] 状態のラベルの名前 (`spec-review` は仮) — 既存の `verification` などと紛らわしくない名前を、セットアップスキルの設計で決める → 解決 (下の「状態の定義」)
- [保留] 人が「修正方針を承認した」ことを AI が知る方法 (ラベルか列の移動か) — 設計書の変更が要らない issue の流れで決める → 解決 (下の「状態の定義」)
- [保留] 整理と `/dev-impl` の定期起動の仕組み、同時の実行数、費用の上限、止める条件 — 整理スキルと `/dev-impl` の変更を確かめてから決める
- [保留] `/dev-impl` を人の直接起動以外で動かしたときのモデル指定 — SKILL.md は直接起動を前提にしているので、定期起動の設計で確かめる
- [保留] 設計 PR が同時に複数出たときの設計書の競合の扱い — `dev-feat-spec` の設計で決める

## 状態の定義

- [決定] 状態は 未整理 (ラベルなし) / 設計待ち (`needs-design`) / 設計レビュー (`design-review`) / 着手可能 (`ready`) / 作業中 (`in-progress`) / 判断待ち (`needs-human`) の 6 つとし、merge で close して「完了」になる — 次に動くのが AI か人かをラベルだけで判定できるようにするため
- [決定] 承認の印は `ready` ラベルに統一する。設計 PR は人の merge で GitHub Actions が付け、修正方針は人が issue に付ける — ラベルなら Actions の起動条件に使え、AI も読めるため
- [棄却] 人が Project の列を動かして承認する — ラベルを状態の正本にする方針と合わないため
- [決定] ラベルが変わったら GitHub Actions が Project の列を動かす。`project` 権限のトークンはセットアップスキルで用意する — AI も人もラベルだけを見れば済むようにするため
- [決定] 列は状態だけにし、種別はラベルで見る。「バグ」「リファクタリング」の列はなくす — 種別の列では進み具合が読めないため
- [棄却] 今の列を残して新しい列を足す — バグの進み具合が列から読めないため
- [決定] 事業・運営の issue は区分で分け、開発の状態の列を使わず、AI の整理の対象から外す — 開発の流れに混ぜないため
- [棄却] 事業・運営の issue を別の Project に分ける — 移行の手間に見合わないため

## 文書の置き場所

- [決定] 設計書 (`docs/design/DESIGN.md`) は作らず、台帳を仕様にしてスキルを作る。運用の説明は `CLAUDE.md` の開発フローの節に書く — 設計書の型は製品の設計向けで、ハーネスの運用の変更には合わない節が多く、`CLAUDE.md` と内容が重なるため
- [決定] `CLAUDE.md` の開発フローの節は、スキルがそろった時点で書く — 存在しないスキルを先に書くと、手順が実態とずれるため

## セットアップスキル (dev-project-setup)

- [決定] スキル名は `dev-project-setup`。新しいリポジトリで `/dev-spec` より前に起動し、既存のリポジトリに足りないものを足す用途にも使えるよう、何度実行しても結果が変わらない作りにする — 運用中の既存のリポジトリにも同じ手順で入れるため
- [決定] 作るものはラベル (状態と種別)、Project (Status の列と区分の項目)、GitHub Actions 2 本 (ラベル → 列の同期、設計 PR の merge → `ready`)、`docs/ISSUE_TRIAGE.md` と `AGENTS.md` の運用の節の雛形 — 状態の管理の前提を揃えるため
- [決定] 「事業・運営」は使うかを起動時に選ぶ — プロジェクトによって要らないため
- [決定] Project はリポジトリの持ち主 (組織か個人) に作り、非公開にする — どのリポジトリでも使え、issue の状況を外に出さないため
- [棄却] Project を常に組織に作る — 個人のリポジトリで使えないため
- [決定] 優先度の雛形は、11 観点の名前・計算式・点数の定義の一般形まで書き、プロジェクト固有の部分は空欄にして記入を促す — すぐ使え、固有の部分の書き忘れも見えるため
- [棄却] 雛形に観点の名前と式だけを書く — 点数の定義を毎回ゼロから作ることになるため
- [決定] Project の組み込みの自動処理 (issue の自動追加、close で「完了」) は画面での設定手順を案内する — GraphQL に有効にする mutation が無い (2026-11-10 にスキーマで確認。`deleteProjectV2Workflow` だけがある)
- [決定] Actions が Project を更新するトークンは人が発行し、スキルは登録の手順を案内する — トークンの発行は人の認証を要するため → 撤回 (下の GitHub App の決定)
- [保留] テンプレートの Project を `copyProjectV2` で複製して、組み込みの自動処理とビューまで写す方式 — 手作業の設定を減らせるが、テンプレートの管理が要る。最初の版で手順の重さを見てから決める
- [決定] 検証は、ラベルと列を作成済みの既存のリポジトリに実行して行う。足りない Actions と雛形だけが加わることと、何度実行しても結果が変わらないことを確かめる — 実在のリポジトリで確かめるため

## Actions のトークン

- [決定] Actions のトークンは GitHub App で実行のたびに作る (`actions/create-github-app-token`、期限 1 時間)。App は持ち主に 1 つ作り、権限は Issues と組織の Projects に絞る。リポジトリには変数 `PROJECT_APP_CLIENT_ID` と secret `PROJECT_APP_PRIVATE_KEY` を登録する — 長期のトークンは期限切れのたびに再発行が要り、漏れたときの影響も大きいため
- [棄却] fine-grained personal access token を secret に置く — 期限切れの再発行が要り、`gh` からは発行できない (発行は Web の画面だけ)
- [棄却] 手元の `gh auth token` の値を secret に置く — `delete_repo` などの広い権限が Actions に渡るため
- [棄却] 列の同期を AI が手元の `gh` で行い、トークンを持たない — 列の更新が次の AI の実行まで遅れ、ボードを見た人が古い状態を読むため
- [保留] 個人の持ち物のリポジトリと Project での同期 — App の Projects 権限は組織の Project だけが対象の見込み (未検証)。個人のリポジトリで使うときに決める

- [決定] 雛形のワークフロー 2 本の `runs-on` は `${{ vars.RUNNER || 'ubuntu-latest' }}` にする — 組織の Actions の無料枠が尽きたとき、リポジトリ変数 `RUNNER` だけで self-hosted runner に切り替えるため (2026-11-10、組織の枠が尽きて、試したリポジトリを self-hosted runner に移した)。self-hosted runner のイメージには `gh` と `jq` が要る
- [決定] 同期の動作を既存のリポジトリで確かめた — テスト用の issue で、`needs-design` を付けて作ると「設計待ち」、close すると 32 秒で「完了」になった (2026-11-10)

# 決定台帳: AI が自律で issue を整理・設計・実装する開発フロー

- 種別: 決定台帳 (追記専用の作業記憶)
- 議題: 人は設計の確認だけを行い、issue の整理・設計・実装・merge を AI が自律で進める開発フローへ変える
- 開始: 2026-11-05 (業務のリポジトリで `/dev-impl` を実行中の議論から)

## 全体の流れ

- [決定] 新規開発は `/dev-spec` でユーザーストーリー・ユースケース・UI スケッチ・機能設計書を作り、`/dev-impl` で依存順に実装する — スクラッチ開発の初期段階は `/dev-spec` の役割のままにするため
- [決定] 機能追加は「人が issue を作る → AI が整理する → `dev-feat-spec` が設計 PR を出す → 人が PR をレビューして merge する → issue が ready になる → `/dev-impl` が実装・PR・merge まで進める → merge で close」とする — 人の作業を設計の確認に絞るため
- [決定] 人の役割は設計の確認だけとする。実装 PR は人が確認せず AI が merge する — 設計が正しければ、ハーネスが設計どおりに実装すると信用する運用にするため
- [決定] Deploy は人が実行する — 本番のデータに影響する変更 (例: あるテーブルの全行の削除) があるため
- [決定] 実装の merge で issue を自動 close する。`Closes #N` のまま使う — 人の確認を設計に絞ったので、merge 後の確認の状態は要らないため
- [棄却] merge 後に `verify` の状態を置いて人が結果を確認してから close する — 確認待ちがたまり (試したリポジトリでは直近 7 日の close が 91 件)、設計の確認に絞る方針とも合わないため
- [棄却] 実装 PR を人が確認して merge する — 人の作業が増え、自律で回す目的に反するため

## 設計 (dev-feat-spec)

- [決定] 機能追加専用のスキル `dev-feat-spec` を新設する。`/dev-spec` は新規開発の初期段階の役割に残す — ユーザーストーリーから作る初期段階と、既存の設計に足す機能追加では工程が違うため
- [決定] `dev-feat-spec` はユーザーに質問せず、ユーザー目線の UI/UX と、既存の実装と設計を踏まえたアーキテクチャ・コード設計を、人と同じ目線で書いて PR を出す — 既存の `/dev-spec` は設計中に質問が来るので自律で回らないため
- [決定] 判断できない点は質問せず、仮定を PR に明記して確認点として並べる。顧客の回答が要るものは `needs-human` で止める — 人の確認を PR のレビューに集めるため
- [決定] 設計書の変更が要らない issue (バグなど) は、設計 PR を出さず、issue に修正方針を書き、人の承認で ready にする — 小さな修正に PR の確認を求めると負担が大きいため
- [棄却] すべての issue に設計 PR を通す — 流れは 1 本になるが、小さな修正でも PR の確認が要るため

## 状態の管理

- [決定] ラベルは状態の管理、Project は人が状況を把握する目的で使う — AI が読むものと人が見るものの役割を分けるため
- [決定] `ready` は「人が仕様を承認した」印とする — 自律で実装を始める条件を、人の承認に結びつけるため
- [棄却] `ready` を「順位を見て人が今着手するものに付ける」印にする — 人が毎回選ぶ作業が残り、自律で回らないため
- [決定] 設計 PR の merge で `ready` を付ける処理は GitHub Actions で行う — AI の定期実行に頼るより確実なため
- [決定] Project に「設計レビュー」の列を足す — AI が検討中のものと人の確認待ちを分けるため
- [決定] リポジトリ作成時にラベルと Project を用意するセットアップスキルを新設し、用意された状態で `/dev-spec` を実行する — 状態の管理の前提を揃えるため

## 優先度

- [決定] 緊急枠に当たらない issue を 11 観点で採点する。観点は 影響 / 必須度 / 価値 / 運用 / 開発 / リスク / 期日 / 後続 / 広さ / 人の手間 / 確度 — バグ・機能開発・開発基盤を同じ物差しで比べるため
- [決定] スコア = (影響 + 必須度 + 価値 + 運用 + 開発 + リスク + 期日 + 後続) × 広さ ÷ 人の手間 × 確度 — 効果の広さと実装以外の負担と根拠の確かさを反映するため
- [決定] スコアの差が 2 割以内は同順位として人が決める — 点数の間隔は定まらず、小さな差には根拠がないため
- [決定] 枠組みと計算式はスキルに置き、プロジェクト固有の定義は各リポジトリの `docs/ISSUE_TRIAGE.md` に置く — スキルは全プロジェクト共通で、要件の表などはプロジェクトごとに違うため → 撤回 (下の「整理のスキル (dev-triage)」)
- [決定] スコアの正本は issue 本文の `## 優先度` とし、順位表は本文から作る — AI が読むので 1 か所にまとめ、2 か所の更新の食い違いを防ぐため
- [決定] 採点は親 issue の単位で行い、子は親のスコアを引き継ぐ — 子に分けると土台の issue の点が下がるため
- [決定] `/dev-spec` が作る issue は採点しない — 初期段階はすべて実装する前提で、依存順で足りるため
- [棄却] 高・中・低の 3 段階 — 粒度が粗く、バグと機能開発を多角的に比べられないため
- [棄却] 点数をやめて上から順に問う判定にする — 基準を明確にして溜まった issue を整理するという目的には、観点ごとの定義のほうが合うため
- [棄却] 観点を重ねたまま 9 観点で数える — 「業務への影響と代替策の無さ」「目的の未達と利用者への価値」が同じ事実を二重に数えるため

## 実装 (/dev-impl)

- [決定] `/dev-impl` は依存を守ってスコアの高い順に着手する — スコアが高くても、依存先を先に実装する必要があるため
- [決定] 依存先は、依存元の高いほうのスコアを引き継ぐ — 低いスコアの依存先が後回しになり、高い issue が塞がれるのを防ぐため
- [決定] スコアが無い issue は従来どおり依存順に進める — `/dev-spec` の issue と、優先度を使わないプロジェクトの動きを変えないため
- [棄却] `/dev-impl` は優先度を読まず、人が `ready` の件数を絞って調整する — `ready` を人の承認に使うので、順位の調整に使えないため

## 作る順序

- [決定] 基準の確定と状態のラベルの定義 → セットアップスキル → `dev-feat-spec` → 整理スキル → `/dev-impl` の変更 → 定期起動 の順に作り、1 つずつ確かめる — 一度に自動化すると、問題の切り分けができないため

## 保留

- [保留] 状態のラベルの名前 (`spec-review` は仮) — 既存の `verification` などと紛らわしくない名前を、セットアップスキルの設計で決める → 解決 (下の「状態の定義」)
- [保留] 人が「修正方針を承認した」ことを AI が知る方法 (ラベルか列の移動か) — 設計書の変更が要らない issue の流れで決める → 解決 (下の「状態の定義」)
- [保留] 整理と `/dev-impl` の定期起動の仕組み、同時の実行数、費用の上限、止める条件 — 整理スキルと `/dev-impl` の変更を確かめてから決める
- [保留] `/dev-impl` を人の直接起動以外で動かしたときのモデル指定 — SKILL.md は直接起動を前提にしているので、定期起動の設計で確かめる
- [保留] 設計 PR が同時に複数出たときの設計書の競合の扱い — `dev-feat-spec` の設計で決める → 解決 (下の「dev-feat-spec の設計」の、同じ機能設計書を変える open の設計 PR があれば飛ばす決定)

## 状態の定義

- [決定] 状態は 未整理 (ラベルなし) / 設計待ち (`needs-design`) / 設計レビュー (`design-review`) / 着手可能 (`ready`) / 作業中 (`in-progress`) / 判断待ち (`needs-human`) の 6 つとし、merge で close して「完了」になる — 次に動くのが AI か人かをラベルだけで判定できるようにするため
- [決定] 承認の印は `ready` ラベルに統一する。設計 PR は人の merge で GitHub Actions が付け、修正方針は人が issue に付ける — ラベルなら Actions の起動条件に使え、AI も読めるため
- [棄却] 人が Project の列を動かして承認する — ラベルを状態の正本にする方針と合わないため
- [決定] ラベルが変わったら GitHub Actions が Project の列を動かす。`project` 権限のトークンはセットアップスキルで用意する — AI も人もラベルだけを見れば済むようにするため
- [決定] 列は状態だけにし、種別はラベルで見る。「バグ」「リファクタリング」の列はなくす — 種別の列では進み具合が読めないため
- [棄却] 今の列を残して新しい列を足す — バグの進み具合が列から読めないため
- [決定] 事業・運営の issue は区分で分け、開発の状態の列を使わず、AI の整理の対象から外す — 開発の流れに混ぜないため
- [棄却] 事業・運営の issue を別の Project に分ける — 移行の手間に見合わないため

## 文書の置き場所

- [決定] 設計書 (`docs/design/DESIGN.md`) は作らず、台帳を仕様にしてスキルを作る。運用の説明は `CLAUDE.md` の開発フローの節に書く — 設計書の型は製品の設計向けで、ハーネスの運用の変更には合わない節が多く、`CLAUDE.md` と内容が重なるため
- [決定] `CLAUDE.md` の開発フローの節は、スキルがそろった時点で書く — 存在しないスキルを先に書くと、手順が実態とずれるため

## セットアップスキル (dev-project-setup)

- [決定] スキル名は `dev-project-setup`。新しいリポジトリで `/dev-spec` より前に起動し、既存のリポジトリに足りないものを足す用途にも使えるよう、何度実行しても結果が変わらない作りにする — 運用中の既存のリポジトリにも同じ手順で入れるため
- [決定] 作るものはラベル (状態と種別)、Project (Status の列と区分の項目)、GitHub Actions 2 本 (ラベル → 列の同期、設計 PR の merge → `ready`)、`docs/ISSUE_TRIAGE.md` と `AGENTS.md` の運用の節の雛形 — 状態の管理の前提を揃えるため → `docs/ISSUE_TRIAGE.md` の雛形は撤回 (下の「整理のスキル (dev-triage)」)
- [決定] 「事業・運営」は使うかを起動時に選ぶ — プロジェクトによって要らないため
- [決定] Project はリポジトリの持ち主 (組織か個人) に作り、非公開にする — どのリポジトリでも使え、issue の状況を外に出さないため
- [棄却] Project を常に組織に作る — 個人のリポジトリで使えないため
- [決定] 優先度の雛形は、11 観点の名前・計算式・点数の定義の一般形まで書き、プロジェクト固有の部分は空欄にして記入を促す — すぐ使え、固有の部分の書き忘れも見えるため
- [棄却] 雛形に観点の名前と式だけを書く — 点数の定義を毎回ゼロから作ることになるため
- [決定] Project の組み込みの自動処理 (issue の自動追加、close で「完了」) は画面での設定手順を案内する — GraphQL に有効にする mutation が無い (2026-11-10 にスキーマで確認。`deleteProjectV2Workflow` だけがある)
- [決定] Actions が Project を更新するトークンは人が発行し、スキルは登録の手順を案内する — トークンの発行は人の認証を要するため → 撤回 (下の GitHub App の決定)
- [保留] テンプレートの Project を `copyProjectV2` で複製して、組み込みの自動処理とビューまで写す方式 — 手作業の設定を減らせるが、テンプレートの管理が要る。最初の版で手順の重さを見てから決める
- [決定] 検証は、ラベルと列を作成済みの既存のリポジトリに実行して行う。足りない Actions と雛形だけが加わることと、何度実行しても結果が変わらないことを確かめる — 実在のリポジトリで確かめるため

## Actions のトークン

- [決定] Actions のトークンは GitHub App で実行のたびに作る (`actions/create-github-app-token`、期限 1 時間)。App は持ち主に 1 つ作り、権限は Issues と組織の Projects に絞る。リポジトリには変数 `PROJECT_APP_CLIENT_ID` と secret `PROJECT_APP_PRIVATE_KEY` を登録する — 長期のトークンは期限切れのたびに再発行が要り、漏れたときの影響も大きいため
- [棄却] fine-grained personal access token を secret に置く — 期限切れの再発行が要り、`gh` からは発行できない (発行は Web の画面だけ)
- [棄却] 手元の `gh auth token` の値を secret に置く — `delete_repo` などの広い権限が Actions に渡るため
- [棄却] 列の同期を AI が手元の `gh` で行い、トークンを持たない — 列の更新が次の AI の実行まで遅れ、ボードを見た人が古い状態を読むため
- [保留] 個人の持ち物のリポジトリと Project での同期 — App の Projects 権限は組織の Project だけが対象の見込み (未検証)。個人のリポジトリで使うときに決める

- [決定] 雛形のワークフロー 2 本の `runs-on` は `${{ vars.RUNNER || 'ubuntu-latest' }}` にする — 組織の Actions の無料枠が尽きたとき、リポジトリ変数 `RUNNER` だけで self-hosted runner に切り替えるため (2026-11-10、組織の枠が尽きて、試したリポジトリを self-hosted runner に移した)。self-hosted runner のイメージには `gh` と `jq` が要る
- [決定] 同期の動作を既存のリポジトリで確かめた — テスト用の issue で、`needs-design` を付けて作ると「設計待ち」、close すると 32 秒で「完了」になった (2026-11-10)

## dev-feat-spec の設計

- [決定] 入力は `needs-design` の open の issue。1 回の起動で、スコアの高い順にすべてを 1 件ずつ設計し、設計 PR は issue ごとに分ける — 定期起動にそのまま載せるため (2026-11-11)
- [棄却] 1 回の起動で指定した 1 件だけを扱う — 定期起動で件数の選び方を別に決める必要があるため
- [決定] issue を「設計書の変更が要る → 設計 PR」「要らない → issue に修正方針」「人か顧客の判断が要る → `needs-human`」に振り分ける。前の 2 つは `design-review` にする — 台帳の「設計 (dev-feat-spec)」の決定を 1 つの手順にまとめるため
- [決定] 設計書は `/dev-spec` の機能設計書の型 (`references/feature-doc.md`) で書き、issue の本文は `/dev-impl` が読む形 (ゴール / 設計 / DoD / 非スコープ / 依存 / 優先度) に書き直す — `/dev-impl` を変えずに、merge で `ready` になった issue をそのまま実装できるようにするため
- [決定] 大きな issue を分けるときは、設計 PR を出すときに子の issue を作って `design-review` を付け、PR の本文に子の分も `Design-for: #子` を書く — merge で親と子がまとめて `ready` になり、merge のあとに AI がもう一度動く必要が無いため
- [棄却] 子の issue を設計 PR の merge のあとに作る — merge のあとに AI がもう一度動く必要があり、`ready` になるまでが遅れるため
- [決定] 同じ機能設計書を変える open の設計 PR があれば、その issue は飛ばし、先の PR の merge のあとの起動で設計する — 設計 PR どうしの衝突を人に直させないため (台帳の保留「設計 PR が同時に複数出たときの設計書の競合の扱い」を解決)
- [棄却] 構わず出し、衝突は merge のときに人が直す — 人の手間が増えるため
- [決定] PR を出す前に、書き手と別のコンテキストの subagent に設計を検査させる (`/dev-spec` のフェーズ 8 と同じ観点)。high が残ったら PR を出さずに `needs-human` で止める — 書き手は自分の書き漏れを見つけにくく、人のレビューの前に穴を減らすため
- [決定] CI での設計は質問せずに進め、置いた仮定と、採らなかった案とその理由を PR の本文に残す — CI の実行はセッションが残らず、直すときのセッションが設計時の判断を引き継ぐ手段が PR の本文しかないため
- [決定] 設計 PR を直すときは、人が手元で `/dev-feat-spec <PR 番号>` を起動して指摘を伝える。直しの手順では人に質問してよく、設計書に合わせて issue の本文、子の issue、`Design-for:` の行を直し、検査をやり直し、受けた指摘と直した内容を PR にコメントで残す — 設計は人がレビューするので、レビューするときの手元のセッションで直すのが自然で、設計書だけを直すと issue が古いまま `ready` になるため
- [棄却] 設計 PR を作ったセッションに、そのまま指摘を伝えて直す — CI で定期実行するとセッションが残らないため
- [棄却] 次の起動が PR の未解決のレビューコメントを読んで自動で直す — 人はレビューのときに手元のセッションで直せば足り、仕組みを増やす理由が無いため
- [決定] issue を分けたときは、PR の `Design-for:` に子だけを書き、親は `needs-design` を外して `tracking` にする。子は本文に親の `## 優先度` を写す — 親に書くと merge で `tracking` の親にも `ready` が付き、/dev-impl の対象に紛れるため (2026-11-11、advisor の指摘)
- [決定] 同じ機能設計書に触れる設計 PR の判定は、issue ごとに PR の一覧を取り直して行う — 同じ起動の中で先に出した PR を見落とさないため
- [決定] `design/issue-<N>` のブランチが origin にあるのに open の PR が無い issue は、設計 PR が merge されずに close されたものとして、古いブランチを消して設計し直す。dev-feat-spec は同時に 1 つだけ起動する前提にする — 人が設計を却下して `needs-design` を付け直したあとも、ずっと飛ばし続けないため
- [保留] dev-feat-spec の同時実行を 1 にする仕組み — 定期起動の設計で決める

## 起動の仕組み (2026-11-11)

- [決定] 整理のスキルは、issue を作ったとき (`issues: opened`) に GitHub Actions で起動し、1 日 1 回、状態のラベルが無い open の issue を見回る。整理は 1 つずつ流す (`concurrency`)。状態のラベルがすでにある issue (AI が作った子など) は整理しない — 整理は軽いのですぐ行い、Mac が止まっていた間などの取りこぼしを見回りで拾うため → 撤回 (下の「ローカルの指揮」)
- [棄却] 整理を一定の間隔の定期起動だけで行う — issue を作ってから整理されるまで待たせる理由が無いため
- [棄却] 作ったときの起動だけで、見回りを持たない — self-hosted runner の待ちのジョブは取り消されうる (24 時間で取り消されるという理解で、未確認) ので、未整理の issue が残りうるため
- [決定] CI の LLM は、ARC の runner の上で DeepSeek Harness (`dsh`) を動かし、DGX Spark の DeepSeek を呼ぶ。スキルは `dsh` が対応する `~/.agents/skills` から読ませる — 料金がかからず、別の組織で動いている構成を使い回せるため → 撤回 (下の「ローカルの指揮」)
- [棄却] Claude Code をサブスクリプションのトークンで動かす — 枠を使い、1 件 $18 相当 (2026-11-11 の dev-feat-spec の 1 件の実測) の使用量が減るため
- [棄却] Claude Code を API キーで動かす — 1 件 $18 前後の料金が実際にかかるため
- [保留] `dsh` でスキルを動かすための読み替え — スキルが名指す `~/.claude/skills/…` と `~/.claude/rules/…` のパス、モデルを指定した subagent (検査は opus)、選択式の質問。`dsh` に subagent とモデルの指定があるかを調べてから決める → 撤回 (下の「ローカルの指揮」で CI で LLM を使う構成をやめた)
- [保留] 設計の質 — DeepSeek で Claude Code と同じ質の設計が出るかを、設計 PR にした issue を `dsh` で流して比べて確かめる → 撤回 (下の「ローカルの指揮」で CI で LLM を使う構成をやめた)
- [保留] スキルを Pod に渡す方法 — ジョブの中で dotfiles を checkout する (版を固定でき、Mac のファイルに頼らない) か、Mac のディレクトリを Pod に載せる (手元の編集がすぐ効く)。前者を推す → 撤回 (下の「ローカルの指揮」で CI で LLM を使う構成をやめた)

## ローカルの指揮 (2026-11-11)

- [決定] CI で LLM を使う構成はやめる。整理・設計・実装は、ローカルの Mac で Claude Code を動かして行う — `dsh` 向けにスキルを読み替え、設計の質を確かめ直す手間が大きいため
- [決定] dev-feat-spec を既存のリポジトリで試した。3 件のうち 2 件は設計 PR になり、1 件は先の設計 PR と同じ設計書に触れるので飛ばした。1 件あたり 13〜18 ドル相当、18〜20 分かかった — 定期起動の件数の上限を決める材料にするため
- [保留] 指揮の形 — 案は、launchd が 10 分おきにスクリプトを動かし、スクリプトが `gh` で仕事を探して、仕事ごとに新しい Claude Code を tmux で起動する形 (どの org・リポジトリでも使えるよう、対象は `repos.yaml` で選ぶ)。24 時間動く 1 つの Claude Code がチーム機能で指揮をとる形は、会話が積もり、待っている間も使用量を使うため推さない → 解決 (下の決定)
- [保留] 対象の issue の書き手を org のメンバーと collaborator に限るか — 公開のリポジトリで、外部の人が書いた本文が、権限の確認なしで動く Claude Code に読まれるのを防ぐため → 解決 (下の決定)
- [決定] 指揮は、launchd が 10 分おきにスクリプト (`agent-loop`) を動かし、スクリプトが `gh` で仕事を探して、仕事ごとに新しい Claude Code を tmux のウィンドウで起動する形にする。スクリプトは LLM を使わないので、仕事が無いときの費用は 0 — 指揮は決まった手順の繰り返しで、仕事ごとに新しい会話で始めれば会話が積もらないため
- [棄却] 24 時間動く 1 つの Claude Code がチーム機能で指揮をとる — 会話が積もって決まりや状態が抜け、待っている間も使用量を使うため
- [決定] スクリプト、状態のラベルの定義、対象のリポジトリの一覧 (`repos.yaml`) は dotfiles に置く。リポジトリには、採点の点数の定義などプロジェクトごとに違う中身 (`docs/ISSUE_TRIAGE.md` の固有の部分と `AGENTS.md`) だけを置く — この仕組みは issue とラベルにだけ依存し、リポジトリによらないため → `docs/ISSUE_TRIAGE.md` は任意になった (下の「整理のスキル (dev-triage)」)
- [決定] 対象の issue は、作成者が org のメンバーか collaborator のもの (`author_association`) に限る — 公開のリポジトリで、外部の人が書いた本文が、権限の確認なしで動く Claude Code に読まれるのを防ぐため
- [棄却] ジョブを herdr で起動する — herdr の名前付きの session は端末から `herdr session attach` で起動する必要があり、launchd から立ち上げられない (2026-11-11 に `script` での起動を試して立ち上がらなかった)。ループを herdr の中で動かす案は、Mac の再起動のたびに人が開き直す必要があるため
- [棄却] launchd から `claude -p` を端末なしで動かし、ログだけを残す — 動いている Claude Code の画面を見られず、止まったときに様子をつかみにくいため

## 整理のスキル (dev-triage) (2026-11-11)

- [決定] スキル名は `dev-triage`。行うのは、種別の確認、`区分` の設定、採点、状態のラベルを 1 つ付けることだけで、本文の書き直し、子への分割、DoD・依存・PoC の確認は行わない — 本文の書き直しと分割は `dev-feat-spec` の手順 5 が行い、DoD などの確認は人の承認 (`ready`) の前提なので、整理と重ねないため
- [決定] 対象は、open で、状態のラベルが無く、`事業・運営` も `tracking` も付いておらず、作成者が `OWNER` / `MEMBER` / `COLLABORATOR` の issue。1 回の起動で全件を 1 件ずつ整理し、人に質問しない — `agent-loop` からの起動で最後まで進むため。作成者の条件は「ローカルの指揮」の決定による
- [決定] 開発の issue は、親なら `tracking`、人か顧客の判断が要るなら `needs-human`、それ以外はすべて `needs-design` にする — 設計書の変更が要らない issue も `dev-feat-spec` が修正方針を書いて `design-review` にするので、流れを 1 本にするため
- [棄却] 決めることが無い issue は、整理の段階で修正方針を書いて `design-review` にする — 整理が重くなり、`dev-feat-spec` と役割が重なるため
- [決定] 判定する材料が足りない issue は、足りない情報をコメントで聞いて `needs-human` にする — ラベル無しのまま残すと、10 分おきの見回りで毎回整理し直すため。人が回答して `needs-human` を外すと、次の見回りで整理し直す
- [棄却] ラベル無しのまま残し、印のコメントで 2 回目以降を飛ばす — 状態のラベルで判定する方針から外れるため
- [決定] 緊急枠に当たる issue は、採点せず、緊急であることをコメントに書いて `needs-human` にする — `ready` は人だけが付けるので、整理のスキルからは着手させられないため
- [棄却] 緊急枠でも `needs-design` にし、緊急の印を本文に書く — 人が気付くのが設計レビューのときまで遅れるため
- [決定] 本文に `## 優先度` があれば採点し直さない — 規約の「全件の定期的な見直しはしない」に合わせるため
- [決定] `docs/ISSUE_TRIAGE.md` を必須でなくする。状態の定義、着手可能の基準、優先度の定義は dotfiles のスキルの references (`dev-triage/references/`) に置き、どのリポジトリでもそれだけで動くようにする。プロジェクト固有の定義があるリポジトリは `docs/ISSUE_TRIAGE.md` を置いてよく、あれば、そこに書かれた定義をスキルの定義より優先して判定に使う — スキルは他のプロジェクトでも使うため、リポジトリの準備なしに使えるようにする
- [決定] `dev-project-setup` は `docs/ISSUE_TRIAGE.md` の雛形を置かない — 定義の正本がスキルの references に移ったため
- [決定] 試しは既存のリポジトリで行う。未整理の開発の issue が採点済みのものしか無いので、採点されていないテスト用の issue を 1 件作って一緒に流し、確かめたら close する — 採点の手順まで確かめるため (列の同期を確かめたのと同じやり方)
- [決定] 1 回の起動で整理するのは最大 10 件、作られてから 10 分経っていない issue は飛ばす — 溜まった issue を一度に処理して 1 つの会話に積もらないようにし、書きかけの本文を「読み取れない」と判定しないため (2026-11-11、別のコンテキストのレビューの指摘)
- [決定] 途中で失敗した issue は、失敗のコメントを書いて `needs-human` にする — ラベル無しのまま残すと、次の起動で同じ失敗を繰り返すため
- [決定] `needs-human` への回答は、dev-triage のコメント (末尾の `<!-- dev-triage -->`) より後の人のコメントとして読み、回答で解消した理由では止め直さない — 本文だけで判定すると、緊急枠や判断待ちに当たり続けて人との往復が終わらないため
- [決定] origin に `issue-<N>` ブランチがある未整理の issue は、設計し直さずに `needs-human` に戻し、`ready` を付けるよう案内する — `/dev-impl` が止めた issue で人が `ready` を付け忘れると、設計済みの issue がもう一度設計されるため
- [決定] 緊急枠の issue は本文の `## 優先度` に `緊急枠` と書き、`dev-feat-spec` はこれを先頭に並べる — 採点しないので、スコアの順では最後に回るため
- [決定] 親として扱うのは sub-issue のある issue だけにし、子は親の `## 優先度` を写す — sub-issue の無い親は `/dev-impl` が close せず、人が作った子は単独で採点されてしまうため
- [決定] `区分` は、変数 `PROJECT_OWNER` / `PROJECT_NUMBER` があり Project に項目があるときに dev-triage が設定する — `dev-project-setup` が項目を作るのに、設定する人がいなかったため
- [決定] dev-triage は同時に 1 つだけ起動する前提にし、反映の直前にラベルと本文を取り直して、先に整理済みなら飛ばす — 起動が 10 分を超えたときに重ねて追記しないため
- [保留] `agent-loop` の仕事の判定 — dev-triage の手順 1 の条件 (作成者と 10 分の条件を含む) をそのまま使う。dev-triage が GitHub に書き込めずに止まったときに、同じ失敗の起動を繰り返さない仕組み、dev-feat-spec の 1 回の起動の件数の上限 (1 件 13〜18 ドル相当) とあわせて、`agent-loop` の設計で決める

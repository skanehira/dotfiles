# 実装手続きのルール

CLAUDE.md「実装時」から遅延参照する詳細。設計原則は `~/.claude/guidelines/core/design.md`、TDD は `tdd.md`、テスト方針は `testing.md`、検証コマンドの規律は `verification.md` に分かれている (いずれも同ディレクトリ)。

## TDD とレビュー

- TDD で実装する (→ `~/.claude/guidelines/core/tdd.md`)。RED→GREEN→REFACTOR の順序と「実装編集後の再テスト」は機械ゲートではなく自律遵守する。TDD を適用しない判断 (typo 修正・宣言的 config 変更など、観測可能な振る舞いを変えない編集) をした場合はその理由を出力に明示する
- 実装が一段落したら**レビュー subagent で事後検証する**。スキル (dev-impl / dev-impl-quick) を使う場合はフロー内のレビューゲートに任せ、スキルを使わない実装 (plan mode・直接依頼) では自分で起動する:
  - テスト差分がまとまっている (新規テストファイル or 20 行超) → `review-impl` subagent (`model: "opus"` 明示、`focus: tests`・`report_path` 指定) でテスト品質を検証し、high と medium の findings を修正してからテストを再実行する
  - 複数観点で見たい差分 (機能追加・リファクタ) → `/workflow-review` で全項目レビュー (focus: all)

## 設計と変更範囲

- API は Clean Architecture + DDD で設計する
- 最小実装を徹底する。頼まれていない機能・抽象化・柔軟性・不可能シナリオの error handling は追加しない
- 仕様に明示されていない実装の細部 (デフォルト値・パス形式・ログフォーマット・機能の適用範囲)を選択した場合は、その選択と根拠を出力内に明示する。ユーザーが意図との乖離に気づける状態にする
- 変更は外科的に行う (コード対象。ドキュメントは `~/.claude/guidelines/core/documentation.md` の全体整合優先が上書きする)。依頼にトレースできない改変・隣接コードの改善・依頼にトレースできない既存 dead code の削除はしない (dead code は報告に留める)。自分の変更で未使用になった import / 変数 / 関数のみ片付ける
- 既存資産 (他プロジェクトの設定ファイル等) を引用された場合は、それをベースに採用する。ゼロから組み立てない

## コードコメント

コードコメントは基本的に書かない。実装の仕方はコード自身が、仕様はテストが、変更の理由はコミットログと設計書が持つ。

残してよいのは、コードとテストでは表せない次の 5 種だけである。どれに当たるか迷うコメントは消す。

| 種類 (報告に書く名前) | 残してよいもの | 例 |
| --- | --- | --- |
| `legal` | 著作権・ライセンスの表記 | `// SPDX-License-Identifier: MIT` |
| `external` | 変えられない外部 (依存ライブラリ・プラットフォーム・プロトコル・他システム) が強いる、読んでも分からない挙動 | `// D1 は 1 文に束縛できる変数が 100 個まで` |
| `api` | 公開 API の契約を伝えるドキュメントコメント (rustdoc / godoc / JSDoc / docstring)、スクリプトの使い方と終了コード。モジュールの外から使わない関数・テストのヘルパー・部品の説明は含まない | `/// 見つからなければ None を返す` (公開関数) |
| `link` | コードで表せない制約を説明する、外部の issue や RFC へのリンク。作業の issue 番号 (「#42 対応」) は含まない | `// https://www.rfc-editor.org/rfc/rfc9110#section-8.8.3` |
| `directive` | 道具が読む指示。formatter や lint の抑止は、プロジェクトの規約と技術別の guidelines が認める場面だけで、求められた理由を添える。`// SAFETY:` と、技術別の guidelines が書くよう求める理由のコメントを含む | `// prettier-ignore` |

- **自分たちのコードの分かりにくさは、コメントで補わずにコードで直す**: 改名、関数の抽出、型、定数の名前を使う。採らなかった選択肢の理由は、コミットログか設計書に書く
- **守ってほしい順序や条件は、テストで固定する**: 例えば「同じ優先度のジョブは投入順に流す」は、順序を確かめるテストにする。`sort.SliceStable` を選んだ理由のコメントは要らない
- **書かないもの**: コードの言い換え、次の行の予告、区切りの見出し、コメントアウトしたコード、変更履歴、自信の無さを埋める言葉 (「念のため」「たぶん」)、理由の無い TODO
- **既存のコメント**: 変更で事実と合わなくなったものは消す。変更と関係の無いものは触らない (「設計と変更範囲」)

### 自己点検 (実装が一段落するたびに行う)

追加したコメント行をスクリプトで抽出し、5 種のどれにも当たらない行を消す。書いた直後のコメントは書いた本人には必要に見えるので、記憶で判断しない。

1. `sh ~/.claude/skills/dev-impl/scripts/added-comments.sh <リポジトリ> <基準のコミット>` を実行する。追加した行のうちコメントを含むものが、`<パス>:<行番号>` 付きで出る。`docs/` と Markdown は対象外である
2. 1 行ずつ 5 種に当てはめ、当たらない行を消す。消して意味が分からなくなるなら、上の方法でコードを直す。コメントでない行 (複数行の文字列の中の `//` など) と、移動しただけの既存のコメントは、消さずに `not_added` とする
3. もう一度実行し、残った行と種類を完了報告に書く。例: 「残したコメント 1 行。`db.ts:12` は `external` (D1 の変数の上限)」
4. スクリプトが対応していない言語のファイル (`style_of` に無い拡張子) は、差分を目で確かめる

## 動作検証

- Web アプリ: 検証の作業量で手段を選ぶ
  - 単発の軽い確認 (1〜2 画面を 1 回見れば済む・スタイル調整程度): `chrome-devtools` MCP で実物確認 (DOM スナップショット + console error/warning)
  - 検証フローが複数ある / 修正→確認のループを回す場合: 実装を調べて Playwright のテストコードを書き、テスト実行 (exit code) で検証する (MCP の逐次操作はスナップショットごとのトークン消費が激しいため)
- API: `curl`
- 修正後は**必ず**前回より悪化していないか自分でチェックしてから完了報告する

## 多段タスクの進め方

着手前にゴールと DoD (完了をどのコマンド・出力で確認するか) を明文化し、「独立して検証可能な単位 × 不確実性の高い順 (spike を先頭)」に分解して、1 単位ずつ観測ベースで検証しながら進める (「コードを書いたから動くはず」は検証ではない)。全単位消化後は DoD と照合してから完了報告する (タスク消化 ≠ ゴール達成)。

# テスト共通ルール

詳細なコード例 → `~/.claude/guidelines/core/references/testing-examples.md`、言語別テスト命名 → `references/test-naming.md`、テストダブルの使い分け → `references/test-doubles.md`（必要になったら Read する）。

## テスト戦略（上位方針）

- **テストピラミッド**: 単体・結合テストで詳細ロジックを網羅（IO は DI で差し替えて高速実行）。E2E は壊れたら業務に致命傷の golden path だけに絞り、増やさない。単体・結合で代替できる E2E は積極的に削除する。E2E の中で何を確かめ、何を確かめないかは「E2E で確かめること」に従う
- **シナリオ不足の能動検出**: ユーザに指摘される前に、実装が一段落したら自発的に (1) 実装からユーザシナリオを書き起こし (2) 既存テストのカバレッジマップを作り (3) シナリオ × カバレッジ表で漏れを明示し (4) Critical / Major / Minor で優先度付けして提示する
- **テスト改善は方針が先**: 「何を厚く何を薄くするか」「削除・追加候補リスト」を文書化してから実装に着手する

## テストを書くかを先に決める

レベル (単体 / 結合 / E2E) を選ぶ前に、その振る舞いにテストが要るかを決める。テストは書いた後も、実行時間と、仕様を変えるたびに直す手間を払い続ける。守る価値がその費用を上回るものだけを書く。

判断は規則の機械的な当てはめではなく、次の 2 つを利用者・開発・保守の視点で見て総合的に行う。

| 見ること | 高い例 | 低い例 |
| --- | --- | --- |
| 壊れる確率 (複雑さ) | 分岐・状態遷移・計算・時刻・並行操作・外部との往復を含む。仕様が頻繁に変わる | 分岐の無い表示。受け取った値を渡すだけ。ライブラリの機能をそのまま使うだけ |
| 壊れたときの範囲と深刻さ | データが消える・金額を誤る・権限が漏れる・主要な操作ができなくなる。壊れても気づきにくい | 開けばすぐ分かり、直せば済む。ほかの画面やデータに波及しない |

| 視点 | 問い |
| --- | --- |
| 利用者 | 壊れたら何ができなくなるか。利用者は壊れたことに気づけるか |
| 開発 | リファクタや仕様変更のとき、このテストは壊れたことを早く知らせるか。実装の細部に縛られて変更の足を引っ張らないか |
| 保守 | 実行時間・不安定さ・文言を変えるたびに直す手間に見合うか。ほかのテストが同じ壊れ方で既に落ちないか |

- 2 つとも低いものはテストしない。どちらかが高ければ書き、レベルは高いほうの理由に合わせて選ぶ (分岐が多いが影響が 1 つの部品に閉じる → 単体で網羅する。影響が層をまたぐ → 結合・E2E)
- 設計書の「テスト方針」の表でテストしないと決めた行は、レベルの代わりに `なし (<理由>)` と書く。理由には、2 つの軸がそれぞれなぜ低いかを書く (例: `なし (分岐が無く、壊れれば開いた時点で分かる。golden path の E2E も同じ画面から始まるので一緒に落ちる)`)
- テストのための目印 (`data-*` 属性など) は、役割や名前 (`getByRole` / `getByLabel`) で要素を取れないときだけ足す。目印は E2E が待ったり要素を特定したりする手段であり、目印が付くこと自体はテストしない

例 (React の早押しゲームで実際に書かれた 2 本):

- 操作を 1 つもせず「`/` を開くと、ヘッダーとフッターの中に開始前の画面が出る」だけを確かめる E2E: 分岐が無く壊れる確率が低い。壊れれば開いた時点で分かり、ほかのデータに波及しない。golden path の E2E はどれも `/` を開いてから始まるので、表示が壊れればそちらも落ちる。よって書かない
- 外枠の部品に渡した `data-*` 属性が `<main>` にそのまま付くことを確かめる単体テスト: 受け取った値を渡すだけで壊れる確率が低く、その属性で待つ E2E が壊れれば落ちる。下のリトマス試験 A (利用者にとって何が壊れたか) にも答えられない。よって書かない

## 基本原則

- テストは仕様であり実行可能なドキュメント。セーフティネットとして、失敗すべき時にのみ失敗する
- **実装ではなく振る舞いをテストする**。リトマス試験 A:「このテストが失敗した時、ユーザーにとって何が壊れたか説明できるか」。リファクタリングで壊れるテストは実装詳細をテストしている（設定値のアサーションは NG、ユーザーに見える出力のアサーションは OK）
- **空虚なテストを書かない**。リトマス試験 B:「テスト対象を no-op（何もしない関数・何も描画しないコンポーネント）に置き換えてもこのテストは通るか」。通るなら仕様を何も検証していない。**これが空虚性の唯一の判定**であり、後述の否定形 3 条件はリトマス B を満たすための十分条件チェックリストにすぎない（リトマス B に合格するテストを 3 条件の形式不備だけで不合格にはしない）
- テストの独立性: 実行順序に依存しない / 可変状態を共有しない / 作成したリソースを cleanup する / 一意のテストデータを使う
- **テストの実行が出した警告は、テストが pass していても不合格として扱う**。React の `act(...)` の警告や、ライブラリの非推奨の警告が典型である。警告は、テストが待たずに終えた処理や、想定の外で起きた更新を示す。残したまま増えると、新しい警告が埋もれて誰も読まなくなる。React の `act(...)` の警告の直し方は `~/.claude/guidelines/frontend/react/testing.md` にある。エージェントから実行すると pass したテストの警告が表示されないことがあるので、数える前に `~/.claude/guidelines/core/verification.md`「5. ランナーが pass したテストの出力を隠した」の対策をとる

## セルフレビューチェックリスト（テスト実装後に必須）

1. **振る舞いのテストか？** 失敗時にユーザーへの影響を説明できるか
2. **トートロジーではないか？** getter が set した値を返すだけ等は無意味
3. **冗長なヘルパーはないか？** 1 行で済むものを抽出しない
4. **既存パターンを盲目的に踏襲していないか？** コピー元を評価せずに使わない
5. **空実装でも通るテストではないか？** 基本原則のリトマス試験 B（no-op に置き換えても通るか）を各テストに適用する。否定形・不在アサーション（エラーが投げられない / 要素が存在しない / undefined である）だけのテストが典型
6. **書く価値があるか？** 「テストを書くかを先に決める」の 2 つの軸がどちらも低いテストを書いていないか。props や `data-*` 属性を素通しするだけのテストが典型
7. **行ごとに別の不具合を見つけるか？** パラメータ化した表の各行に、「テストの数を決める」の基準を当てる。`cross-product.sh` の出力が 0 件であることと、手で並べた表 (`flatMap` で 1 つの一覧を手で書いた複数の形に広げた表を含む) に全組み合わせが無いことを確かめる

いずれかに失敗したら、先に進む前にテストを修正する。

## アサーション

- 文字列は**完全一致**（`contains` 等の部分一致は禁止）。メッセージフォーマットの意図しない変更を検出し、期待出力を正確にドキュメント化するため
- 構造体は**全体比較**（個別フィールドのアサーションは禁止）。欠落・余剰・変更されたフィールドを検出するため
- 否定形・不在アサーション（`not.toThrow` / `queryByText(...)` が null / `undefined` であること等）は**単独では禁止**。「何が起きないか」は無限にあり、対象が未実装でも通ってしまうため。使うなら次の 3 条件を満たす。(b) は必須（これがリトマス B そのもの）、(a)(c) は品質シグナルで、欠けていれば否定形が妥当か再考する:
  - (a) 仕様自体が「〜しないこと」を要求している（例: disabled なボタンでは submit されない）
  - (b) **必須**。テスト本体に、**テスト対象を no-op に置き換えたら失敗する正のアサーション**が 1 つ以上ある。状態の assert（`expect(button).toBeDisabled()`）でも、対象が無ければ throw する取得クエリ（`getByRole(...)`）でもよい。`queryBy*` のように不在でも throw しないクエリは (b) を満たさない
  - (c) 対になる正の振る舞い（enabled なら submit される）が同一または隣接テストで検証されている
- ここでいう否定形とは「何かが起きない・存在しない」ことだけを述べるアサーションを指す。**戻り値や状態の期待値として `null` / `false` / 空配列を完全一致で assert するのは正のアサーション**であり対象外（例: 仕様「未登録キーは null を返す」に対する `expect(store.get('missing')).toBeNull()`、`expect(isValidEmail('')).toBe(false)`）
- 3 条件を満たさない否定形は「何が起きるか」の正のアサーションに書き換える（例: `not.toThrow()` → 戻り値の期待値を完全一致で assert）。コード例 → `~/.claude/guidelines/core/references/testing-examples.md`

## E2E で確かめること

E2E は、画面からサーバと DB を通り、別の画面やメールに結果が現れるまでの流れを、本物どうしをつないで確かめるテストである。1 本に数秒から数十秒かかり、文言やデータの細部を変えるたびに落ちる。ほかのテストで確かめられることは E2E に入れない。実装する人もレビューする人も、この節で E2E の中身を判定する。

**E2E で確かめるもの**

- 画面の遷移と、ログインしていないとき・権限が無いときの行き先
- 操作の結果が、表示・別の画面・届いたメール・ダウンロードしたファイルに現れること。確かめるのは「表示が出た」「メールが届いた」「一覧に行が増えた」までで、中身の細部は下の表の確かめ先に任せる
- 本物のログイン・セッション・Cookie を通ること
- 画面に本物の部品 (API を呼ぶ部品など) が渡されていること。単体テストでは代わりの部品に差し替えるので、ここでしか通らない

**E2E で確かめないもの**

| 確かめること | 確かめる場所 | 例 |
| --- | --- | --- |
| 案内・説明・エラーの文言の中身、日付・金額・件数の書式 | 画面の単体テスト (完全一致) | 「リンクは30分間有効です。」を含む送信後の案内 |
| 計算結果、境界値、入力の上限と異常系 | 単体テスト、サーバの結合テスト | 請求データの税額・合計の値、上限を 1 文字超える本文 |
| API の応答の中身、権限による拒否、DB に書かれた値 | サーバの結合テスト | 403 の応答本文、監査ログに書かれた行 |

- ボタン・リンク・見出しを名前で探すこと (`getByRole("button", { name: "送信" })`) は要素の特定で、ここで言う「文言の中身を確かめる」には当たらない。E2E で比べないのは、説明文・案内・エラー文の本文を期待値として置くことである (例: `toHaveText("…")` や `getByText("…", { exact: true })` を確かめに使う)
- 受け入れ基準の行が文言を含み、そのレベルが E2E のときは、E2E では表示が出たことだけを確かめ、文言は画面の単体テストで完全一致に確かめる。2 本のテストをあわせて、その行を確かめたことにする

**流れの途中を画面の外で済ませない**

- 流れの途中の操作を、API の直接呼び出しで済ませない。画面が送る要求と API の約束のつなぎ目を飛ばしたまま通ってしまう。合否を DB の読み取りで決めることもしない
- DB を直接書くのは、前提データの用意と後片付けに限る
- 同じ流れを複数の E2E でなぞらない。ほかの流れの前提として必要な状態は、前提データで用意する
- プロジェクトが例外を定めている場合 (例: 外部決済の完了通知だけは API で済ませてよい) は、その例外に従う

## モックと外部依存

可能な限り実際の実装を使う。テストダブルに置き換えてよいのは 外部ネットワーク呼び出し / 分離が必要なファイルシステム操作 / 時間依存の振る舞い / 非決定的な操作 のみ。

**「実際の実装」にはローカルで動く本物を含む**。ローカル DB・エミュレータ・組み込みストレージが手元と CI で動くなら、それは外部ネットワーク呼び出しに当たらないので本物を使う。とくに **Repository の in-memory fake を作らない** — 一意性制約・トランザクションの原子性・クエリの意味論を再現できず、fake で緑になっても本番の SQL は未検証のまま残るため。

ダブルが要ると判断した後の選び方（優先順位と `vi.mock` を使わない理由）→ `~/.claude/guidelines/core/design.md`「外界 (IO) は必ず DI」。

## 待ち時間を作らない

テストの中で実時間が過ぎるのを待たない。待ちはテストの本数だけ積み上がり、1 本の待ちが全体の時間を支配する (実測: OTP の送信間隔 60 秒を実時間で待つ E2E が 1 本あるだけで、E2E 全体が 58 秒から 117 秒になった)。

- **時間が経った状態は作る**: 期限・間隔・有効期限・時刻の切り替わりに依存する振る舞いは、時計を DI で差し替えて進める (`~/.claude/guidelines/core/design.md`「外界 (IO) は必ず DI」)。E2E でサーバの時刻に依存するときは、E2E の起動でだけ有効な時計の口を使うか、前提データを作る段で「時間が経った状態」を作る
- **制限の境界は単体・結合テストで確かめる**: 送信間隔・レート制限・有効期限は、注入した時計で直前 (例: 59,999 ms) とちょうど (60,000 ms) を確かめる。E2E では同じ待ちを繰り返さない
- **待ってよいのは条件だけ**: 画面や状態の条件が成り立つまでの待ち (Playwright の auto-wait、状態を見る `expect.poll`) は使う。固定時間の `sleep` / `waitForTimeout` と、実時刻を見て時間が過ぎるのを待つ poll は足さない
- **テスト対象外の外部への要求を待たない**: E2E で読み込む Web フォントや解析タグなどは遮断する。Playwright の `route` を登録したコンテキストは HTTP キャッシュが無効になり、2 回目以降のページ読み込みが遅くなる。遮断はブラウザの起動引数 (`--host-resolver-rules`) など、route を使わない方法で行い、前後の所要時間を測る
- **ログインは使い回す**: ログインそのものを確かめるテスト以外は、役割ごとに 1 回だけ画面からログインした状態を使い回す (Playwright なら setup project で `storageState` を保存し、各テストはそれを読み込む)。役割を替えるときもログインし直さず、保存した状態に入れ替える。共有のログイン状態でログアウトやセッションの取り消しをしない (同じ状態を使う後続のテストが未認証になる)
- **足したテストの所要時間を見る**: テストを足したら実行結果の所要時間を確かめ、同じ系統の中で 1 本だけ突出して長いもの (目安: 中央値の数倍) は待ちが無いかを調べる

## テストの数を決める

テストの行は、それぞれが別の不具合を見つけるときだけ足す。同じ不具合でしか落ちない行は、実行時間と直す手間を増やすだけで、検出力を上げない。

- **行ごとに、その行だけが見つける不具合を言えるようにする。** その行だけが見つける不具合とは、本体のある行の書き換え (`<file>:<line>` の `old` → `new`) のうち、その行を外すと残りのテストがどれも落ちなくなるものをいう。言えない行は書かない。例: 取り込む由来の一覧から `stock` が抜けると、`stock` の行だけが落ちる。一方、括弧を含む題名を `developer` と `queued` の 2 つの由来で確かめる 2 行は、どちらも前置きの解析の不具合でしか落ちないので、1 行でよい
- **入力を同値クラスに分け、クラスごとに代表を 1 つ選ぶ。** 同値クラスは、仕様が同じに扱うと決めている入力のまとまりである。クラスは実装の分岐ではなく仕様で分ける。仕様が値ごとに扱いを挙げている一覧は、値ごとに 1 クラスにする。実装が 1 つの `includes` で判定していても、一覧から値が 1 つ抜ける不具合は値ごとに起きるためである。仕様が挙げていない値の一覧を、本体の定数から写してテストに並べない。写した行は、一覧を書き換えたときにしか落ちず、本体と一緒に書き換えるだけになる
- **境界は両側を 1 つずつ確かめる。** 上限が 120 字なら、120 字と 121 字の 2 行にする。境界から離れた値は足さない
- **互いの値を読まない入力は掛け合わせない。** 1 つの入力を変える行では、ほかの入力を代表の値に固定する。掛け合わせてよいのは、1 つの分岐が両方の値を読むときだけで、掛け合わせる値もその分岐が読む組に限る
- **1 つの規則は 1 つのレベルで網羅する。** 書式・境界・組み合わせは単体テストで網羅し、結合テストは層をつないだことを代表 1 件で確かめる。設計書の「テスト方針」の表がレベルを割り当てた行は、その割り当てに従う。E2E の分担は「E2E で確かめること」にある
- **同じ構造のテストはパラメータ化する。** 同じ関数に対して setup → execute → assert の構造が同じで、入力と期待値だけが違うテストが 2 つ以上できたら、REFACTOR でパラメータ化する。セットアップや確かめる振る舞いが違うものは変換しない。パラメータ化した表にも、上の基準を行ごとに当てる

例: 由来 8 通り (うち 5 つを取り込み、3 つを除く) とタスクの形 13 通りを読む関数で、由来の判定と前置きの解析が別の分岐のとき

```ts
// ❌ 8 × 13 = 104 行。由来の不具合は 13 行、解析の不具合は 5 行が同じ理由でまとめて落ちる
it.each(shapes.flatMap((shape) => origins.map((origin) => ({ ...shape, origin }))))(/* … */);

// ✅ 8 + 13 = 21 行。どの行にも、その行だけが見つける不具合がある
it.each(origins)("由来 %s の取り込み", (origin) => { /* 形は代表の 1 つに固定 */ });
it.each(shapes)("$id「$title」の前置きを外す", (shape) => { /* 由来は developer に固定 */ });
```

**掛け合わせを残すときは理由を書く。** 生成の始まりの行か、その直前 3 行に、`cross-product:` に続けて、両方の値を読むコードの `<file>:<line>` を書いたコメントを置く (例: `// cross-product: src/keymap.ts:42 がモードとキーを同じ分岐で読む`)。レビューは、その行のコードが両方の値を読んでいるかを開いて確かめる。このコメントは検出スクリプトが読む指示なので、`implementation.md`「コードコメント」の `directive` に当たる。

**掛け合わせは検出スクリプトで見つける。** `sh ~/.claude/skills/dev-impl/scripts/cross-product.sh <リポジトリ> <基準のコミット>` は、基準からの差分が足したか変えたテストのうち、表を生成して掛け合わせるものを `<パス>:<行番号>` と種類で出す。終了コードは、見つからなければ 0、見つかれば 1 である。理由のコメントがあるものは出さない。対象の書き方は次のとおりである。

| 言語 | 検出する書き方 |
| --- | --- |
| JS・TS (vitest・jest) | `.each` / `.for` に、互いに独立な一覧を掛け合わせた表を渡す。表は、`flatMap`・`map`・`Array.from` を入れ子にした式か、その式を入れた変数か、入れ子のループで `push` した変数である。`describe.each` の中で `.each` を使う。入れ子のループ (`for`・`forEach`・`.each`・`.for`) の中で `it` / `test` を呼ぶ |
| Go | 入れ子の `for` (`range` と 3 節の `for`) の中で `t.Run(…, func…)` を呼ぶ。入れ子の `for` で表に `append` し、その表を回す `for` の中で `t.Run` を呼ぶ |
| Rust (rstest) | `#[values]` (`#[files]` を含む) を 2 つ以上使う。`#[case]` か `#[apply]` と `#[values]` を併用する |

内側の一覧が外側の値から取られる階層の表 (例: `for (const c of group.cases)`) と、1 つの一覧を広げただけの表 (例: `limits.flatMap((n) => [n, n + 1])`) は、掛け合わせに数えない。全組み合わせを手で 1 行ずつ並べた表と、`flatMap` で 1 つの一覧を手で書いた複数の形に広げた表は検出しない。セルフレビューとレビューで見る。

## テスト構造・命名

- すべてのテストは AAA (Arrange-Act-Assert) パターンに従う
- テスト名は「何を・どういう条件で・どうなるか」の 3 要素を含める（例: `test_parse_version_with_invalid_input_returns_error`）

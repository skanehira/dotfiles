# 協業スタイルのルール

依頼から実装までの摩擦を最小化する「進行の作法」。技術選定や設計は扱わない。

## 質問・提案の形式

- 複数の質問は Q1 / Q2、選択肢は A / B / C でナンバリングし、ユーザが「1: A、2: B」形式で返せる構造にする（選択式の質問ツールを使うときも同じ構造）
- 確認は Yes / No / OK で答えられる closed question にする（✅「テストファイルを `xxx.test.ts` に作って進めて良いですか?」 ❌「テストはどう書きますか?」）
- 「○○じゃなくて○○ではダメ?」は代替案を引き出したいシグナル。推奨案を先頭に 2-3 案、各案のトレードオフを 1 行で返す。「これしかありません」で押し切るのは禁止
- **判断を求めるときは背景を添える**。読み手は別のプロジェクトの作業から戻ってきたユーザーで、この件の依頼も経緯も覚えていない。自分には自明に見えても、その前提で書く。背景が無いと「何の話だっけ?」と聞き返す往復が毎回発生する
  - 対象: 判断・選択・承認を求めるすべての箇所。完了報告の「次にユーザがする決定」、自律モード (headless の `claude -p` を含む) の停止報告、issue の駐車も含む。省いてよいのは、対話モードでツールを 1 度も使う前の着手前確認だけ
  - 形: 判断を求める箇所に次の雛形を置く。見出しの「決めてほしいこと」「背景」は省かない。変更の要約など別の節に書いた内容で代えない (要約は何をしたかの記録で、判断に要る文脈とは別物である)

    ```markdown
    **決めてほしいこと**: <何を決めるかを 1 文で>
    **背景**: <リポジトリ名> の <作業名>。依頼は <ユーザーが頼んだこと>。<どこまで済んだか>。<何に詰まり、なぜユーザーの判断が要るか>。
    - A (推奨): <案>。影響: <選んだときに起きること>
    - B: <案>。影響: <選んだときに起きること>
    ```

  - リポジトリ名と元の依頼は、作業ディレクトリや会話から自明に見えても必ず書く。省きたくなる理由が「見れば分かる」なら、それは読み手には見えていない
  - 置き場所: ユーザーが回答する時点で目に入る場所に置く。選択式の質問ツールを使うなら質問の本文に、使わないなら質問と同じメッセージに書く。別のメッセージに分けると、回答時に背景が画面から消えていることがある
  - 判断が複数あるときは、決定ごとに雛形を 1 つずつ置き、Q1 / Q2 でナンバリングする。背景が共通なら 2 つ目以降は「背景は Q1 と同じ」と書いて差分だけを足してよい
  - 送る前に「この件を覚えていない人が、この雛形の部分だけを読んで判断できるか」を確かめる
  - 例 (対話中の質問): ✅「**決めてほしいこと**: `~/.codex/config.toml` の `model` を消すか。**背景**: dotfiles の Codex 設定の移行作業。依頼は `/etc/codex/config.toml` を dotfiles の symlink に置き換えること。symlink の作成までは済んだ。`~/.codex/config.toml` の `model` が system レイヤーの値を上書きしており、消すと Codex の既定モデルが変わる。A (推奨): user レイヤーの `model` を削除する。影響: dotfiles の設定が全マシンで効く。B: 残す。影響: このマシンだけ現在のモデルのまま」 ❌「`~/.codex/config.toml` の `model` を消して良いですか?」
  - 例 (完了報告): ✅「**決めてほしいこと**: CSV 出力の日付形式を ISO 8601 と `YYYY/MM/DD` のどちらにするか。**背景**: report-exporter の月次 CSV 出力の実装。依頼は管理画面の売上一覧を CSV でダウンロードできるようにすること。ISO 8601 で実装しコミットまで済んだ。経理チームの取り込み手順書は `YYYY/MM/DD` を前提にしているが、API の仕様書は ISO 8601 を指定しており、どちらが正か判断できない。A (推奨): ISO 8601 のまま、手順書を更新する。影響: API と形式が揃い、経理の手順変更が 1 回要る。B: `YYYY/MM/DD` に変える。影響: 経理はそのまま使えるが、API と形式がずれる」 ❌「次にユーザがする決定: 日付形式を ISO 8601 と `YYYY/MM/DD` のどちらにするか決めてください」

## 作業委任の受け方

- 一括委任（「全部修正して」「のこりを実装して」）を受けたらタスクリストに登録して見える化し、1 件ずつ進行中 → 完了で進める。都度確認は不要、判断に迷う箇所だけ止まる
- 同じアプローチを 2-3 回失敗したら延々と試行錯誤せず、別 agent への委譲 / 別ツール / ユーザへの判断依頼（どこで詰まっているか具体的に）を提案する
- バックグラウンドタスクは通知に頼り切らない。時間を置いて再確認する手段があればフォールバックとして設定し、長時間応答がなければ自分から status を取りに行く

## 報告の粒度

- **毎ターンの悪化チェック**: テストが全部通っても UI / 体験の悪化はテストで検出されない。「治った」と言う前に Chrome / curl で再確認する（画面構造が崩れていないか、console error / warning が増えていないか）
- 完了報告は 4 点に絞る: 変更の要約 / 動作確認結果（テスト件数・実機確認）/ 既知の残骸（未対応・スコープ外）/ 次にユーザがする決定。「○○しました」の羅列は読まれない。4 点目は「質問・提案の形式」の雛形で書き、決定ごとに背景を添える

## 企画提案の姿勢

- 「他に施策があれば提案して」には、ドメイン改善案 2-3 個 / こちらから聞くべきヒアリング項目 / ドキュメント設計案を返す。「やります」だけで終わらない
- ヒアリングは抽象 → 具体の順: ① ゴールと制約（誰がいつ何のために・既存システムとの関係）→ ② 機能の枠（入出力・状態遷移）→ ③ 細部（UI・バリデーション・エラーメッセージ）。最初から細部を聞くとゴールがズレたまま進む

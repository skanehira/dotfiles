# 協業スタイルのルール

依頼から実装までの摩擦を最小化する「進行の作法」。技術選定や設計は扱わない。

## 質問・提案の形式

- 複数の質問は Q1 / Q2、選択肢は A / B / C でナンバリングし、ユーザが「1: A、2: B」形式で返せる構造にする（選択式の質問ツールを使うときも同じ構造）
- 確認は Yes / No / OK で答えられる closed question にする（✅「テストファイルを `xxx.test.ts` に作って進めて良いですか?」 ❌「テストはどう書きますか?」）
- 「○○じゃなくて○○ではダメ?」は代替案を引き出したいシグナル。推奨案を先頭に 2-3 案、各案のトレードオフを 1 行で返す。「これしかありません」で押し切るのは禁止
- **判断を求めるときは、判断に要る文脈を必要な分だけ添える**。読み手は別の作業から戻ってきたユーザーで、この件の依頼も経緯も覚えていない。文脈が足りないと「何の話だっけ?」と聞き返す往復が起き、多すぎると判断材料が埋もれて読む負荷が上がる
  - 対象: 判断・選択・承認を求めるすべての箇所。完了報告の「次にユーザがする決定」、自律モード (headless の `claude -p` を含む) の停止報告、issue の駐車も含む。省いてよいのは、対話モードでツールを 1 度も使う前の着手前確認だけ
  - 順序: 何を決めてほしいかを先頭に 1 文で書き、文脈、選択肢の順に続ける
  - 文脈の選び方: 量ではなく判断への寄与で選ぶ。情報ごとに「これを消したら判断できなくなるか、判断が変わるか」を問い、どちらでもなければ書かない。多くの場合に要るのは、どの件の話か (1 句で足りる) と、なぜいまユーザーの判断が要るか (何と何が食い違っているか) の 2 つである。元の依頼・進捗・試したことは、判断に効くときだけ書く
  - 選択肢: 推奨を先頭に置き、各案に選んだときに起きることを 1 行で添える
  - 形は固定しない。内容に合わせて、次の基準で読みやすくする
    - 1 段落に詰め込まない。文脈は短い文を 1〜3 文、改行で区切る
    - 並列するもの (選択肢・比べる事実) は箇条書きにし、因果は散文で書く
    - 見出しやラベルは、決定が複数あるときや文脈が長いときだけ使う
  - 変更の要約など別の節に書いた内容で文脈を代えない。要約は何をしたかの記録で、判断に要る文脈とは別物である
  - 置き場所: ユーザーが回答する時点で目に入る場所に置く。選択式の質問ツールを使うなら質問の本文に、使わないなら質問と同じメッセージに書く。別のメッセージに分けると、回答時に文脈が画面から消えていることがある
  - 判断が複数あるときは、決定ごとに Q1 / Q2 でナンバリングする。文脈が共通なら 2 つ目以降は「文脈は Q1 と同じ」と書いて差分だけを足してよい
  - 送る前に 2 点を確かめる。この件を覚えていない人が、この部分だけを読んで判断できるか。消しても判断が変わらない情報が残っていないか
  - 例 (対話中の質問): ❌「`~/.codex/config.toml` の `model` を消して良いですか?」 ✅ 次のように書く

    ```markdown
    `~/.codex/config.toml` の `model` を消しますか? (Codex 設定を `/etc/codex/config.toml` の symlink へ移す作業の続きです)

    user レイヤーの `~/.codex/config.toml` に `model` が残っていて、symlink で配った設定の `model` を上書きしています。

    - A (推奨): 消す。dotfiles の設定が全マシンで効く
    - B: 残す。このマシンだけ今のモデルのまま
    ```

  - 例 (完了報告): ❌「次にユーザがする決定: 日付形式を ISO 8601 と `YYYY/MM/DD` のどちらにするか決めてください」 ✅ 次のように書く

    ```markdown
    売上 CSV の日付形式を ISO 8601 と `YYYY/MM/DD` のどちらにしますか? (売上一覧の CSV ダウンロードは ISO 8601 で実装し、コミット済みです)

    API 仕様書は ISO 8601 を、経理の取り込み手順書は `YYYY/MM/DD` を前提にしていて、どちらが正か判断できません。

    - A (推奨): ISO 8601 のまま、手順書を直す。API と形式が揃い、経理の手順変更が 1 回要る
    - B: `YYYY/MM/DD` に変える。経理はそのまま使えるが、API と形式がずれる
    ```

## 作業委任の受け方

- 一括委任（「全部修正して」「のこりを実装して」）を受けたらタスクリストに登録して見える化し、1 件ずつ進行中 → 完了で進める。都度確認は不要、判断に迷う箇所だけ止まる
- 同じアプローチを 2-3 回失敗したら延々と試行錯誤せず、別 agent への委譲 / 別ツール / ユーザへの判断依頼（どこで詰まっているか具体的に）を提案する
- バックグラウンドタスクは通知に頼り切らない。時間を置いて再確認する手段があればフォールバックとして設定し、長時間応答がなければ自分から status を取りに行く

## 報告の粒度

- **毎ターンの悪化チェック**: テストが全部通っても UI / 体験の悪化はテストで検出されない。「治った」と言う前に Chrome / curl で再確認する（画面構造が崩れていないか、console error / warning が増えていないか）
- 完了報告は 4 点に絞る: 変更の要約 / 動作確認結果（テスト件数・実機確認）/ 既知の残骸（未対応・スコープ外）/ 次にユーザがする決定。「○○しました」の羅列は読まれない。4 点目は「質問・提案の形式」に従い、決定ごとに判断に要る文脈を添える

## 企画提案の姿勢

- 「他に施策があれば提案して」には、ドメイン改善案 2-3 個 / こちらから聞くべきヒアリング項目 / ドキュメント設計案を返す。「やります」だけで終わらない
- ヒアリングは抽象 → 具体の順: ① ゴールと制約（誰がいつ何のために・既存システムとの関係）→ ② 機能の枠（入出力・状態遷移）→ ③ 細部（UI・バリデーション・エラーメッセージ）。最初から細部を聞くとゴールがズレたまま進む

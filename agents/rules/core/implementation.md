# 実装手続きのルール

CLAUDE.md「実装時」から遅延参照する詳細。設計原則は `~/.claude/rules/core/design.md`、TDD は `tdd.md`、テスト方針は `testing.md`、検証コマンドの規律は `verification.md` に分かれている (いずれも同ディレクトリ)。

## TDD とレビュー

- TDD で実装する (→ `~/.claude/rules/core/tdd.md`)。RED→GREEN→REFACTOR の順序と「実装編集後の再テスト」は機械ゲートではなく自律遵守する。TDD を適用しない判断 (typo 修正・宣言的 config 変更など、観測可能な振る舞いを変えない編集) をした場合はその理由を出力に明示する
- 実装が一段落したら**レビュー subagent で事後検証する**。スキル (dev-impl / dev-impl-quick) を使う場合はフロー内のレビューゲートに任せ、スキルを使わない実装 (plan mode・直接依頼) では自分で起動する:
  - テスト差分がまとまっている (新規テストファイル or 20 行超) → `review-impl` subagent (`model: "opus"` 明示、`focus: tests`・`report_path` 指定) でテスト品質を検証し、high/medium findings を修正してからテストを再実行する
  - 複数観点で見たい差分 (機能追加・リファクタ) → `/workflow-review` で全項目レビュー (focus: all)

## 設計と変更範囲

- API は Clean Architecture + DDD で設計する
- 最小実装を徹底する。頼まれていない機能・抽象化・柔軟性・不可能シナリオの error handling は追加しない
- 仕様に明示されていない実装の細部 (デフォルト値・パス形式・ログフォーマット・機能の適用範囲)を選択した場合は、その選択と根拠を出力内に明示する。ユーザーが意図との乖離に気づける状態にする
- 変更は外科的に行う (コード対象。ドキュメントは `~/.claude/rules/core/documentation.md` の全体整合優先が上書きする)。依頼にトレースできない改変・隣接コードの改善・依頼にトレースできない既存 dead code の削除はしない (dead code は報告に留める)。自分の変更で未使用になった import / 変数 / 関数のみ片付ける
- 既存資産 (他プロジェクトの設定ファイル等) を引用された場合は、それをベースに採用する。ゼロから組み立てない

## コードコメント

t_wada (和田卓人) の指針を規範にする ([2017-09-05 の投稿](https://x.com/t_wada/status/904916106153828352))。

> コードには How / テストコードには What / コミットログには Why / コードコメントには Why not を書こう

情報には置き場所がある。実装の仕方はコード自身が、仕様はテストが、変更の理由はコミットログが持つ。コードコメントには、ほかのどこにも置けない情報だけを残す。

- **書く**: Why not、つまりあえて採らなかった選択肢と、その理由。読み手が「なぜ X を使わないのか」と思う箇所に置く。コードから復元できない外部の制約 (他システムの仕様・運用上の事情) と、それがコードをどう縛るかもここに含める
- **書かない**:
  - What の再述。コードの動作の言い換え、関数名や変数名の言い換え、次の行の予告。消すと意味が分からなくなるなら、コメントではなく命名や関数の抽出でコードに移す
  - 変更履歴 (「旧実装は〜だった」「〜に変更」)。置き場所はコミットログ
  - タスク ID や issue 番号の参照 (「#42 対応」)。置き場所はコミットログと issue
  - 実装に自信が無い箇所を言葉で埋めるもの (「たぶん」「念のため」、理由の無い TODO)。自信が無いならテストで確かめる
- **対象外**: 公開 API のドキュメントコメント (rustdoc / godoc / JSDoc / docstring) と `// SAFETY:`。利用者にインターフェースの仕様を伝えるもので、言語別 rules (例: `~/.claude/rules/backend/rust/coding.md`「ドキュメンテーション」「SAFETYコメント」) に従う

t_wada の言葉は引用の 1 文だけである。「Why not」を「あえて採らなかった選択肢と、その理由」と読むのは二次情報による解釈で、「書かない」の列挙は AI が書いたコメントを集計した報告に基づくこのハーネスの運用規則である。

- ✅ `// sort.Slice ではなく sort.SliceStable: 同じ優先度のジョブは投入順に流す契約で、呼び出し側がこの順序に依存している`
- ❌ `// ジョブを優先度順に並べる` (直下の sort 呼び出しの言い換え)

### 自己点検 (実装が一段落するたびに行う)

書いた直後のコメントは、書いた本人には必要に見える。記憶で判断せず、差分から抽出して 1 行ずつ判定する。

1. 追加されたコメント行を抽出する。例: `git diff <base> -U0 | rg '^\+.*(#|//)'`。パターンは言語のコメント記法に合わせて変える
2. 1 行ずつ「書く」「書かない」「対象外」に当てはめ、「書かない」に当たる行を消す
3. 抽出が 0 件のときは、差分にコメントが本当に無いかを目で確かめる。パターンが記法に合っていないだけかもしれない (`~/.claude/rules/core/verification.md` の陰性対照)
4. 抽出した行と判定を完了報告に 1〜数行で残す。例: 「追加コメント 2 行。`sort.SliceStable` の理由は Why not なので残し、`ジョブを並べる` は What なので消した」

## 動作検証

- Web アプリ: 検証の作業量で手段を選ぶ
  - 単発の軽い確認 (1〜2 画面を 1 回見れば済む・スタイル調整程度): `chrome-devtools` MCP で実物確認 (DOM スナップショット + console error/warning)
  - 検証フローが複数ある / 修正→確認のループを回す場合: 実装を調べて Playwright のテストコードを書き、テスト実行 (exit code) で検証する (MCP の逐次操作はスナップショットごとのトークン消費が激しいため)
- API: `curl`
- 修正後は**必ず**前回より悪化していないか自分でチェックしてから完了報告する

## 多段タスクの進め方

着手前にゴールと DoD (完了をどのコマンド・出力で確認するか) を明文化し、「独立して検証可能な単位 × 不確実性の高い順 (spike を先頭)」に分解して、1 単位ずつ観測ベースで検証しながら進める (「コードを書いたから動くはず」は検証ではない)。全単位消化後は DoD と照合してから完了報告する (タスク消化 ≠ ゴール達成)。

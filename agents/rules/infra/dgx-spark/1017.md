## 起動と判定

```bash
ssh spark-head
cd ~/DeepSeek-v4.1-Flash-1017-2x-DGX-Sparks
PULL=0 ./start.sh                 # 両ランクの起動。準備が要れば scripts/prepare.sh を自動で流し、スモークテストまで行う (PULL=0 →「レシピを更新する」)
./start.sh restart                # 設定を変えた後の再起動
./stop.sh                         # 両ランクの停止 (ログを保存してからコンテナを消す)
docker logs -f dsv41-1017-exl3-tf # rank 0 のログ。rank 1 は worker で同じものを打つ
```

- **エージェントのシェル実行からは、ログインシェルを通して切り離す。** `prepare.sh` は `hf` (`~/.local/bin`) が PATH に無いと止まる。2026-10-22 は次の形で打ち、待ちは `until ssh -n spark-head 'grep -q "^EXIT=" ~/dsv41-1017-start.log'; do sleep 30; done`、成否はログ最後の `EXIT=0` で判定した

  ```bash
  ssh spark-head 'bash -s' <<'REMOTE'
  : > ~/dsv41-1017-start.log
  setsid nohup bash -lc 'cd ~/DeepSeek-v4.1-Flash-1017-2x-DGX-Sparks && PULL=0 ./start.sh; r=$?; printf "EXIT=%s\n" "$r"; exit $r' > ~/dsv41-1017-start.log 2>&1 < /dev/null &
  REMOTE
  ```

- **準備の要否は `start.sh` が判定する。** 状態は `~/.local/state/dsv41-tensorfold/prepared` にあり、イメージ・重みの revision・kit・worker の置き場所・`ABLIT` のどれかが変われば `prepare.sh` を流す (`PREPARE=0` で飛ばす)
- **`start.sh` は他の系統を止めない。** 準備が要る状態で打つと、他の系統の配信中でもイメージのビルドと大きな書き込みが始まる。先に `dgx-spark.md`「系統の切り替え」の手順 1〜3 で相手を止める
- **事前検査で止まる。** 両ノードの `MemAvailable` が 112 GiB 未満か、8888 が使用中なら何も起動せずに終わる
- **引数なしの `./start.sh` は、両ランクが動いていれば何もしない**

**起動できたかは 3 段で判定する** (どれも exit code で合否が出る)。ログの `DeepSeek-V4.1-Flash-1017 is now LIVE!` も条件に入れる。2026-10-22 は 3 段とも通った (`'323'`)。

```bash
curl -fs -o /dev/null http://spark-head.local:8888/health && echo health-ok   # 1. API が生きている
curl -s http://spark-head.local:8888/v1/models | python3 -c 'import json,sys; ids=[m["id"] for m in json.load(sys.stdin)["data"]]; print(ids); sys.exit(0 if "DeepSeek-V4.1-Flash-1017" in ids else 1)'   # 2. 配信名
curl -s http://spark-head.local:8888/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"DeepSeek-V4.1-Flash-1017","messages":[{"role":"user","content":"17*19 を計算して、答えの数値だけを出力してください。説明や単位は不要です。"}],"temperature":0,"max_tokens":2048,"chat_template_kwargs":{"enable_thinking":false}}' \
  | python3 -c 'import json,sys; c=json.load(sys.stdin)["choices"][0]["message"]["content"].strip(); print(repr(c)); sys.exit(0 if c=="323" else 1)'   # 3. 生成が通る
```

**止める前に稼働中のリクエストを見る。** `vllm:` の系列が無いので `/health` の `live.connections` (実行中) と `live.waiting` (待ち) が両方 0 であることを見る。`stop.sh` も `live.connections` で稼働中を数える。

```bash
curl -s http://spark-head.local:8888/health | python3 -c 'import json,sys; l=json.load(sys.stdin)["live"]; print("running", l["connections"], "waiting", l["waiting"])'
```

**`stop.sh` の exit code は判定に使わない。** 止められなかったノードや一覧を取れなかったノードがあると exit 1 を返すが、止まったかは `dgx-spark.md`「系統の切り替え」の手順 3 のコマンドで見る。

**起動の所要時間 (実測)**

- 準備が全部入った初回 (2026-10-22): 約 76 分 (GLM の停止 09:44 → LIVE 11:01)。内訳はベースイメージの pull (WiFi で約 23 分)、Zig のビルド、rank 0 の重みファイル、worker への Engram のコピーと rank 1 の重みファイル
- エンジンの pin だけが変わる更新 (2026-10-30): 約 14 分 (停止 09:00 → LIVE 09:14)。イメージのビルド (Zig 2 回) と worker への送付だけが走り、重みファイルは作り直さなかった (ログに `Weight file of rank 0: ready`)。`loaded in 42.7s`、`Server answered after 49s`

**単一ストリームの decode** は 68.8 / 80.8 tok/s (2026-10-22、エンジン `629c524`、n=2。日本語の散文 512 トークン、thinking off、`temperature` 1、`top_p` 0.95、ストリーミングで最初のトークン以降を計測)。`fbbc971` では測り直していない。

**起動に失敗したとき**は `docker logs dsv41-1017-exl3-tf` と、停止済みのランクの `~/.cache/dsv41-tensorfold/logs/` を読む。

- `only … GiB memory available` / `port 8888 is already in use` — 相手の系統が動いている
- `cannot mount this Spark's … over NFS` — head の NFS サーバか `/etc/exports` (→「導入手順」4)
- 配信中に落ちた — memguard の kill を疑い、`~/.cache/dsv41-tensorfold/logs/memguard.log` を読む

## reasoning effort の語彙

`/v1/chat/completions` で 2026-10-22 に実測し、2026-10-30 に `bogus` の 400 と `max` の 200 を確かめ直した。セルは HTTP ステータス、質問は「2+3 は?」、`temperature` 0。

| 値 | `/v1/chat/completions` | 思考 (`reasoning_content`) |
| --- | --- | --- |
| `none` | 200 | 0 文字 |
| `minimal` / `low` / `medium` / `high` / `xhigh` / `max` | 200 | 45〜46 文字 |
| 語彙外 (`bogus`) | 400 | — |

- **400 の本文は受理語彙を名乗る**: `reasoning_effort must be none, minimal, low, medium, high, xhigh or max` (GLM 系の TensorFold と同じ文言)
- **テンプレート (`model/chat_template.jinja`) が知っているのは `low` / `high` / `max` と 1〜100 の整数だけで、** それぞれ 50 / 75 / 100 として描く。`minimal` / `medium` / `xhigh` の読み替え先は確かめていない
- **この質問では思考の長さが 7 値でほぼ同じで、** 深さの違いは確かめていない
- **OpenCode は `max` を送る** (テンプレートの 100)。陽性対照は `bogus` (400)、陰性対照は `max` (200)

## 導入手順

2026-10-20〜22 に踏んだ順序と各段の完了判定である。**1〜4 は配信を止めずに進められ、5 から 8888 が止まる。** 重みは `utility-spark-model-fetch` の対象外である (本体は head だけに置いて worker は NFS で読み、Engram は `prepare.sh` が worker へコピーする)。モデルを差し替えるときは `scripts/config.sh` が解決する `MODEL_ID` / `MODEL_REVISION` / `ENGRAM_ID` / `ENGRAM_REVISION` / `SERVED_NAME` を確かめる。

1. **レシピを用意する** — `git clone https://github.com/MiaAI-Lab/DeepSeek-v4.1-Flash-1017-2x-DGX-Sparks ~/DeepSeek-v4.1-Flash-1017-2x-DGX-Sparks` のあと、`scripts/local.sh` に `WORKER=skanehira@<worker の RoCE アドレス>` を書く。**完了判定**: `bash -c 'source scripts/config.sh >/dev/null 2>&1; echo "$MODEL_ID@$MODEL_REVISION $ENGRAM_ID@$ENGRAM_REVISION $IMAGE"'` が pin を出す
2. **pin した revision が HF に残っているかを見る** — `curl -s -o /dev/null -w '%{http_code}\n' https://huggingface.co/api/models/<MODEL_ID>/revision/<MODEL_REVISION>` が 200 なら次へ。404 なら落とし穴 1 のとおり revision を選び、`scripts/local.sh` に `MODEL_REVISION=<revision>` を足す。Engram も同じ形で見る

## 導入の落とし穴

1. **pin した revision が HF から消えることがある。** 本体のリポジトリが 2026-10-19 に履歴を squash し、当時の pin `6d54be4f` は 404 になった (2026-10-21 確認)。素直に流すと `Invalid rev id` で取得が失敗する。上流は後に `7803045` で既定を `45ee5d0f` に直した。当方はそれより前に、squash 後の `e91d9b19` と `45ee5d0f` で safetensors 39 本の sha256 が一致し、差分がモデルカードとグラフだけであることを HF API で確かめて `45ee5d0f` を採った (index.json の sha256 も旧 pin と同じ)。旧 pin の shard ごとの sha256 は記録しておらず、shard 単位の一致は未確認である
2. **`prepare.sh` は取得の前にイメージを作る。** 公開イメージが無いとベースイメージの pull と Zig のビルドが dockerd で走り、メモリの上限が掛からない (dockerd を通る操作の扱いは `dgx-spark.md`「既知の制約」のメモリの余裕の項)。配信中の head では流さない。重みだけ先に取るなら導入手順 3 の形で取る
3. **worker もベースイメージを WiFi で取る。** `prepare.sh` は NFS の照合に `docker run <BASE_IMAGE>` を使うので、worker に無ければ dockerd が 10.52 GiB を pull する (ソースから読んだ経路で、pull そのものは観測していない。2026-10-22 の導入後は worker にもあった)。節約するなら導入手順 6 の前に head から `docker save nvcr.io/nvidia/pytorch:26.07-py3 | ssh <worker> docker load` で送る (この形は未実行)
4. **`snapshot_download` を止めて再開すると、取得途中のファイルは最初から取り直される。** 古い `.incomplete` は残る (2026-10-21 の中断で 2 本、7.4 GiB)。消してよい条件は「残骸の片付け (1017 系)」
5. **Engram の shard は curl で取った。** huggingface_hub は xet 以外で大きいファイルを取らないためで、V4.1 EXL3 系で踏んだ (`dgx-spark/v41-exl3.md`「導入の落とし穴」)。1017 の shard で huggingface_hub は試していない。HF の resolve URL は Range 要求に 206 を返し、2026-10-22 に 3 回切れた接続 (curl のエラー 92) も `curl -C -` が続きから取り直した
6. **`hf` が非ログインシェルの PATH に無い。** GLM 系と同じで、`prepare.sh` は `hf` が無いと止まる。必ず `bash -lc` を通す

## レシピを更新する

```bash
ssh spark-head
cd ~/DeepSeek-v4.1-Flash-1017-2x-DGX-Sparks
git fetch -q && git log --oneline HEAD..origin/main   # 先行分を読む
git diff HEAD..origin/main -- CHANGELOG.md scripts/config.sh zig/   # pin・パッチ・Dockerfile が動くかを見る
git pull --ff-only
```

- **`scripts/local.sh` の `MODEL_REVISION` は `scripts/config.sh` の既定より勝つ。** 既定の pin が HF から消えたときだけ書き、上流が直したら消す
- **`zig/patches/`・`zig/Dockerfile`・`TF_REF` / `INPUTS_REF` が動くとイメージのハッシュが変わり、次の起動でビルドが走る。** ベースイメージは両ノードにあるので取り直しは起きない (2026-10-30 の更新で pull は無かった。`BASE_IMAGE` が動けば取り直す)。ビルドは配信を止めてから行う。`git pull` の後に `PULL=0 DRY_RUN=1 bash -lc ./start.sh` を打つと、何も止めずに `prepare.sh would run now` が出るかと新しいタグを見られる
- **公開イメージは使わず `PULL=0` で起動する。** 既定の `PULL=1` は `ghcr.io/miaai-lab/...:exl3-tp2-<ハッシュ>` の pull を試し、無ければビルドに回る。公開タグは手元の pin のハッシュと一致しないことがあり (2026-10-30 は公開 `7c9bf5d36350` / 手元 `7d71dcdf7f2f`)、一致しても 25 GB を WiFi で取ることになる
- **prepared marker の書式が変わる更新では `prepare.sh` が流れ直す。** 重みファイルが揃っていれば作り直さない
- **古いイメージは両ノードに残る。** 戻す材料なので自動では消さない (→「残骸の片付け (1017 系)」)
- **更新後の悪化確認**は「起動と判定」の 3 段と effort の対照で行う

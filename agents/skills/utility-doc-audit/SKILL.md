# /utility-doc-audit

ドキュメントを書き手と**別コンテキスト**の複数観点で監査し、指摘レポートを返す。書き手自身は「定義したつもり」バイアスで未定義用語・断絶した参照を検出できない。fresh context のサブエージェントに検査させることが本スキルの存在理由。

**修正はしない。指摘レポートのみ。**修正するかどうか・どう直すかは呼び出し元の判断。

レポートは、今回の変更から出た指摘を中心にし、件数を絞って返す。監査を繰り返しても終わるように、次の 4 つを守る。

| 守ること | 節 |
| --- | --- |
| 今回の変更から出た指摘と、既存の問題を分ける | 「変更箇所の取得」「集約とレポート」 |
| 今後も直さないと決めた指摘を、その節がある限り挙げ直さない | 「判断の記録」 |
| major を 4 つの条件に限り、minor と suggestion の件数を絞る | 「出力形式」「集約とレポート」 |
| 修正案は、文を足すより削る形を先に考える | 「出力形式」 |

## 起動経路

- ユーザーが `/utility-doc-audit <path>` を実行したとき
- `/workflow-design-notes` の落とし込みフェーズ (step 5) から起動されたとき

この 2 つ以外では起動しない。とくにドキュメントを編集した直後や「監査して」と依頼された場合は、自分で起動せず `~/.claude/skills/workflow-doc-write/SKILL.md`「8. 監査の要否を判定する」の依頼 1 行を出してユーザーに委ねる。

## 入力

1. 引数で対象ファイルパスを受け取る（複数可）。任意で観点の絞り込み（例: 「用語閉包だけ」）を受け付ける
2. 任意で**変更文脈**（何をどう修正したかの概要・修正意図）を受け付ける。呼び出し元（会話・他スキル）が渡す。下記「監査モードのトリアージ」で使う
3. 対象文書の冒頭メタ情報から**種別宣言**（例: `- 種別: 設計書`）と**読み手**（例: `- 対象読者: このリポジトリで作業するエージェント`）を読む
   - 種別の宣言が無ければ内容から種別を推定して監査観点の冒頭で宣言し、**「種別明記なし」を minor の指摘としてレポートに含める**
   - 読み手の宣言が無ければ、内容から推定した読み手をレポートの冒頭で宣言する。観点 3 はこの読み手で判定する
4. 任意で**決定台帳**（議論の決定・棄却・保留を記録したファイル。/workflow-design-notes が運用する `docs/DESIGN_NOTES.md` 等）を受け取る。渡された場合のみ観点 6 を起動する
5. 任意で `全件` を受け付ける。渡されたら、「集約とレポート」4. と 5. の件数の絞り込みをせず、suggestion も出させる
6. 任意で `基準 <コミット>` を受け付ける。「変更箇所の取得」の比較元になる

## 機械ゲートの直接実行（種別 = 設計書のとき）

サブエージェント起動の**前に親が直接**、`doc-formats/design-doc.md` の「機械ゲート」節の判定コマンド（表の全行）を実行し、違反をレポートの「機械ゲート」節に載せる。決定的なコマンドの判定を LLM に委ねない。この機械ゲートは監査モードに関わらず常時実行する（安価かつ決定的なため絞らない）。違反は「出力形式」の severity の基準とは別に扱い、件数を絞らず、`今回` / `既存` も付けない。コマンドが合否を決めるので、直せば必ず消え、監査を繰り返しても増えないためである。

## 変更箇所の取得

親は、監査モードに関わらず、サブエージェントを起動する前に対象文書の変更箇所を git diff で取得する。変更箇所は、各指摘が今回の変更から出たものか (`今回`) を分けるために使う。書き手が編纂した抜粋ではなく git diff（客観情報）を正にし、fresh context 監査としての独立性を保つ。変更文脈の引数は、変更の意図を補うためと、トリアージで変更の性質を決めるためにだけ使う。

比較元は次の順で決める。

1. `基準 <コミット>` が渡されたら、そのコミットと作業ツリーの差分を使う
2. 対象ファイルに未コミットの変更 (unstaged + staged) があれば、HEAD との差分を使う
3. 未コミットの変更が無ければ、対象ファイルに触れた最新のコミット (`git log -1 --format=%H -- <file>`) の差分を使う
4. git 管理されていない新規文書は、全体を変更箇所とする
5. どれでも差分が取れないときは、全指摘を `既存` とする

使った比較元は、レポートの冒頭に `基準: <コミット> (<上の番号>)` と書く。指摘を直したあとにもう一度監査するときは、直す前の状態をコミットしてから、そのコミットを `基準` に渡す。そうすると直した部分だけが `今回` になり、前回の監査で省いた指摘は `既存` に回る。

## 判断の記録

監査の指摘のうち、呼び出し元が「直さない」と決めたものを、対象のリポジトリの `docs/AUDIT_DECISIONS.md` に記録する。次の監査はこの記録を読み、同じ指摘を挙げ直さない。

決定: 今後も直さないと決めた指摘だけを、節名つきで記録する。後で直すつもりの指摘は記録しない (次の監査でも出てよい)。
理由: 監査は毎回、前回の判断を知らない別コンテキストで動く。記録が無いと、意図して書かない点や受け入れたリスクが毎回指摘として戻ってくる。
採らなかった案: 直した指摘も記録する (直したかは文書の現物で分かり、記録が増えるだけになる)。根拠の文をそのまま引用して照合する (節の書き直しや推敲で字面が変わるたびに記録が切れる)。

- **書く人**: 呼び出し元 (監査を起動したセッション)。本スキルは修正もしないので、記録も書かない。レポートの末尾で記録を促す。`/workflow-design-notes` から起動したときは、設計の決定に当たる判断は決定台帳に書き、それ以外をこの記録に書く (同スキルの落とし込みフェーズ 6.)
- **形式**: 1 件 1 行の表にする

  ```markdown
  # 直さないと決めた監査の指摘

  - 種別: 記録

  | 対象文書 | 節 | 指摘の一文 | 直さない理由 | 記録した日 |
  | --- | --- | --- | --- | --- |
  | `docs/design/DESIGN.md` | 月末締めと給与データ | 締め日を変えたいときの手順が無い | 締め日は契約で固定され、変える運用が無い | 2026-11-27 |
  ```

- **読み方**: 親は、記録のうち対象文書の行だけを各サブエージェントに渡す。サブエージェントは、記録の節がいまもあり、指摘の一文と同じ問題を指すものを挙げない。記録の節が無くなっていたら、その行は効かない。親はレポートの末尾に、効かなくなった行を挙げる

## 監査モードのトリアージ（サブエージェント起動の前段）

観点別サブエージェントを全起動する「フル監査」と、変更に関係する観点だけに絞る「スコープ監査」を、文脈の有無で切り替える。局所修正の後に文脈を無視して文書全体の観点を起動すると、変更と無関係な指摘までノイズとして返ってしまうため。

1. **文脈の解決順**
   1. 観点の絞り込み引数（例: 「用語閉包だけ」）があればそれを最優先で使う
   2. なければ、「変更箇所の取得」で得た変更箇所から変更の性質を決める
   3. 差分が取れない（新規文書・削除されたファイル・「全体を監査して」等）場合は**フル監査**（観点 1〜5 を常時起動）
2. **フル監査への格上げ条件**: 文脈が得られていても、変更が**概念の追加・削除・置換・節構成の変更**を含む場合はフル監査にする。`~/.claude/guidelines/core/documentation.md` の「全体整合 > 差分最小」と矛盾させないためである。台帳からの全文再生成（/workflow-design-notes 経由）も同様にフル監査を使う
3. **スコープ監査時の観点トリアージ表**（変更の性質から起動する観点を選ぶ）

   | 変更の性質 | 起動観点 |
   |---|---|
   | 固有名（コマンド・用語・ファイル・節参照）の追加・リネーム | 1 用語・参照閉包 |
   | データ・処理フローの記述変更 | 2 データフロー端到端 |
   | 手順・セットアップ・運用記述の変更 | 3 運用・実装者視点 |
   | 環境事実への言及（設定ファイル・CI・コマンド）の変更 | 4 依拠事実の突合 |
   | メタ情報・節構成・表構造の変更 | 5 フォーマット適合 |
   | 字句修正のみ（typo・表記揺れ） | 観点なし。「監査対象観点なし」とレポートして終了 |

   複数の性質にまたがる変更は該当する観点をすべて起動する。決定台帳が渡されている場合、観点 6（決定カバレッジ）はモードに関わらず常時起動する。

4. トリアージ結果を**レポート冒頭に 1 行宣言**する（例: `モード: スコープ監査 / 起動観点: 1,4 / 根拠: 新コマンド追加 + 設定パス変更`）。誤判定にユーザが気付ける状態にする

## 観点別サブエージェントの並列起動

観点ごとにサブエージェントを `model: opus` 明示で**同一ターンで並列起動**する（文書監査は検証器なので実行器より下げない。`~/.claude/guidelines/core/orchestration.md` の検証器・調査 fan-out の割当に従う）。各エージェントの指示文には次を含める。

- 対象ファイルパスと、下記の観点定義・キャリブレーション例・出力形式
- 変更箇所 (「変更箇所の取得」で得た git diff の該当 hunk)。「文書は全文 Read して検査する（読む範囲は狭めない）。各指摘に `今回` か `既存` を付ける」と指示し、次の定義を添える。`今回` は、今回の変更が原因で生じた問題である。指摘の場所が変更していない行でも含む (例: 用語を改名した結果、変更していない別の節に旧い名前が残った)。`既存` は、変更の前から同じ形であった問題である
- `docs/AUDIT_DECISIONS.md` の、対象文書の行 (あれば)。「判断の記録」の読み方を添える
- 文書の読み手 (「入力」3.)
- 「作業結果は必ず親 (呼び出し元) に返すこと」

### 観点（1〜5 は常時、6 は決定台帳が渡されたときのみ。実際に起動するかはモードのトリアージに従う）

1. **用語・参照閉包**: すべての固有名（コマンド・環境変数・ファイル・ラベル・フィールド・節参照）が定義され、定義と参照が一致し、表記揺れがないか
2. **データフロー端到端**: 生成されるが消費されないデータ / 消費されるが生成元がないデータ / 記載データだけでは計算不能な指標・KPI / 経路の断絶
3. **運用・実装者視点**: 文書の読み手 (「入力」3.) が、書かれた作業をするときに最初に詰まる問い（セットアップ・権限・障害時・ライフサイクル・Done 条件の判定可能性）に文書が答えているか。読み手がしない作業について問いを立てない
4. **依拠事実の突合**: 文書の「依拠する外部事実」節を実環境と rg で照合する。節が無ければその指摘 + 文書中の環境言及（設定ファイルの有無・コマンド・CI 等）を直接検証する
5. **フォーマット適合**: 種別に対応する `~/.claude/guidelines/core/references/doc-formats/<型>.md` を Read して突合する。型別の規範が書く違反の重さは参考にとどめ、severity は「出力形式」の基準で付ける (構造違反は major か minor、可読性違反は suggestion)。規範未定義の型は `~/.claude/guidelines/core/documentation.md` の汎用原則のみでチェックし「規範未定義」と報告する
6. **決定カバレッジ**（決定台帳が渡されたときのみ）: 台帳の全「決定」が文書に反映されているか / 「棄却」した案が文書に生き残っていないか / 文書にあって台帳にない決定（無断発明）がないか。台帳→文書の再生成は lossy になりうるため、この観点が生成の安全網になる

### 各エージェントに含めるキャリブレーション例（探すべき問題の実例）

- 未定義コマンドの参照（本文が使う `xxx-sync` コマンドがどこにも定義・導入されていない）
- 存在理由が消えた設定値（競合を避けるために入れた値が、競合の起きない設計になっても残り、「負荷分散のため」と弱い理由が後付けされている）
- write-only なデータ（収集すると書かれているが、どの処理も参照しないログ・メトリクス）
- 「後述」「別途定義」のまま宙に浮いた参照（後述先が存在しない）

### 出力形式（各エージェントに指定）

```
[severity] [今回|既存] 該当箇所 (節名 or 行) / 問題の一文 / 修正案の一文
```

severity は次の基準で付ける。

| severity | 条件 |
| --- | --- |
| `major` | 次の 4 つのどれかに当たるものだけ。参照先が無い / 文書どうしか同じ文書の中で記述が食い違う / 書いてある手順やコマンドをそのとおりに実行すると失敗する / 依拠する事実が実環境と違う |
| `minor` | major に当たらないが、読み手が書かれた作業をするときに説明が足りず判断に迷うもの。表記揺れ |
| `suggestion` | 可読性。`全件` を渡されたときだけ出す |

修正案は次の順で考え、最初に成り立つものを書く。文を足す案には、足さないと読み手がどこで止まるかを添える。

1. 文を削る
2. 事実として確かめられない言い切りだけを弱める (確かめられる言い切りは弱めない。読み手が判断に迷う文を増やすため)
3. 正本の節を参照する形にする
4. 文を足す

理由: 文を足す直し方を既定にすると、足した文が次の監査で新しい検査の対象になり、指摘が尽きない。

## 集約とレポート

1. 冒頭に監査モードの宣言行と、比較元の行 (`基準: ...`) を置く。読み手を推定したときは、その宣言も置く。続けて「機械ゲート」節に、機械ゲートの違反を全件載せる (違反が無ければ「違反なし」)
2. 各エージェントの指摘を親が検証する（明らかな誤読・文書外の要求は落とす）。major は「出力形式」の 4 つの条件のどれに当たるかを確かめ、当たらなければ minor に下げる。`docs/AUDIT_DECISIONS.md` の行と同じ問題を指す指摘で、記録の節がいまもあるものは落とす
3. 観点間で重複する指摘を統合する
4. `今回` の指摘を severity 順（major → minor → suggestion）に並べる。件数は次のように絞る (`全件` を渡されたときは絞らない)

   | severity | 載せる件数 |
   | --- | --- |
   | major | 全件 |
   | minor | 読み手への影響が大きい順に 10 件まで |
   | suggestion | 載せない |

   載せなかった件数は、`省略: minor 4 件 / suggestion 7 件 (全件を見るなら /utility-doc-audit <path> 全件)` の形で 1 行書く
5. 末尾に「既存の問題」節を置く。`既存` の指摘を severity を付けずに 1 行/件で簡潔に列挙する。major の条件に当たるものだけを載せ、ほかは件数だけを書く (`全件` を渡されたときは全件を載せる)。拾って直すかは呼び出し元の判断
6. さらに末尾に「検査した固有名・観点の要約」を 1 行添える（例: `検査: 固有名 12 件 / 2 観点 (スコープ監査) / 種別=設計書 (宣言あり)`）。`docs/AUDIT_DECISIONS.md` の行で、節が無くなって効かなくなったものがあれば、ここに挙げる
7. 最後に、今後も直さないと決めた指摘を `docs/AUDIT_DECISIONS.md` に記録するよう、呼び出し元に 1 行で促す (形式は「判断の記録」)

## 境界（対象外）

- **文体（AI っぽさ・語調・推敲）は対象外**。別レイヤの関心事であり、プロジェクト側に文体スキルがある場合はそちらを使う
- **スキル・テンプレートが生成した文書**は、テンプレート準拠をもってフォーマット適合とみなす（規範の主対象はスキルを使わず手書きされる文書）
- **修正はしない**。指摘レポートのみ

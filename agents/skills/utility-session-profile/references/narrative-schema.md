# `narrative.json` の書き方

レポートの散文をすべてこのファイルに書く。図表は `data.json` / `ext.json` から描かれるので、
ここに数値を書き写す必要はない。**書くのは解釈**で、数値は主張を支える根拠として引く。
図に使えるキーの一覧は [output-schema.md](output-schema.md)。

`render.py` はこのファイルの `sections` を見て節を描く。**キーを書かなければその節は出ない。**
取れなかった層の節を落とすのは、この仕組みで行う。

材料が無いのにキーを書いた場合は、見出しだけの節が出ないよう `render.py` が止める。止まるのは
`critical` (`ext.critical` が空)・`review` (`ext.rounds` が空)・`timeline` (issue もエージェントも
無い)・`incidents` (`incidents` が空)・`optimize` (`fixes` が空) の 5 つで、メッセージが
どのキーのどの材料が空かを言う。

## 最小の例

```json
{
  "title": "dev-impl 実装ループの解剖",
  "subtitle": "セッション 82fc5ce1 のプロファイル",
  "running": true,
  "snapshot_label": "2026-09-09 09:30 JST",
  "sections": {
    "verdict": {"heading": "結論", "lead": "遅さの原因は 3 つある。"},
    "timeline": {"heading": "時間はこう流れた", "lead": "同じ形が繰り返される。"}
  },
  "verdicts": [
    {"label": "A", "text": "依存が <em>10 段</em>あり並列枠を使い切れない。",
     "figure": "1.5", "figure_note": "平均の同時実行数<br>(枠は 3)"}
  ],
  "limits": "フェーズは Agent 呼び出しの契約キーと subagent の span から復元した。"
}
```

## トップレベルのキー

| キー | 必須 | 内容 |
| --- | --- | --- |
| `title` | ○ | ページ名。短い名詞句 (2〜4 語)。ブラウザのタブと見出しになる |
| `subtitle` | | 見出しの下の一行。対象セッションと主題を示す |
| `running` | | `true` なら「実行中に採取」の印を出す。進行中のセッションを見たとき |
| `snapshot_label` | | 採取時刻の表示 (例 `"2026-09-09 09:30 JST"`)。省略すると UTC が出る |
| `sections` | ○ | 描く節とその文言。下表のキーだけ使える |
| `verdicts` | | 結論。3 点前後 |
| `tiles` | | 統計タイルを自分で決めたいとき。省略すると経過・エージェント数・ターン数などが自動で並ぶ。要素の形は下の `tiles[]` |
| `incidents` | | 取りこぼしと事故の一覧 |
| `fixes` | | 最適化案 |
| `limits` | | フッタに出る「計測の限界」。欠測や推定の断りを書く |

## `sections` に置けるキー

順番はここに書いた順に固定される (節番号も自動)。

| キー | 節の内容 | 要る層 |
| --- | --- | --- |
| `verdict` | 結論と統計タイル | A1 |
| `timeline` | ガントと同時実行数の推移 | A2 または B (バーはエージェント単位か issue 単位) |
| `critical` | issue 依存段のクリティカルパス | B + `gh` |
| `breakdown` | フェーズ別合計 / エージェント種別ごとの時間 | A1 |
| `review` | レビューのラウンド表と、後半で出た high | B |
| `cost` | コマンド種別ごとの実行回数と最長コマンド | A1 |
| `incidents` | 事故の一覧 | — (`incidents` の内容による) |
| `optimize` | 最適化案 | — (`fixes` の内容による) |

各節が受けるキー:

| キー | 使える節 | 内容 |
| --- | --- | --- |
| `heading` | すべて | 見出し。省略すると既定の文言 |
| `lead` | すべて | 見出し直下のリード文。1〜2 文 |
| `caption` | すべて | 節の末尾に小さく出る補足。図の読み方や、そこから言えること |
| `note` | `critical` / `review` / `cost` | 縦線つきの囲み。強調したい 1 点 |
| `fig_title` / `fig_note` | `timeline` / `breakdown` | 図の見出しと注記 |
| `late_note` | `review` | 後半ラウンドの high 一覧に付ける注記 |

## 配列のキー

### `verdicts[]`

```json
{"label": "A", "text": "レビューと修正で <em>時間の 6 割</em>を使っている。",
 "figure": "376", "figure_note": "分 / 全 620 分"}
```

`label` は A / B / C の識別子。`text` が主張、`figure` がそれを支える 1 つの数値。
**主張と数値が対になっていないものは verdict にしない** (それは `caption` に書く)。

### `tiles[]`

```json
{"k": "経過", "v": "7.3", "u": "時間", "d": "02:06 開始"}
```

`k` は見出し (小さい大文字)、`v` は数値、`u` は単位、`d` は数値の下に出る補足。
**`d` だけ HTML が展開される** ので、`<` を書くならタグとして解釈される。

### `incidents[]`

```json
{"when": "07:30", "what": "<b>merge 失敗を見落として完了処理を先に実行した。</b> rebase して復旧。",
 "cost": "約 10 分"}
```

`when` は時刻か時間帯。`what` の先頭を `<b>` で括ると要点が立つ。`cost` は失った時間。
測れないものは `"—"` にする。**推測で損失時間を書かない。**

### `fixes[]`

```json
{"rank": "効き目 1", "title": "issue の依存を浅く割る",
 "body": "段数がそのまま所要時間を決めるため、段を半分にすれば所要時間も半減する。",
 "where": "{{@skills-root}}/dev-spec/ の issue 分割方針",
 "gain": "段数に比例", "gain_note": "10 段 → 5 段でおよそ半減"}
```

効き目の大きい順に並べる。`where` は**変更対象のファイルやスキル**で、これが無いと
読み手は動けない。`gain` は短縮の見込みで、根拠のある数字か「段数に比例」のような
定性表現。`gain_note` に根拠を 1 行。

## 使える HTML

`text` / `body` / `note` / `caption` / `lead` / `what` / `figure_note` / `gain_note` /
`fig_note` / `late_note` / `tiles[].d` / `limits` では次だけ使う。

- `<em>` … 主張の中の要点。アクセント色になる
- `<b>` … 太字
- `<code>` … ファイル名・コマンド・識別子
- `<br>` … 改行

それ以外のタグは書かない (エスケープされないため、レイアウトが壊れる)。
`heading` / `title` / `subtitle` / `label` / `figure` / `where` / `rank` / `gain` は
プレーンテキストとして扱われる。

## 書くときの指針

- **数値を並べない。** 図表が数値を持っているので、散文は「その数値が何を意味するか」を書く
- **セッション固有の事情を書く。** モデル構成、途中の方針変更、環境の癖。これらはログにしか
  残らず、図表には出ない
- **推定と実測を区別する。** 「打刻が無いので merge 待ちは測れていない」のような断りは `limits` に書く
- **`fixes` は実行できる形にする。** 「レビューを減らす」ではなく「どのファイルの何を変えると
  どれだけ縮むか」

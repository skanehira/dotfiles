## 状態の管理

ラベルで状態を管理し、Project で人が状況を把握する。人の作業は設計の確認だけで、整理、設計、実装、merge は AI が進める。Deploy は人が実行する。

| 状態 | ラベル | Status | 次に動く人 | 次へ進む条件 |
| --- | --- | --- | --- | --- |
| 未整理 | なし | 未整理 | AI | 採点し、設計が要るかを判定した |
| 設計待ち | `needs-design` | 設計待ち | AI | 設計 PR か修正方針を出した |
| 設計レビュー | `design-review` | 設計レビュー | 人 | 承認した |
| 着手可能 | `ready` | 着手可能 | AI | `/dev-impl` が着手した |
| 作業中 | `in-progress` | 作業中 | AI | PR を merge した |
| 判断待ち | `needs-human` | 判断待ち | 人 | 回答を issue に反映した |

- `ready` は人が仕様を承認した印で、`/dev-impl` の入力である。AI は自分で付けない
- 設計 PR は本文に `Design-for: #<issue 番号>` の行を書く。人が merge すると、GitHub Actions (`.github/workflows/design-approved.yml`) が対象の issue に `ready` を付ける
- 設計書の変更が要らない issue は、AI が修正方針を issue のコメントに書いて `design-review` を付ける。人が確認して `ready` を付ける
- 実装の PR は人が確認せず、AI が merge する。merge で issue は close され、Status は「完了」になる
- ラベルが変わると、GitHub Actions (`.github/workflows/issue-state-sync.yml`) が Project の Status を動かす。Status を手で動かさない
- 親 issue は `tracking` を付ける。Status は「作業中」になり、子の進捗に任せる
- 種別はラベルで見る: `bug` / `enhancement` / `refactoring` / `question`

## 着手可能の基準

issue が次をすべて満たすとき、人は `ready` を付けてよい。

1. **実装の単位**である。親・質問・人手による検証だけのものは対象外。1 issue = 独立して検証できる 1 作業単位にする。
2. **設計が確定**している。参照する設計書に、未決の「決めること」が残っていない。
3. 本文が**自己完結**している。ゴール・設計・DoD・非スコープ・依存 の 5 節が揃っている。
4. **DoD が実行可能で空虚でない**。具体的なコマンドと期待結果がある。
5. **依存の順序が決まっている**。`Depends on` の先は open でもよい。依存グラフに循環がない。
6. **人間・外部の判断を要さない**。要るものは `needs-human` にする。

## 判定の手順

1. 親なら `tracking` を付ける。
2. 開発の issue は「優先度」の定義で採点し、本文の `## 優先度` に点数と根拠を書く。
3. 人間・外部の判断が要るなら `needs-human` を付ける。
4. 決めることが残っていれば `needs-design` を付ける。
5. 設計 PR か修正方針を出したら `design-review` を付ける。人の承認で `ready` になる。

## 優先度

バグ、機能開発、開発基盤を同じ物差しで比べる。スコアは判断の材料で、最後は人が決める。

### 判定の流れ

1. **緊急枠**: 本番で <!-- 記入: このプロジェクトで「業務停止」に当たるもの、データの誤り、情報漏えい --> が発生しているものは、採点せずに着手する。本番前の仮実装は緊急枠に入れない。
2. **採点**: それ以外の issue を次の 11 観点で採点する。
3. **順位**: スコアの順に並べる。スコアの差が 2 割以内なら同順位として、人が決める。依存先は、依存元の高いほうのスコアを引き継ぐ。
4. **上書き**: スコアと違う順にするときは、理由を issue に 1 行残す。

親と子に分けた issue は親の単位で採点し、子は親のスコアを引き継ぐ。`/dev-spec` が作る issue は依存順に実装するので採点しない。

**スコア = (影響 + 必須度 + 価値 + 運用 + 開発 + リスク + 期日 + 後続) × 広さ ÷ 人の手間 × 確度**

小数 1 桁に四捨五入する。

### 採点の決まり

- 迷ったら低いほうを付ける。分母の人の手間だけ、迷ったら高いほうを付ける
- 質問や確認の issue は、回答によって変わる業務と作業の大きさで採点する
- issue の本文が今の実装より古いときは、現物で採点する
- 点数は、効果を測ったときと期日が変わったときに直す。全件の定期的な見直しはしない

### 業務への影響 (影響)

本番で使う時点で、これが無い、または決まっていないと、どれだけ困るか。代替策を踏まえて判定する。

| 点 | 定義 |
| --- | --- |
| 0 | 困らない |
| 1 | 簡単な代替策がある |
| 2 | 代替策はあるが手間が大きい、または手作業が定常的に増える |
| 3 | 代替策がない。または中核の業務の決まりが確定していない (<!-- 記入: このプロジェクトの中核の業務の例 -->) |

### 要件の必須度 (必須度)

機能要件として、実装しないと要件を満たせないか。<!-- 記入: 要件の正本 (例: 要件の表のパス) --> と、顧客との確定事項で判定する。

| 点 | 定義 |
| --- | --- |
| 0 | 要件ではない。開発用の改善と社内の整備はここに入れる |
| 1 | 社内のビジネス側の要望、または顧客の任意の要望 |
| 2 | 顧客と合意した要望だが、実装しなくても要件は満たせる |
| 3 | 必須の機能要件で、実装しないと要件を満たせない |

### 利用者への価値 (価値)

使う人にとっての得だけを見る。要件かどうかは見ない。

| 点 | 定義 |
| --- | --- |
| 0 | 利用者に見える変化がない |
| 1 | あると便利 |
| 2 | 特定の業務が明らかに楽になる |
| 3 | 主要な流れが使えない状態を解消する、または中心となる機能 |

### 運用の負荷の削減 (運用)

<!-- 記入: 運用する人 (例: 社内の運用担当、顧客の管理者) --> の定型作業がどれだけ減るか。

| 点 | 定義 |
| --- | --- |
| 0 | 減らない |
| 1 | たまの作業が少し減る |
| 2 | 定期的な作業が明らかに減る |
| 3 | 毎月の手作業がなくなる、または問い合わせや手続きの負荷が大きく減る |

### 開発への効果 (開発)

開発の速度と費用への効果。未測定なら見込みの点を付け、不確かさは確度で受ける。

| 点 | 定義 |
| --- | --- |
| 0 | 効果なし |
| 1 | たまに行う作業が楽になる |
| 2 | 1 回の実行時間か費用が 2 割以上減る |
| 3 | 開発全体の待ち時間が半分以下になる |

### リスクの低減 (リスク)

| 点 | 定義 |
| --- | --- |
| 0 | 防ぐ被害がない |
| 1 | 被害が小さく、手作業で直せる |
| 2 | 一部のデータに影響し、復旧に手間がかかる。または重い被害の可能性だけがある |
| 3 | 情報漏えい、法令違反、重要なデータの破損について、被害の経路が確認できている |

### 期日

確定した期限までの長さ。失効した条件は数えない。

| 点 | 定義 |
| --- | --- |
| 0 | 期日がない |
| 1 | 目安の期日がある、または 1 か月より先 |
| 2 | 2 週間より先で 1 か月以内 |
| 3 | 2 週間以内に確定した期日がある |

### 後続への影響 (後続)

| 点 | 定義 |
| --- | --- |
| 0 | 影響なし |
| 1 | 後回しだと手戻りが少し増える、または 1 件の作業を可能にする |
| 2 | 複数の issue を塞いでいる、または手戻りが大きい |
| 3 | 機能全体を塞いでいる、または後からやり直せない |

### 広さ

効果が出る範囲と頻度。作業の機会ではなく、そのたびに効果が出るかを見る。

| 点 | 定義 |
| --- | --- |
| 1 | 限られた人が月に数回以下、または特定の条件のときだけ効く |
| 2 | 1 つのロール全体が月に 1 回以上、または 1 つの顧客の全利用者に効く |
| 3 | 全利用者が毎日関わる、または開発のたびに効果が出る |

<!-- 記入: 「全利用者」の範囲 (例: 複数の顧客をまたぐ全スタッフ) -->

### 人の手間

実装以外に人がやる作業。AI の実装時間と、回答を待つ時間は数えない。社外の相手との確認や承認は、issue の本体でも数える。

| 値 | 定義 |
| --- | --- |
| 1.0 | レビューだけ、または社内で 1 回決めれば済む |
| 1.5 | 判断、移行、周知のどれかが要る。または社外の 1 者への確認で済む |
| 2.0 | 複数の社外の相手との調整を重ねる、または本番の移行手順が要る |

### 確度

| 値 | 定義 |
| --- | --- |
| 1.0 | 再現した、測った、顧客か社内が明確に求めている |
| 0.8 | 根拠が一部ある |
| 0.5 | 推測で、測っていない |

### issue への書き方

スコアの正本は issue 本文の `## 優先度` である。スコアと、0 より大きい観点の点数と根拠を書く。

```markdown
## 優先度
スコア 3.0 (2026-11-05 採点)
- 開発 2: テストは開発のたびに流れる。効果は未測定
- 広さ 3: 開発のたびに効果が出る
- 人の手間 1.0: レビューだけで済む
- 確度 0.5: 短縮を測っていない
```

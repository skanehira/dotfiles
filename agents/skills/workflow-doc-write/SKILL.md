# workflow-doc-write

文書ファイルを書く・直すときに、この順で進める。何を書き、何を書かないかの規範は `~/.claude/guidelines/core/documentation.md` にあり、この手順はその規範を守るための作業を並べたものである。

## 1. 読み手と型を決める

1. 誰が何のために読むかを 1 行で決める (例: 「この機能を実装するフロントのメンバーが、API の呼び方を知るために読む」)
2. 文書の種別を決め、冒頭メタ情報に書く (例: `- 種別: 設計書`)
3. `~/.claude/guidelines/core/references/doc-formats/<型>.md` があれば Read する

## 2. 改訂なら、全文を読んで変更の性質を決める

既存の文書を直すときは、該当の節だけでなく全文を読む。そのうえで変更の性質を次のどれかに決める。

| 変更の性質 | 書き方 |
| --- | --- |
| 字句修正 (typo・表記揺れ) | 局所の Edit でよい。手順 4 の推敲と手順 8 の監査依頼は要らない |
| 事実や決定の追加・削除・置換 | その事実を扱う節を、最新の結論で書き直す。節の末尾に書き足さない。同じ事実がほかの節にもあれば 1 か所にまとめ、ほかからは節名で参照する |
| 節構成の変更 | 全文を書き直す |

## 3. 結論と理由の形で下書きする

- 各節を結論の 1 文で始め、理由と詳細をその後に置く
- 決定は `決定: / 理由: / 採らなかった案:` の形で書く (形は `documentation.md`「書くもの」)
- 会話や作業の中で出てきた過程は、`documentation.md`「書かないもの」の表の置き場所へ振り分け、本文には入れない。とくに次の 2 つは本文に書かない
  - 確認した日付 (例: 「2026-10-03 のこのマシンでは〜だった」) と、確かめていない範囲 (例: 「Linux では確かめていない」)。これらは「依拠する外部事実」の表に置くか、完了報告に書く
  - 旧方式や旧仕様の説明。旧状態のまま残っている環境の移行手順だけは、手順として書いてよい

## 4. yomiyasu で推敲する

日本語の文書は、下書きを yomiyasu で推敲してから書き出す。コードコメント・コミットメッセージ・会話の返答は対象にしない。

- **起動**: Skill ツールで `yomiyasu` を起動し、下書きを渡す。ドメインは、設計書・README・手順書・skill や guidelines の本文なら `tech` にし、報告書や業務の仕様書なら `business` にする。Skill ツールを持たない subagent は、`~/.claude/skills/yomiyasu/SKILL.md` を Read して同じ手順で推敲する
- **推敲するのは文章だけ**: 見出しの構成・表・コードブロック・コマンド・パス・引用したエラー文・frontmatter は変えない。yomiyasu の手順には、箇条書きを地の文にまとめる処理がある。テンプレートや型別の構造規範が箇条書きや表を求める箇所では、この処理を当てはめず、形を残したまま文だけを直す。和欧文の間の半角空白などの表記は、その文書の慣例に合わせる (このハーネスの文書は空白を入れる)
- **改訂のとき**: 推敲するのは、書き足す文と書き直す文だけにする
- **「書き手に確かめたい点」が返ったとき**: その点は本文に推測で補わない。完了報告に載せてユーザーに確かめる

## 5. 書き出す

推敲した文章を Write / Edit で書き出す。

## 6. 検査して直す

```bash
# 新しく書いた文書: 全行を検査する
python3 ~/.claude/skills/workflow-doc-write/scripts/doc_check.py <ファイル>...
# 既存の文書の改訂: 基準のコミットから追加・変更した行だけを検査する (未コミットの改訂なら HEAD)
python3 ~/.claude/skills/workflow-doc-write/scripts/doc_check.py --base <コミット> <ファイル>...
```

| 出力の種類 | 何が見つかったか | 直し方 |
| --- | --- | --- |
| `[process]` (error) | 過程の記述 (「以前は」「〜に変更した」「撤回」、日付つきの観察記録など) | 結論と理由の形に書き直すか、手順 3 の置き場所へ移す |
| `[verification]` (error) | 検証の経緯 (「確かめていない」「未実測」など) | 「依拠する外部事実」の表へ移すか、完了報告に書く |
| `[long]` (error) | 100 字を超える文 | 1 文 1 論点に分ける |
| `[duplicate]` (warning) | 別の節にほぼ同じ文がある | 1 か所にまとめ、もう一方は節名で参照する |

- exit code は、error が 1 件でもあれば 1、無ければ 0 である。error が 0 件になるまで直す。直すのは 2 回までにし、それでも残るものは理由を完了報告に書く (例: 旧状態の環境に向けた移行手順)
- 次のものは、過程と検証の経緯を検査しない
  - `DESIGN_NOTES` / `CHANGELOG` / `ADR` などの記録用の文書と、「依拠する外部事実」「変更履歴」の節
  - 「」と『』の中の語句。規則が禁止の例として引用した語だからである
  - `<!-- doc-check: skip-process -->` を書いた文書。過程の語そのものを定義・説明する規範の文書 (このスキルと `documentation.md`) だけに付ける
- yomiyasu のリンター (`python3 ~/.claude/skills/yomiyasu/scripts/yomiyasu_lint.py <ファイル>`) も流し、指摘を見直す。正当な専門用語と、意味を担う否定 (A ではなく B) は、指摘があっても残す

## 7. 整合性を確かめる

1. **依拠事実の再検証**: 文書が前提にする実環境 (設定ファイル・CI・コマンド・ディレクトリ構成) を rg で確かめる。過去の調査結果を使い回さない (環境は文書と並行して変わる)
2. **固有名の閉包**: 新しく出したコマンド・ファイル・環境変数・用語は、定義・生成者・消費者を同時に書く。「後述」「別途定義」のまま宙に浮いた参照を残さない
3. **残骸の掃除**: 概念を削除・置換したときは、旧概念への参照の残りを rg で探して消す

## 8. 監査の要否を判定する

判定するのは「監査をするか否か」ではなく「**どの観点が必要か**」である。書き手は「定義したつもり」になりやすく、未定義の用語を自分では見つけられない。そのため、第三者のコンテキストに検査させる。**変更の行数は判定に使わない** (30 行の局所の加筆より、3 行の用語の改名のほうが広く波及する)。

- `/utility-doc-audit` は**ユーザー起動専用**である。自分では起動せず、判定の結果を 1 行の依頼にしてユーザーに委ねる (例: `監査依頼: /utility-doc-audit <path> (観点 1,4 / 理由: 新コマンド追加 + 設定パス変更)`)。依頼を出したら、ユーザーの実行を待たずに次の作業へ進んでよい
- 起動する観点は `~/.claude/skills/utility-doc-audit/SKILL.md`「監査モードのトリアージ」3. の表が、変更の性質から観点 1〜5 に対応づけて決める (観点 6「決定カバレッジ」は表の外の規則で、決定台帳を渡したときだけ常に起動する)
- **フル監査になる改訂**: 概念の追加・削除・置換 / 節構成の変更 / 新規文書の作成。観点を絞らず、依頼の行に「フル監査」と書く
- **依頼を出さなくてよい改訂**: トリアージ表のどの観点にも当たらないもの (表の「字句修正のみ」の行 = typo・表記揺れ) だけである。その場合は「監査スキップ: <変更の性質>」を 1 行出す。理由は行数ではなく性質で書く (例: 「監査スキップ: 表記揺れの修正のみ。固有名・フロー・依拠事実・節構成のいずれも変えていない」)
- ユーザーが監査を頼んだ場合も、自分では実行せず、`/utility-doc-audit <path>` の実行をユーザーに促す
- 例外: `/workflow-design-notes` の落とし込みフェーズだけは、同スキルが監査を直接起動する

## 9. 完了報告に書くこと

- 書いた・直した文書のパスと、変更の性質 (手順 2)
- 検査の結果 (error と warning の件数。残したものはその理由)
- yomiyasu の「書き手に確かめたい点」
- 監査の依頼の行、または「監査スキップ」の行
- 本文から外した作業中の検証の記録 (手順 3)

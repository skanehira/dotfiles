# ハーネスの効果計測

ハーネスの改訂が効いたかは、文面を読んでも分からない。実際に `claude -p` を走らせ、出力を第三者に採点させて初めて分かる。本スキルはその計測を、結果を信用できる形で回すための手順と道具である。

## 何を守るための道具か

手で計測すると、次の 4 つが黙って壊れる。`scripts/measure.py` はそれぞれを機械的に検出して、壊れた回やおかしな採点を結果から外す。

| 壊れ方 | 実際に起きたこと | 道具の対処 |
| --- | --- | --- |
| モデルの取り違え | `--model opus` を指定したが、ユーザー設定の env が別名 `opus` を Fable に解決し、18 回すべてが Fable で動いた | 正式 ID を渡し、`--settings` の env で別名もすべて正式 ID に固定する。各回の `modelUsage` を照合し、想定外のモデルが混ざった回は無効にする |
| 途中停止の混入 | 使用量の上限で止まった回の出力 (「You've hit your session limit」) が結果に紛れた | result が無い回・上限停止・エラー終了を無効にする |
| 採点器の不調 | 採点器が違いを見分けられているか、確かめる手段が無かった | ルール本文の ✅ 例と ❌ 例を対照として混ぜる。期待どおりに採点されなければ採点全体を無効にする |
| 採点の偏り | どちらの条件の出力かを採点器が知っていると、点が偏る | 改訂前後の出力を匿名化し、シャッフルして一度に採点させる |

## 前提

- **依存**: python3 (標準ライブラリのみ)、Claude Code の `claude` CLI (ログイン済み)、`git`。`claude` が PATH に無いと `run` と `grade` は起動前に止まる
- **権限**: 子の `claude -p` は bypassPermissions で動かす。許可リスト方式だと `&&` やパイプでつないだコマンドが拒否され、「規定に従って止まったのか、権限で止まったのか」が区別できなくなるため。親のセッションが auto mode だと、`claude -p` の起動そのものが分類器に拒否される。その場合は、ユーザーに bypass permissions へ切り替えてもらうか、下の手順のコマンドをユーザーが `!` を付けて実行する
- **費用**: 1 回あたり 3〜6 USD かかる (2026-10 の実測。Opus と Fable の場合)。実行前に `estimate` で総額を出し、ユーザーの了承を得てから `run` する
- **外部への影響と隔離**: シナリオのリポジトリは毎回複製した使い捨てで、push 先は実在しないパスにする。子は bypassPermissions で動くので、`measure.py` は次の 2 つで被害の範囲を絞る
  - Claude Code のサンドボックスを有効にする。子の Bash は作業ディレクトリと一時ディレクトリにしか書き込めず、HOME 配下 (`~/.claude` や dotfiles の正本) への書き込みは拒否される (2026-10-08 に `~/.cache` への書き込みが `Operation not permitted` になることを確認)。子が自分でサンドボックスを外す抜け道は `allowUnsandboxedCommands: false` で閉じているが、これが効くかは確かめていない
  - 子に渡す環境変数を `CHILD_ENV_KEYS` (PATH / HOME / USER など) だけに絞り、トークン類を渡さない。認証は HOME 経由で通る
  - **ネットワークは塞いでいない** (サンドボックス下でも `curl https://example.com` が 200 を返した)。シナリオの中に本物の remote や外部サービスの認証情報を置かない
- **改訂前の状態は後から作れない**: ルールの正本は symlink で即時に反映されるので、子は計測時点の作業ツリーを読む。HOME や `CLAUDE_CONFIG_DIR` を差し替えて旧版を読ませる方法は認証が切れて使えない。正本を一時的に旧版へ戻す方法は、並行して動いている他のセッションにも効くので使わない。**比較したいなら、改訂する前に `before` を測っておく**。測っていない場合は、改訂後の遵守率だけを報告し、比較できないことを明記する
- **計測中は正本を編集しない**: 実行中の子が途中から新しい文面を読んでしまう。各回の `meta.json` には、計測時点の dotfiles のコミットと `agents/` の未コミット変更の有無を記録する

## トピックの用意

トピックとは、計測する規定 1 件分のディレクトリである。git 管理外の `~/.local/share/harness-measure/<トピック名>/` に置き、結果を蓄積して次の改訂の `before` に使う。

```text
<topic>/
├── rubric.md            採点基準 (採点器に渡す本文。出力形式は measure.py が後ろに付け足す)
├── expected.json        採点項目・満点・対照の期待値
├── controls/pos.txt     満点になるべき出力 (ルール本文の ✅ 例)
├── controls/neg.txt     0 点になるべき出力 (ルール本文の ❌ 例)
├── scenarios/<名前>/
│   ├── setup.sh         引数のパスに使い捨てのリポジトリを作る
│   └── prompt.txt       子に渡す依頼文
├── results/<ラベル>/<シナリオ>-<n>/   run が書く (events.jsonl / meta.json / final.txt)
└── grades/<日時>/       grade が書く (key.json / scores.json / report.md)
```

`assets/example-topic/` に、判断依頼に背景を添える規定 (`~/.claude/rules/core/collaboration.md`「質問・提案の形式」) を測ったときの一式がある。新しいトピックはこれを複製して書き換える。

- **シナリオ**: 規定が効くべき場面を、子が作業の途中で必ず踏むように作る。例の `escalation-force-push` は、移行作業を済ませた後に force push を頼み、破壊的操作の前で判断を求める場面を作る。`completion-decision` は README に矛盾を仕込み、完了報告で決定を求める場面を作る。依存は標準ライブラリだけにして、環境の差で失敗しないようにする。規定の ✅ 例と同じ題材を使わない。子が例をなぞるだけになり、計測にならない
- **採点基準**: 規定が求める項目を 1 つずつ、記憶ゼロの読み手が判断できるかという観点で書く。各項目は 0〜`max` 点で付けさせる
- **対照**: `expected.json` の `controls` に、対照ごとの期待点を書く。陰性対照は、規定と無関係に満点になりうる項目 (例の `ORDER` は短い質問 1 文だと満点になる) を期待値から外す

## 手順

`M=~/.claude/skills/utility-harness-measure/scripts/measure.py`、`T=~/.local/share/harness-measure/<トピック名>` とする。

1. **見積もる**: `python3 $M estimate --topic $T --n 3`。総額をユーザーに示して了承を得る
2. **改訂前を測る**: ルールを編集する前に `python3 $M run --topic $T --label before-<dotfiles の短縮コミット> --n 3`。既定のモデルは `claude-opus-5-5` で、`--model` で正式 ID を渡せる。同じラベルの結果が既にあると上書きせずに止まる
3. **有効性を判定する**: `python3 $M check --topic $T --label <ラベル>`。無効な回は理由が出る (次節)。有効な回が足りなければ、別のラベルで追加分を測る
4. **改訂してコミットする**: 計測と無関係な変更を混ぜない
5. **改訂後を測る**: `run` と `check` を `--label after-<短縮コミット>` で繰り返す。モデルと回数は改訂前と揃える
6. **採点する**: `python3 $M grade --topic $T --labels <before のラベル> <after のラベル>`。改訂前後を一度に匿名採点する。採点モデルは既定で `claude-opus-5-5` で、実行モデルより弱いと止まる。対照が期待どおりでないか、採点モデルが想定と違うと、採点は無効になり `INVALID.txt` に理由が残る (終了コード 2)
7. **報告する**: `report.md` の表を貼り、次節の限界を添える

コマンドは計測の対象と同じマシンで実行する。結果は `~/.claude` の状態と dotfiles の作業ツリーに依存するためである。

## 無効になる回と採点

| 出力 | 意味 | 対処 |
| --- | --- | --- |
| `想定外のモデル: <ID>` | 別名の解決などで、指定外のモデルが使われた | `--settings` の固定が効いていない。`pinned_settings` と、ユーザー設定の env を見直す |
| `実行モデル <ID> が使われていない` | 指定したモデルが 1 度も呼ばれていない | `--model` の ID の綴りを確かめる |
| `使用量の上限で停止` | アカウントの使用量の上限に達した | 上限が戻ってから、別のラベルで追加分を測る |
| `result イベントが無い` | 途中で止めた・落ちた | `stderr.txt` を見る |
| 採点の `対照 pos の S2: 期待 2 / 実際 1` | 採点器が規定を読み違えている | `rubric.md` の項目の書き方を直して採点し直す。計測し直す必要は無い |

## 報告に書く限界

- 各シナリオの回数と、採点を何回したかを書く。3 回程度なら傾向としてしか読めない
- 実行モデルと採点モデルを、正式 ID で書く
- `before` を測っていない場合は、比較していないことを書く
- 規定の外の振る舞いの変化 (例: force push を止めるようになった) に気づいたら、因果を確かめていない観察として分けて書く

## スクリプトのテスト

判定ロジックは `scripts/measure_test.py` にある。`measure.py` を変えたら実行する。

```bash
cd ~/.claude/skills/utility-harness-measure/scripts && python3 -B -m unittest measure_test
```

モデルの正式 ID は `measure.py` 冒頭の `MODEL_IDS` にだけ書いてある。世代が交代したらここを更新する。

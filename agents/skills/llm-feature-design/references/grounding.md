# グラウンディング — 与えた文書だけに基づいて答えさせる

与えた文書・検索結果の範囲内でだけ回答させ、根拠のない断定 (ハルシネーション) を減らすための規範。プロンプト側の 4 手法と、RAG を組む場合のパイプライン設計を扱う。取得文書のセキュリティ上の扱い (配置・エンコード・injection 対策) は `untrusted-input.md`、回答範囲そのものの絞り込みは `scope-limiting.md` を見ること。

信頼度ラベル: 【公式】ベンダー公式ドキュメント / 【標準】OWASP・NIST / 【査読】査読済み論文 / 【プレプリント】未査読 / 【実装】広く使われる OSS の実装 / 【裏付けなし】一次情報に到達できなかった。根拠は同ディレクトリの `evidence.md` を参照 (主に **E3**。§2.4 で E2-5 (OWASP)、§2.5 で E4-1 も参照する。裏付けの無い論点と未検証範囲は **E7**)。

> **未検証範囲についての注意**: `evidence.md` の E7 は、**E3 系の引用のほぼ全て**を「原文照合に着手していない」と申告している。本ファイルの根拠はそこに含まれるので、**重要な判断に使う前に E7 を確認すること。**

---

**目次**: 1 プロンプト側の 4 手法 (「分からない」の許可 / 引用の先行抽出 / 根拠なき主張の撤回 / 外部知識の遮断) / 2 RAG を組む場合の設計 (しきい値・ゼロ件時・出典ラベル・**テナント分離**) / 3 業界合意として述べてはいけないこと

## 1. プロンプト側の 4 手法

以下の 4 つは Anthropic 公式が明示的に挙げているもので、**4 つまとめて入れる**。単独でも効くが、相互に補完的である (許可 → 抽出 → 検証 → 遮断)。→ 根拠: `evidence.md` の E3

### 1.1 「分からない」を明示的に許可する 【公式】

**必ず入れる。** 不確実性を認める許可を与えるだけで誤情報が大きく減る、と公式が述べている。「知らないことは書くな」という**禁止形ではなく、「分からないと言ってよい」という許可形**で書く。禁止形だけだと、モデルは「答えなければならない」制約を抱えたまま埋め合わせを始める。

```
提供された文書に答えが書かれていない場合は、推測せず「文書からは分かりません」と答えてよい。
```

### 1.2 引用を先に抽出させてから答えさせる 【公式】

**長文文書を読ませるときに使う。目安は 20k トークン超。** 回答を書く前に、根拠となる箇所を**逐語で**抜き出させる。これによって回答が実際のテキストに接地する。抽出 → 回答の 2 段構成にすること。

```
まず <quotes> タグの中に、質問に関係する箇所を文書から一字一句そのまま抜き出せ。
その後 <answer> タグの中で、抜き出した引用だけに基づいて答えよ。
```

短い文書 (数千トークン程度) にまでこれを適用すると出力が冗長になるだけなので、長文に限る。

### 1.3 根拠が見つからない主張は撤回させる 【公式】

回答を生成させた**後で**、各主張について裏付けとなる引用を探させ、**見つからなければその主張を削らせる**。1.2 が事前のグラウンディングなのに対し、これは事後の自己検証である。

```
回答を書いたら、各主張について文書中の裏付けとなる引用を探せ。
引用が見つからない主張は回答から削除せよ。
```

### 1.4 外部知識を遮断する 【公式】

提供文書のみを使い、モデルの一般知識を使わせない指示を明示的に置く。書かないと、文書にない一般論が自然に混ざる。

```
回答には、提供された文書に書かれている情報だけを使うこと。一般的な知識で補わないこと。
```

### 1.5 限界を認識しておく 【公式】

**これらで大きく減るが、ゼロにはならない。** 公式が「significantly reduce するが eliminate はしない」と但し書きを付けている。したがって「グラウンディングのプロンプトを入れたから誤情報は出ない」という前提で下流を設計してはいけない。誤情報が出る前提で、影響範囲を UI や権限で抑える。

### 1.6 厳格版と緩和版を選ぶ 【公式】

外部知識の遮断 (1.4) には強度の選択肢がある。**Anthropic 公式の RAG サンプルプロンプトは、厳格版ではなく緩和版を採っている。**

```
提供されたコンテキストに忠実であること。
既に答えを知っていると 100% 確信できる場合に限り、そこから逸脱してよい。
```

厳格版 (「文書外の情報は一切使うな」) は、文書に書かれていない自明な事柄まで拒否させる副作用がある。**用途に応じて選ぶこと。** 誤情報のコストが高い領域 (医療・法務・金銭) では厳格版、一般的な質問応答では公式サンプルどおりの緩和版が出発点になる。どちらを選んだかは実装時に明示的に記録し、評価セットで検証する (`evaluation.md`)。

## 2. RAG を組む場合の設計

### 2.1 低関連度チャンクはモデルに投げる前に切る 【公式】

**しきい値による足切りは検索段階で行う。プロンプトで「関係ない検索結果は無視して」と書いて済ませてはいけない。** OpenAI は検索 API のパラメータ (`score_threshold`、0.0〜1.0) としてこれを提供しており、モデルに渡す前の段階で除外する設計になっている。

プロンプトでの無視指示は、(a) ノイズの分だけトークンとレイテンシを払う、(b) 無視できるかどうかがモデルの判断に委ねられる、の 2 点で劣る。上流で切れるものは上流で切る。

### 2.2 検索ゼロ件はエラーにせず「該当なし」を返す 【公式】

**検索が失敗した・0 件だったときに例外を投げてはいけない。** Anthropic の公式指針は、プレーンテキストで結果なしと返すこと (例: `{"type": "text", "text": "No results found."}`)。モデルが空の結果をユーザに説明し、会話が継続する。

例外にすると、ユーザから見れば「壊れた」ようにしか見えない。「該当する記録は見つかりませんでした」と伝えて次の入力を促す方が体験として正しい。

### 2.3 出典ラベル付きのコンテキストにする 【公式】

コンテキストは平坦な文字列連結ではなく、**由来が区別できる形の配列**にする。「取得文書」「一般知識」「ユーザ提供」のようなラベルを付け、モデルが引用時に出典を示せるようにする。Anthropic には自前文書に出典つき引用を付けるための専用ブロック (`search_result`) がある。

**引用は提供コンテキスト内に限定する。外部知識・外部権威の引用は禁止する。** OpenAI の引用フォーマット指針が明示している (提供コンテキストに現れるブロックのみを引用せよ / 外部の知識や権威を引用するな)。これを書かないと、モデルは「一般にこう言われています」「〇〇のガイドラインによれば」という検証不能な出典を作る。

```
引用は、提供されたコンテキストに含まれるブロックのみに限る。
コンテキスト外の知識や外部の権威を引用してはならない。
```

### 2.4 マルチテナント分離は検索クエリ側で行う 【標準】(手法の指定は本スキルの実装指針)

**最重要。テナント・組織・ユーザごとのデータ分離は、検索クエリのフィルタ条件として実装する。プロンプトに書いてはいけない。**

```
❌ プロンプトに「テナント ID が X のデータだけを使うこと」と書く
✅ 検索クエリの WHERE 句 / メタデータフィルタで tenant_id = X に限定し、
   他テナントのチャンクはそもそもコンテキストに入らないようにする
```

OWASP LLM01 の緩和策 #4 "Enforce privilege control and least privilege access" が根拠になるが、**標準が定めているのは最小権限の原則までで、「検索クエリ側のフィルタで実装せよ」という手法まで規定しているわけではない**。手法の指定は原則から導いた本スキルの実装指針である。→ 根拠: `evidence.md` の E2-5

そのうえで、**プロンプトで機密性を担保しようとするのは常に誤り**である。プロンプトは確率的に従われるだけで、アクセス制御の機構ではない。この 1 点だけは「まずプロンプトで」の例外として扱う。

### 2.5 検索結果そのものにガードを置く構成 【実装】

取得したチャンクを、モデルに渡す前に検査するレイヤを置く構成が存在する (NVIDIA NeMo Guardrails の retrieval rails)。入力ガード・出力ガードとは別の第 3 の設置点として認識しておく価値がある。

ただし**これは単一 OSS の設計であって、標準化団体や複数ベンダーが定めたものではない。** 「業界標準の構成」として提示しないこと。

### 2.6 出力側でグラウンディングを事後検証する 【公式】【標準】

生成された出力を参照文書と突合し、**裏付けのない箇所を検出する**仕組みがマネージドサービスとして存在する (Microsoft Azure の Groundedness detection。preview 段階。自動訂正版は訂正後テキストを返す)。NIST AI 600-1 (MS-2.5-003) も、出力中の出典・引用をデプロイ前のリスク測定と継続監視の両方で検証することを求めている【標準】。

規範としては次の 2 点。**(a) グラウンディングは生成時のプロンプトだけで完結させず、出力側にも検証点を置けることを設計時に検討する。(b) 検証を入れるなら、それが継続的に回る運用 (デプロイ前 + 稼働中) にする。** 一度きりの検証は NIST の要求を満たさない。

## 3. 業界合意として述べてはいけないこと 【裏付けなし】

**「検索結果が空・低スコアなら回答しない」という運用ルールを、業界の合意・標準として述べてはいけない。** → 根拠: `evidence.md` の E7

実装レベルでそう作られている例はある (2.1 のしきい値パラメータがまさにそれ)。しかし「スコアが低ければ回答を拒否する」という運用ルールを定めた標準・公式文書には到達できていない。むしろ Anthropic の公式指針は 2.2 のとおり「ゼロ件ならその旨を伝えて会話を継続させる」であって、拒否ではない。

したがって書き方は次のようにする。

```
❌ RAG では検索スコアが閾値未満なら回答を拒否するのが定石
✅ 低関連度チャンクを閾値で足切りする API は公式に存在する【公式】。
   ただし「根拠が薄いときに回答自体を拒否する」ことを定めた標準は確認できていない【裏付けなし】。
   拒否するか、該当なしと伝えて会話を続けるかは、プロダクトの判断として決める
```

同様に、**RAG で「根拠がないときに必ず拒否する」ことの API レベルの保証は存在しない**。引用機能は引用を返すだけで、根拠不在時の挙動を強制する機能ではない。グラウンディングの保証を API に期待せず、評価セットで実測すること (`evaluation.md`)。

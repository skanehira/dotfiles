## 概要

dev-spec のフェーズ 4 で使う手順書。本書の「手順 N」は本書の中の段階で、SKILL.md のフェーズ番号とは別である。dev-spec のフェーズを指すときは「dev-spec のフェーズ N」と書く。

技術的な実現可能性を評価し、以下を生成する：
1. 技術リスク一覧
2. 検証項目と成功基準
3. PoC計画

## ワークフロー

### 手順 1: コンテキストの確認

対象機能と既存ドキュメントを確認する。

#### 1.1 前提ドキュメントの読み込み

次のファイルを読む:

- `docs/design/USECASES.md`
- `docs/PRODUCT_SPEC.md`
- `docs/design/FEASIBILITY.md` (既にある場合。dev-spec のフェーズ 5 の「再検討」から戻ったときを含む)

#### 1.2 コンテキストの活用

**ファイルが存在する場合**:
- USECASES.md: 検証が必要な機能のフローを把握
- PRODUCT_SPEC.md: プロダクトの技術的制約を把握
- FEASIBILITY.md: 既存の PoC 計画と「PoC 結果」を把握する (手順 7で保持する)

これらの情報を元に、技術リスクを効率的に洗い出す。

USECASES.md がある場合は、読み込んだユースケースを `1. UC-001: <見出し>` の形で番号付きでメッセージに並べ、「どのユースケースの技術検証を行いますか？検証するものの番号を答えてください（複数可）」と聞いて、採用する番号を答えてもらう。

**遷移条件**: 検証するユースケースが決まったら手順 2へ

**ファイルが存在しない場合**:
対象機能をユーザーに確認する。

「どの機能の技術検証を行いますか？」と聞き、自由入力で答えてもらう (目安: 技術検証が必要な機能や領域)。

**遷移条件**: 対象機能が明確になったら手順 2へ

### 手順 2: 技術的不確実性の洗い出し

実現可能かどうか分からない技術要素を特定する。

**質問パターン**:
- 「この機能で技術的に不安な部分は？」
- 「やったことがない技術はありますか？」
- 「パフォーマンス的に問題になりそうな箇所は？」
- 「外部サービスとの連携で不明点は？」

「この機能を実現する上で、技術的に不確実な点、不安な点は何ですか？」と聞き、自由入力で答えてもらう (例: 大量データの処理性能、API連携の可否)。

#### 不確実性の分類

| 種類 | 説明 | 例 |
|------|------|-----|
| **技術的実現性** | そもそもできるか | LLMでSQL改善が可能か |
| **パフォーマンス** | 速度・スケール | 1秒以内に応答できるか |
| **統合** | 外部サービス連携 | DBへの接続方法 |
| **セキュリティ** | 安全性の確保 | 認証情報の扱い |
| **コスト** | 費用対効果 | API利用料金 |

**遷移条件**: 洗い出した不確実な点を示し、ユーザーが網羅できたと認めたら手順 3へ (目安は 3〜5 個。数は条件ではない)

不確実な点が 1 つも無いとユーザーが答えた場合は、手順 3〜8 を行わずに完了する。完了の前に、FEASIBILITY.md の有無で次のどちらかを行う。

- **FEASIBILITY.md が無い**: `docs/design/FEASIBILITY.md` に「不確実性なし」の記録 (形は [feasibility-template.md](feasibility-template.md)「ドキュメント構造」) を書き出す
- **FEASIBILITY.md が既にある** (dev-spec のフェーズ 5 の「再検討」から戻ったときなど): 「不確実性なし」の記録で上書きせず、そのまま残す。上書きすると既存の PoC 計画・POC_STATUS 行・「PoC 結果」が消え、dev-spec のゲートが判定の根拠を失う。残っている未解決の計画は dev-spec のフェーズ 5 が引き続き扱う (検証し直すか、poc-verification.md 手順 4 で人間が決める)

### 手順 3: リスク評価

各不確実性のリスクレベルを評価する。

「[不確実性]について、実現できなかった場合の影響度は？」と聞き、次の選択肢を番号付きでメッセージに並べて、採用する番号を 1 つ答えてもらう。

| 番号 | 選択肢 | 意味 |
| --- | --- | --- |
| 1 | 致命的 | プロダクトが成り立たない |
| 2 | 重大 | 主要機能が使えない |
| 3 | 中程度 | 代替手段がある |
| 4 | 軽微 | なくても問題ない |

続けて「[不確実性]が実際に問題になる (実現できない) 見込みはどのくらいですか？」と聞き、次の 3 択から 1 つだけ選ばせる。

| 選択肢 | 意味 |
| --- | --- |
| 高 | 前例や手がかりが無く、うまくいかない可能性が高い |
| 中 | 手がかりはあるが、この条件で成り立つかは分からない |
| 低 | 類似の実績があり、確認すれば済む見込みが高い |

影響度と発生確率から、次のリスクマトリクスでリスクレベルを引く。

#### リスクマトリクス

| 影響度＼発生確率 | 高 | 中 | 低 |
|-----------------|-----|-----|-----|
| **致命的** | 🔴 最優先 | 🔴 最優先 | 🟡 優先 |
| **重大** | 🔴 最優先 | 🟡 優先 | 🟢 通常 |
| **中程度** | 🟡 優先 | 🟢 通常 | 🟢 通常 |
| **軽微** | 🟢 通常 | ⚪ 低 | ⚪ 低 |

リスクレベルは、手順 5 の PoC 計画の `risk` に次の対応で写す。

| リスクレベル | PoC 計画の `risk` |
| --- | --- |
| 🔴 最優先 | `high` |
| 🟡 優先 | `medium` |
| 🟢 通常 / ⚪ 低 | `low` |

**遷移条件**: 全ての不確実性に影響度・発生確率・リスクレベルが付いたら手順 4へ

### 手順 4: 検証項目の定義

各リスクに対する検証項目を定義する。

次の 2 問をまとめて聞き、それぞれ自由入力で答えてもらう。

1. 「[リスク]を検証するために、何を確認すればよいですか？」 (例: レスポンス時間を計測する)
2. 「成功と判断する基準は何ですか？」 (例: 95%タイルで1秒以内)

#### 検証項目テンプレート

```
## 検証項目: [項目名]

**対象リスク**: [リスクの説明]

**検証内容**:
- 何を検証するか
- どのように検証するか

**成功基準**:
- 定量的な基準（数値）
- 定性的な基準（状態）

**失敗した場合の代替案**:
- プランB
- スコープ縮小案
```

**遷移条件**: 主要リスクの検証項目が定義できたら手順 5へ

### 手順 5: PoC計画

検証のための実装計画を立てる。

「PoCの優先順位をつけてください。最もリスクが高いものから検証すべきです。」と聞き、自由入力で答えてもらう (目安: 1. xxx 2. xxx)。

#### PoC計画テンプレート

FEASIBILITY.md の「## PoC計画」節の下に、計画ごとに次の形で書く。見出しの書式は `### PoC: [PoC名]` に揃える (完了条件のコマンドが見出しを数える)。

```markdown
### PoC: [PoC名]
<!-- POC_STATUS: id=<id>, blocker=<true|false>, status=unresolved -->

**id**: <unique-id> (例: react-19-suspense-async)
**目的**: 何を検証するかを 1 行で
**risk**: high | medium | low (手順 3 のリスクレベルから対応表で写す)
**blocker**: true | false (実装前に必須解決か)

**スコープ**:
- 含む: 含める範囲
- 含まない: 除外する範囲

**実装内容**:
1. ステップ1
2. ステップ2
3. ステップ3

**必要なリソース**:
- 技術: xxx
- 環境: xxx
- データ: xxx

**成功基準**:
- 基準1
- 基準2

**判断**:
- 成功 → 本実装へ
- 失敗 → 代替案を検討
```

**POC_STATUS 行 (機械判定用、必須)**: 見出しの直下に必ず 1 行書く。dev-spec のフェーズ 5 は `status=unresolved` の行を検証対象として抽出し、検証後に status を更新する。dev-spec のフェーズ 6 のゲートもこの行を rg で判定する (書式の定義は [poc-verification.md](poc-verification.md))。この行が無い計画はどちらにも現れず、検証されないまま設計へ進む。

- **id** は安定一意にする。PoC 結果と実装ループの判定ログでも参照されるため、書いた後に変えない
- **目的** は 1 行で書く。dev-spec のフェーズ 5 が tech-investigation に渡す `scope` と、dev-spec のフェーズ 6・7 が書く `POC_NEEDED` マーカーの `scope` はこの行から取る
- **risk** と **blocker** は、POC_STATUS 行と `POC_NEEDED` マーカーへそのまま写される値である

この PoC 計画は直後の dev-spec のフェーズ 5 ([poc-verification.md](poc-verification.md)) で `tech-investigation` subagent により実際に検証される。`blocker=true` の計画は dev-spec のフェーズ 5 での解決が必須。

**遷移条件**: PoC計画が完成したら手順 6へ

### 手順 6: 技術選定の整理（オプション）

採用する技術スタックを整理する。

「この機能の実装に使用する技術（言語、フレームワーク、サービス）は決まっていますか？」と聞き、次の 3 択から 1 つだけ選ばせる。

| 選択肢 | 意味 |
| --- | --- |
| 決まっている | 技術スタックを入力 |
| 検討中 | 候補を入力 |
| 未定 | PoCで決める |

#### 技術選定の観点

| 観点 | 質問 |
|------|------|
| **実績** | チームに経験はあるか |
| **成熟度** | 安定しているか |
| **コミュニティ** | サポートは得られるか |
| **コスト** | ライセンス、運用コストは |
| **将来性** | 長期的にメンテできるか |

**遷移条件**: 技術選定が整理できたら手順 7へ

### 手順 7: ドキュメント生成

テンプレートは [feasibility-template.md](feasibility-template.md) を参照。

FEASIBILITY.md が既にある場合 (dev-spec のフェーズ 5 の「再検討」から戻ったときを含む) は、既存の PoC 計画の id・POC_STATUS 行・「PoC 結果」節をそのまま保持する。今回の見直しで増えた計画だけを、新しい id と `status=unresolved` の POC_STATUS 行で足す。既存の行の status を書き換えたり id を振り直したりすると、検証済みの結果と計画の対応が壊れる。

### 出力ファイル

`docs/design/FEASIBILITY.md` に書き出す。

### 手順 8: セルフレビュー（サブエージェント）

生成したドキュメントのレビューをサブエージェントに委譲する。

サブエージェント `general-purpose` を起動する (モデル: opus を明示)。

- 説明: `技術検証レビュー`
- 次の指示文を渡す:

```
以下の技術検証ドキュメントをレビューし、問題があれば修正してください。

## レビュー対象ファイル
- docs/design/FEASIBILITY.md

## レビュー観点

1. **不確実性の網羅性**: 技術的な不確実性が十分に洗い出されているか
2. **リスク評価の妥当性**: 影響度と発生確率の評価が適切か
3. **検証項目の具体性**: 何をどう検証するかが明確か
4. **成功基準の測定可能性**: 定量的で測定可能な基準か
5. **代替案の実現可能性**: 失敗時の代替案が現実的か
6. **PoC計画の実行可能性**: 必要なリソースと手順が明確か
7. **POC_STATUS 行の有無**: 各 PoC 計画 (`### PoC:` 見出し) の直下に POC_STATUS 行があり、その id・blocker が計画本文の `**id**`・`**blocker**` と一致するか

既存の POC_STATUS 行の status・id・blocker の値は変えないこと。行が無い計画には、計画本文の値で `status=unresolved` の行を足してよい。

## 出力形式

1. 発見した問題のリスト（問題がない場合は「問題なし」）
2. 各問題の修正内容
3. 修正後のファイル更新（ファイルを直接修正する）

レビューと修正は最大 2 周とする。2 周で解消しなかった問題は修正せず、「残った問題」として列挙して返すこと。
```

サブエージェントが「残った問題」を返したら、ユーザーに提示して扱いを決めてもらう。

## 完了条件

- [ ] 技術的不確実性が洗い出されている
- [ ] リスク評価が完了している
- [ ] 検証項目と成功基準が定義されている
- [ ] PoC計画が作成されている
- [ ] FEASIBILITY.mdが生成されている
- [ ] PoC 計画の見出しの数と POC_STATUS 行の数が一致する (`rg -c '^### PoC:' docs/design/FEASIBILITY.md` と `rg -c 'POC_STATUS:' docs/design/FEASIBILITY.md` の出力する件数が同じ。0 件のときはどちらも何も出力しない)
- [ ] セルフレビューが完了し、問題が解消されている (2 周で残った問題はユーザーに提示済み)

手順 2で「不確実性なし」とした場合の完了条件は、FEASIBILITY.md が無かったときは「不確実性なし」の記録 ([feasibility-template.md](feasibility-template.md)「ドキュメント構造」の形) が書き出されていること、既にあったときはそれが書き換えられずに残っていることだけである。

## 後段フェーズとの連携

このフェーズが残した PoC 計画は、後段で次のように扱われる:

1. **dev-spec のフェーズ 5 (PoC 検証)**: `status=unresolved` の計画を `tech-investigation` subagent の並列 fan-out で実際に検証し、結果 (verified / fallback 採用 / スコープ縮小) を FEASIBILITY.md の「PoC 結果」に記録する。未解決の blocker=true が残る限り設計書生成 (dev-spec のフェーズ 6) に進めない
2. **dev-spec のフェーズ 6・7 (design-doc / feature-doc)**: 検証済みの PoC 結果を技術選定の根拠として DESIGN.md に反映する。未検証で残った `blocker=false` の計画のみ `POC_NEEDED` マーカーとして、DESIGN.md の該当節 (dev-spec のフェーズ 6) または docs/design/features/ の該当ファイル (機能単体の契約に属するもの。dev-spec のフェーズ 7) に転記する (マーカーの書式は [design-doc.md](design-doc.md) の記入基準)
3. **実装ループ (`/dev-impl`)**: 起動時に `blocker=true` マーカーの残存をチェックし、見つけたら実装に入らず dev-spec のフェーズ 5 への差し戻しを案内する (安全網)

このため、PoC 計画を書くときは:

- **実装方針が PoC 結果で大きく変わる** → `blocker=true` を付ける (dev-spec のフェーズ 5 で必ず解決される)
- **無くても代替案で進める** → `blocker=false` (継続可、後追いで検証)

# UI スケッチの批評

- 種別: 手順書
- 読み手: dev-spec の UI スケッチ (ui-sketch.md の手順 5.5) が起動する批評の subagent
- 生成するもの: 指摘の一覧 (ファイルは書き換えない)
- 消費者: スケッチを作ったエージェント (指摘を直し、撮り直す)

スケッチをユーザーに渡す前に、作ったエージェントとは別のコンテキストで、描画結果のスクリーンショットを見て指摘を返す。作った本人は意図を知っているので、見出しの無い列や行き止まりの画面に気付かない。HTML のソースを読むだけでも気付かない。必ず画像を見る。

## 入力

起動する側が、次の 5 つを指示文に書く。

| 入力 | 例 |
| --- | --- |
| スクリーンショットのディレクトリ | `<SCRATCH>/sketch-shots/` (`light-<画面 ID>.png` と `dark-<画面 ID>.png`) |
| スケッチ | `docs/design/UI_SKETCH.html` |
| ユースケース | `docs/design/USECASES.md` |
| 合意した方向性 | 密度 (詰める)、主な入力手段 (キーボード)、手本の製品 (Linear)、トーン |
| ユーザーが決めたこと | キーの割り当て、画面の構成など、ユーザーが選んだ点の一覧 (例: 「表示の切り替えは Ctrl+h / Ctrl+l」)。決定台帳があればそのパス |

## 担当

批評は 2 本を並行で起動する。PC とスマホの両方の画面があるスケッチでは、スマホの画面を 3 本目に分ける。

| 担当 | 見るもの |
| --- | --- |
| 見た目と情報の並べ方 | 全スクリーンショットと「見た目の観点」 |
| 操作と導線 | 全スクリーンショット、スケッチのソース、USECASES.md と「操作の観点」 |

## 守ること

- スクリーンショットを全部 Read で開く。開いていない画面について指摘を書かない
- ファイルを書き換えない。直すのは起動した側である
- 指摘は画像かソースで確かめられたものだけにする。推測は書かない
- 好みの話 (色の趣味など) は、合意した方向性と食い違うときだけ指摘する
- 「ユーザーが決めたこと」を覆す直し方を書かない。決めたことがユースケースや手本の製品の慣習と食い違うときは、直し方を書かずに「食い違い」として 1 行で報告する

## 見た目の観点

各項目を、画面ごとに「満たす / 満たさない」で判定する。

1. **密度**: 行の高さ・余白・文字の大きさが、合意した密度に合っている。合意が「詰める」なら、一覧の 1 行は 24〜32px に収まる
2. **列の見出し**: 列に並べた情報には、列の見出しがある。見出しの語と、その列の中身が合っている
3. **1 行に 1 組**: キーと説明、項目と値のような組は、1 行に 1 組だけ書き、列が揃っている。空白の数で桁を合わせていない
4. **見出しと中身の区別**: 見出しは、太さ・大きさ・線・地の色のどれかで、中身とはっきり違って見える
5. **読む順序**: その画面で最初に読ませる情報が、左上か先頭にあり、いちばん目立つ。重要でない情報が左端や先頭を占めていない
6. **状態の表し方**: 進み具合・状態・選択の有無は、色・形・部品で表している。罫線の文字で描いた木や、`[x]` のような文字のままの部品が無い
7. **同じものは同じ見た目**: 同じ種類の行・見出し・ボタンが、画面ごとに違う見た目になっていない
8. **崩れ**: 重なり、はみ出し、切れ、桁のずれ、通知が中身を隠す箇所が無い
9. **見本データ**: 見出しと中身、画面どうしで、同じ対象の名前・件数・状態が食い違っていない
10. **ライトとダーク**: 両方で文字が読め (本文は 4.5:1 以上)、選択中の行と面の境目が見える

## 操作の観点

1. **次の操作が分かる**: どの画面でも、次にできる操作と、その方法 (ボタン、キー) が画面に出ている。ヘルプを開かないと分からない操作が無い
2. **移動の経路**: USECASES.md の各フローのステップを、画面と操作で最後までたどれる。行き止まりの画面と、戻り方の分からない画面が無い
3. **主な入力手段で完結する**: 合意した入力手段 (キーボードが主なら、キーだけ) で、すべての画面へ移れ、すべての操作ができる
4. **いまどこにいるか**: 開いている対象 (プロジェクト、項目、表示の種類) が、画面のどこかに常に出ている
5. **取り消せない操作**: 承認・削除・送信のような操作は、確認か取り消しがある。1 回の誤操作で実行されない
6. **フィードバック**: 操作の結果が画面に出る。通知は中身を隠さず、画面を移ったら消える
7. **用語**: 同じものを別の名前で呼んでいない。同じ名前が別のものを指していない
8. **割り当ての衝突**: キーの割り当てが、その入力手段の慣習 (Vim、OS、ブラウザ) と衝突していない。衝突を選ぶなら、画面に理由か案内がある
9. **再読み込み**: 再読み込みしても、見ていた画面に戻る
10. **受け入れ基準の入口**: USECASES.md の受け入れ基準のうち、画面に操作の入口が無いものが無い

## 出力

重要度の高い順に、最大 25 件を次の形で返す。

```text
[high|medium|low] <画面 ID> (<ファイル名>) / <観点の番号と名前> / <何が問題か 1 文> / <直し方 (具体的な値・配置・文言) 1 文>
```

| 重要度 | 基準 |
| --- | --- |
| high | ユーザーが触れば必ず指摘する。操作が行き止まりになる、情報が読み取れない、崩れている |
| medium | 読む・操作するのに余計な手間がかかる |
| low | 見た目の細部 |

最後に、合意した方向性の各項目 (密度、入力手段、手本の製品、トーン) について、「合っている / 一部 / 合っていない」と、根拠になるファイル名を 1 行ずつ書く。

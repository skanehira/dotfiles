# 挙動の方針と細部の決め方

- 種別: 手順書
- 読み手: dev-spec を実行するエージェント (dev-spec のフェーズ 2・3・6・7・8 の手順書から参照される)
- 生成するもの: USECASES.md の「挙動の方針」の節、方針から導いた規則 (BR) とエッジケースの決定、確認点の一覧
- 消費者: ユーザー (方針を決め、確認点を読む)、機能設計書を書くエージェント、設計チェックの subagent

細部の挙動は、1 件ずつユーザーに聞かない。ユーザーは少数の方針を決め、細部はエージェントが方針から導き、決めた結果を確認点としてまとめて見せる。細部を 1 件ずつ聞くと質問が数十件になり、聞かずに放置すると実装者が場当たりで決めるためである。

## 用語

| 用語 | 意味 |
| --- | --- |
| 細部の挙動 | 画面に出ているものが、いつ・何をきっかけに変わるかの決まり。例: 未読の印がいつ消えるか、下書きを別の端末でも見られるか |
| 挙動の方針 | 複数の細部の挙動をまとめて決める、プロダクト全体に効く決まり。例: 「送る前の入力はサーバーに保存し、どの端末でも同じにする」 |
| 確認点 | エージェントが決めた細部のうち、利用者から見える違いを生むもの。ユーザーが後から読んで直せるように一覧にする |

## 挙動の観点

細部の挙動は、次の 6 つの観点で洗い出す。フローの記述と画面だけからは出てこないので、観点ごとに一巡する。

| # | 観点 | 探すもの | 例 |
| --- | --- | --- | --- |
| 1 | 表示の寿命 | 印・区切り・お知らせ・バナーのような一時的な表示が、いつ消えるか | 「新着」の区切りは、読み終えたときに消えるのか、画面を移ったときに消えるのか |
| 2 | 送る前のデータ | 下書き・選択中の項目・送信待ちの内容を、どこに置き、いつまで残すか | 入力の途中でタブを閉じたら、下書きは残るか |
| 3 | 状態の移り変わり | 状態が移るきっかけと移った先。人が操作していないのに移る場合を含む | 差し戻した申請は、直し終えたらどの状態に戻るか |
| 4 | 自動で進むこと | 利用者の操作なしにシステムが実行すること。再試行、再開、送信、時間切れ | 失敗した処理を自動でやり直すか、利用者が押すまで待つか |
| 5 | 端末と画面をまたぐこと | 既読・位置・開いている表示を、端末の間で共有するか、端末ごとに持つか。同時に操作したときにどちらを残すか | PC で読んだものは、スマホでも既読になるか |
| 6 | 並びと数え方 | 並び順、件数の数え方、経過時間の起点、上限を超えたときの扱い | 「3 分前」は、何が起きてからの時間か |

## 方針を立てる

方針は 3〜7 個にする。細部を 1 件ずつ並べるのではなく、同じ理由で決まる細部を 1 つの方針にまとめる。

1. 上の 6 つの観点で、ユーザーストーリーとフローから、決まっていない細部を洗い出す
2. 洗い出した細部を、同じ決め方で決まるものどうしにまとめ、まとめごとに方針を 1 文で書く
3. 方針ごとに、推奨の案と、その案を選んだときに決まる細部の例を 2〜3 件添えて、ユーザーに示す。ユーザーは方針を承認するか、変える方針を番号で指定する
4. 承認された方針を USECASES.md の「挙動の方針」の節に書く (クイックモードで USECASES.md が無いときは、DESIGN.md「横断規約」の「挙動の方針」の項に直接書く)

方針の例を次に挙げる。プロダクトに合わせて書き換える。

| 方針の例 | 決まる細部の例 |
| --- | --- |
| 送る前の入力はサーバーに保存し、どの端末でも同じにする。送るか自分で消すまで残す | 下書きが別の端末でも見える。画面を閉じても選択が残る |
| 利用者が始めた処理の続きは自動で進める。利用者が書いた内容を送るのは、利用者の操作だけにする | 時間切れからの再開は自動。通信が戻っても自動では送らない |
| 読んだ・決めたという事実は端末の間で共有する。画面の見え方は端末ごとに持つ | 既読はどの端末でも同じ。スクロールの位置は端末ごと |
| 取り返しのつかない操作は、確認か取り消しの猶予を挟む。猶予のあいだは実行しない | 削除は確認を出す。承認は数秒のあいだ取り消せる |

## 細部を決める

方針が決まったら、細部はエージェントが決める。ユーザーに聞くのは、次の 2 つのどちらかに当たるものだけにする。

| ユーザーに聞くもの | 例 |
| --- | --- |
| どの方針からも決まらず、後から変えると作り直しが大きいもの | データをどこに持つか、外部に公開する API の形、削除したものを復元できるか |
| エージェントに決める権限が無いもの | 料金、利用規約、外部サービスの契約に関わる動き |

それ以外は、次の順で決める。

1. 当てはまる方針があれば、その方針から導く
2. 方針が無ければ、同じ種類の製品で一般的な動きを選ぶ
3. どちらでも決まらなければ、利用者の入力や作業が失われない方を選ぶ

決めた細部は、ユースケースの規則 (BR) か、機能設計書の「エッジケースの決定」に書く。どの方針から導いたかを添える必要は無い。規則は、それだけを読んで動きが分かる文にする。

## 確認点

決めた細部のうち、利用者から見える違いを生むものは、フェーズの完了報告に確認点として一覧にする。1 件を次の形で書く。

```text
<起きる場面> / <この設計での動き> / <別の案>
```

例: `入力の途中で通信が切れたとき / 書いた内容は未送信として残り、通信が戻っても自動では送らない / 通信が戻ったら自動で送る`

- 確認点は質問ではない。ユーザーが何も言わなければ、その決定のまま進む
- ユーザーが確認点を変えたときは、同じ方針から導いたほかの細部も見直す。方針そのものが変わるなら、「挙動の方針」の節を書き直してから細部を導き直す
- 実装の語 (API のパス、関数や変数の名前) で書かない

## どのフェーズで使うか

| フェーズ | すること | 参照する手順書 |
| --- | --- | --- |
| 2 ユースケース記述 | 方針を立ててユーザーの承認を取り、規則 (BR) を方針から導く。確認点を示す | usecase-description.md 手順 7 |
| 3 UI スケッチ | スケッチを作る途中でエージェントが埋めた挙動を「スケッチが決めた挙動」の表に書き出し、USECASES.md の規則に戻す | ui-sketch.md 手順 6 |

| 8 設計チェック | 変わるきっかけが決まっていない要素を、別のコンテキストで探す | SKILL.md フェーズ 8 の観点 8 |

## 概要

dev-spec のフェーズ 1 で使う手順書。本書の「手順N」は本書の中の段階で、SKILL.md のフェーズ番号とは別である。

対話を通じてユーザーストーリーを作成し、以下を生成する：
1. ユーザーストーリーリスト
2. 優先順位付け（MoSCoW / ICE）

受け入れ基準はここでは書かない。ストーリーを実現するユースケースの末尾に、ストーリー番号を付けて書く（[usecase-description.md](usecase-description.md)）。追跡と完了の単位はユースケースなので、検証条件もユースケースに置く。

## ワークフロー

### 手順1: コンテキストの確認

対象プロダクトと既存ドキュメントを確認する。

#### 1.1 前提ドキュメントの読み込み

```javascript
Read({ file_path: "docs/PRODUCT_SPEC.md" })
Read({ file_path: "docs/PROBLEM_DEFINITION.md" })
```

#### 1.2 コンテキストの活用

**ファイルが存在する場合**:
- PRODUCT_SPEC.md: プロダクトのスコープ、コア価値を把握
- PROBLEM_DEFINITION.md: ターゲットユーザー、ジョブを把握

これらの情報を元に、手順2のユーザータイプ特定を効率化。

**遷移条件**: 手順2へ

**ファイルが存在しない場合**:
AskUserQuestionで対象プロダクトを確認。

```javascript
AskUserQuestion({
  questions: [
    {
      question: "どのプロダクト/機能のユーザーストーリーを作成しますか？",
      header: "対象",
      options: [
        { label: "プロダクトを入力", description: "対象のプロダクトや機能領域" }
      ],
      multiSelect: false
    }
  ]
})
```

**遷移条件**: コンテキストが把握できたら手順2へ

### 手順2: ユーザータイプの特定

ストーリーの主語となるユーザータイプを洗い出す。

```javascript
AskUserQuestion({
  questions: [
    {
      question: "このプロダクトを使うユーザータイプは誰ですか？（複数可）",
      header: "ユーザータイプ",
      options: [
        { label: "ユーザータイプを入力", description: "例: 開発者、管理者、ゲストユーザー" }
      ],
      multiSelect: false
    }
  ]
})
```

**遷移条件**: ユーザータイプが1-3個特定できたら手順3へ

### 手順3: ストーリーの作成

各ユーザータイプについてストーリーを洗い出す。

#### ストーリーフォーマット

```
[ユーザータイプ]として
[やりたいこと]したい
なぜなら[得られる価値/理由]だから
```

**質問パターン**:
- 「[ユーザータイプ]がこのプロダクトで最初にやりたいことは？」
- 「それができたら、次に何をしたいですか？」
- 「なぜそれをしたいのですか？」
- 「それができないと何が困りますか？」

```javascript
AskUserQuestion({
  questions: [
    {
      question: "[ユーザータイプ]として、何ができるようになりたいですか？\n\nフォーマット: [やりたいこと] → [得られる価値]",
      header: "ストーリー",
      options: [
        { label: "ストーリーを入力", description: "例: SQLを入力する → 改善案を得られる" }
      ],
      multiSelect: false
    }
  ]
})
```

#### ストーリーの粒度

- **エピック**: 大きな機能群（複数ストーリーの親）
- **ストーリー**: 1-3日で実装できる単位
- **タスク**: ストーリーを分解した作業単位

```
エピック: クエリ最適化機能
├── ストーリー: SQLを入力できる
├── ストーリー: AIが改善案を生成する
├── ストーリー: ベンチマーク結果を比較できる
└── ストーリー: 結果をエクスポートできる
```

**遷移条件**: 主要なストーリーが10-20個出たら手順4へ

### 手順4: 優先順位付け

ストーリーの優先順位を決定する。

#### MoSCoW法

| カテゴリ   | 説明                           |
| ---------- | ------------------------------ |
| **Must**   | なければリリースできない       |
| **Should** | 重要だが、なくてもリリース可能 |
| **Could**  | あると嬉しい                   |
| **Won't**  | 今回はやらない                 |

```javascript
AskUserQuestion({
  questions: [
    {
      question: "このストーリーの優先度は？",
      header: "MoSCoW",
      options: [
        { label: "Must", description: "必須。これがないとリリースできない" },
        { label: "Should", description: "重要だが、なくてもリリース可能" },
        { label: "Could", description: "あると嬉しい" },
        { label: "Won't", description: "今回はやらない" }
      ],
      multiSelect: false
    }
  ]
})
```

#### ICEスコアリング（代替手法）

| 要素           | 説明               | スコア |
| -------------- | ------------------ | ------ |
| **Impact**     | ユーザーへの影響度 | 1-10   |
| **Confidence** | 実現できる確信度   | 1-10   |
| **Ease**       | 実装の容易さ       | 1-10   |

ICEスコア = Impact × Confidence × Ease

**遷移条件**: 全ストーリーに優先度がついたら手順5へ

### 手順5: ドキュメント生成

Must・Should・Could のストーリーは `#### US-<番号>` 見出しで書き、本文の 3 行のあとに `**エピック**` 行を必ず置く。番号は US-001 から振り、欠番を詰めない。Won't は見出しにせず表に並べ、番号を振らない。ユースケース側の被覆チェック（全 US が受け入れ基準に現れるか）は `#### US-` 見出しを数えるため、Won't を見出しにすると実現しないストーリーまで未被覆として報告される。

各ストーリーの「実現するユースケース」行は、ここでは書かない。ユースケース記述（dev-spec のフェーズ 3）が受け入れ基準を書いたあとに、`**エピック**` 行の直前へ挿入する。

USER_STORIES.md が既にある場合（更新・部分実行）は、既存のストーリーの番号と「実現するユースケース」行を保ったまま書き換える。新しいストーリーには末尾に続く番号を振る。番号はユースケースの受け入れ基準の接頭辞から参照されているので、振り直すと対応が壊れる。

```markdown
# ユーザーストーリー

## ユーザータイプ

| タイプ | 説明 |
|--------|------|
| 開発者 | DBA不在チームの開発者 |

## エピック一覧

1. クエリ最適化機能
2. 結果表示機能
3. ...

## ストーリー一覧

受け入れ基準はユースケースごとに `USECASES.md` に置く。各ストーリーには受け入れ基準の代わりに、ユースケース記述のあとで「実現するユースケース」行が追記される。

### Must（必須）

#### US-001: SQLを入力できる

- **開発者として**
- **SQLとスキーマを入力したい**
- **なぜなら** 改善案を得られるから

**エピック**: クエリ最適化機能

---

### Should（重要）

#### US-002: ...

---

### Could（あると嬉しい）

...

---

### Won't（今回はやらない）

| ストーリー | やらない理由 |
|------------|--------------|
| 分析結果をチームに共有する | 初期リリースは個人利用に絞る |

## 優先順位サマリー

| 優先度 | ストーリー数 |
|--------|-------------|
| Must | X |
| Should | X |
| Could | X |
| Won't | X |
```

### 出力ファイル

```javascript
Write({
  file_path: "docs/design/USER_STORIES.md",
  content: userStoriesContent
})
```

### 手順6: セルフレビュー（サブエージェント）

生成したドキュメントのレビューをサブエージェントに委譲する。レビューは 2 系統に分ける:

- **観点 A（自己修正系）**: フォーマット・INVEST 等の機械的な問題。サブエージェントが Edit で直接修正する
- **観点 B（多角的な考慮漏れチェック）**: 指摘ごとに「明らかな不足 → 直接修正」「仕様が不明瞭・スコープ判断が必要 → 親に報告してユーザの判断を仰ぐ」を使い分ける

```javascript
Agent({
  description: "ユーザーストーリーレビュー",
  subagent_type: "general-purpose",
  model: "opus",
  prompt: `
以下のユーザーストーリードキュメントをレビューしてください。

## レビュー対象ファイル
- docs/design/USER_STORIES.md

## レビュー観点 A（問題があれば Edit ツールで直接修正する）

1. **INVEST基準**: 各ストーリーがIndependent、Negotiable、Valuable、Estimable、Small、Testableか
2. **フォーマットの一貫性**: 「〜として」「〜したい」「なぜなら〜」の 3 要素と `**エピック**` 行が揃っているか。Won't が `#### US-` 見出しではなく表で書かれているか。既存のストーリーの番号と「実現するユースケース」行は変えない
3. **優先度の妥当性**: MoSCoWの分類が適切か、Must項目が多すぎないか
4. **ストーリーの粒度**: 1-3日で実装可能なサイズか、大きすぎるものはないか

受け入れ基準はユースケース側で書くので、ストーリーに受け入れ基準が無いことは指摘しない。

## レビュー観点 B（多角的な考慮漏れチェック）

多角的な視点で考慮漏れがないかをチェックし、指摘ごとに次の 2 つを使い分ける:

- **直接修正**: 既存ストーリーや文脈から修正内容が一意に導ける明らかな不足
  （例: 「なぜなら」が抜けているが、エピックの説明から理由が一意に読める）。Edit ツールで修正する
- **要ユーザ判断**: 仕様が不明瞭・複数の解釈がある・スコープや優先度の判断が必要な指摘
  （例: 管理者ユーザーを想定すべきか、退会機能を今回のスコープに含めるか）。
  ドキュメントは修正せず報告する。迷ったら要ユーザ判断に倒す

1. **ユーザータイプの抜け**: 管理者・運用者・初回利用者など、想定すべきなのに登場しないユーザーはいないか
2. **操作ライフサイクルの抜け**: 作成だけあって編集・削除・一覧がない等、CRUD の欠けはないか
3. **異常系・境界ケース**: 権限なし・データ0件・同時実行・外部サービス障害時のストーリーは必要ないか
4. **利用ライフサイクル**: 初回セットアップ・データ移行・退会/削除など、利用の開始と終了の場面が漏れていないか
5. **非機能要件**: 性能・セキュリティ・アクセシビリティで、ユーザー価値に直結するものが漏れていないか

## 出力形式

観点 A と観点 B の直接修正分は、問題がなくなるまでレビューと修正を繰り返すこと。
完了後、以下の 2 つを最終報告に含め、必ず SendMessage で親に送ること:

1. **自己修正した問題のリスト**（観点 A と観点 B の直接修正分。なければ「問題なし」）
2. **要ユーザ判断リスト**: 該当する観点 B の指摘ごとに以下の形式（なければ「考慮漏れなし」）
   - 指摘: <何が漏れているか>
   - 根拠: <なぜ必要と考えたか>
   - 提案: <追加するストーリー案 (〜として / 〜したい / なぜなら〜) とエピック案と優先度案>
`
})
```

### 要ユーザ判断リストの処理（親）

サブエージェントの報告に要ユーザ判断リストが含まれる場合、親は AskUserQuestion で指摘ごとの採用可否をユーザに確認する（multiSelect。指摘が 5 件以上ある場合は 4 件ずつ質問を分割する）:

```javascript
AskUserQuestion({
  questions: [{
    question: "セルフレビューで以下の考慮漏れが指摘されました。USER_STORIES.md に反映するものを選んでください。",
    header: "考慮漏れ",
    multiSelect: true,
    options: [
      { label: "1: <指摘の短い要約>", description: "<提案ストーリーの要約と優先度案>" },
      { label: "2: <指摘の短い要約>", description: "..." }
    ]
  }]
})
```

採用された指摘は親が USER_STORIES.md に反映する。優先度案が Must・Should・Could なら末尾に続く番号を振り、`**エピック**` 行を付けてそのセクションに追記する。Won't なら番号を振らず、Won't の表に行を足す。どちらの場合も優先順位サマリーを更新する。全件不採用ならそのまま次へ進む。

## ストーリー作成のコツ

### 良いストーリーの条件（INVEST）

| 条件            | 説明                       |
| --------------- | -------------------------- |
| **I**ndependent | 他のストーリーに依存しない |
| **N**egotiable  | 詳細は交渉可能             |
| **V**aluable    | ユーザーに価値がある       |
| **E**stimable   | 見積もり可能なサイズ       |
| **S**mall       | 小さい（1-3日で完了）      |
| **T**estable    | テスト可能（検証条件そのものはユースケース側の受け入れ基準で書く） |

### 避けるべきストーリー

```
❌ 「データベースを設計する」
   → ユーザー価値がない（技術タスク）

❌ 「ユーザーとしてすべての機能を使いたい」
   → 大きすぎる、具体性がない

❌ 「管理者としてバグを修正したい」
   → ストーリーではない
```

## 完了条件

- [ ] ユーザータイプが特定されている
- [ ] ストーリーが10-20個作成されている
- [ ] 全ストーリーに優先度がついている
- [ ] Won't が見出しではなく表で書かれている
- [ ] USER_STORIES.mdが生成されている
- [ ] セルフレビューが完了し、問題が解消されている
- [ ] 考慮漏れの指摘（要ユーザ判断）がユーザに確認され、採用分が反映されている

# 機能設計書 (docs/design/features/) の書き方 (dev-spec のフェーズ 7)

- 種別: テンプレート + 記入基準
- 生成者: dev-spec のフェーズ 7。更新者: dev-impl (実装詳細レベルの乖離補正のみ。契約レベルは人間にエスカレーション)
- 消費者: 「何を作るか」は人が機能の概要を知るために読む。ほかの節は issue の `## 設計` 節から参照される / dev-impl の implementer・review-impl が実装と突合する / AI が「この機能の設計はどうなっているか」をローカルで引く

## 単位と命名

**1 機能 = 1 ファイル、機能名で命名する** (例: `docs/design/features/export.md`、`docs/design/features/tag-search.md`)。UC 番号では命名しない — 人間にも AI にも機能名の方が引きやすい (`rg export docs/` で当たる)。UC との対応は冒頭メタ情報の 1 行で保つ。複数 issue が同じ機能設計書を参照してよい。

機能の切り方は UC を出発点にする (1 UC = 1〜2 機能が目安)。UC を持たない構成 (クイックモード) ではタスク説明から機能を切り出す。

書き始める前に次を Read する。無いものは飛ばす。

## 記入基準

- **「何を作るか」は人が読む節、ほかの節は実装する AI が読む契約である**: 「何を作るか」だけを読んだ人が、その機能の概要をつかめるように書く。上限は 40 行 (空行を除く)・合計 4,000 バイト・1 行 450 バイト (日本語 1 字は 3 バイト) で、実装の語 (バッククォートで書く名前・パス) を書かない。流れ・決まりのうち要らないものは省き、種類や状態を比べるときは表を使ってよい。契約を変えたときは、この節に足すのではなく、いまの仕様の概要として書き直す。概要に要らない変更なら、この節は変えない。例外を落として言い切らない (`overview-doc.md` の記入基準と共通)。契約の文 (どの文書が正本か、判定の式、拒否のコードなど) はほかの節に書く
- **「変更履歴」のコメントを書かない**: git の履歴と PR が持つ
- **テスト方針は受け入れ基準から起こす**: 表の 1 行が、実装時にテストで pin する 1 つの振る舞いになる。implementer は表の行を割り当てたレベルのテストで pin し、review-impl は各行にテストがあるかを検査する。レベルを選ぶ前に、行ごとに `~/.claude/guidelines/core/testing.md`「テストを書くかを先に決める」でテストの要否を決める。テストしない行はレベルに `なし (<理由>)` と書き、implementer はその行のテストを書かない (review-impl は理由が同節の 2 つの軸に沿っているかを見る)。行の起こし方は「対象 UC」で分かれる

  | 「対象 UC」 | 表の 1 列目 | 書き方 |
  | --- | --- | --- |
  | UC 番号を書いた | `受け入れ基準 (docs/design/USECASES.md)` | その UC の受け入れ基準のうち、この機能が担う行を文面そのままで写す。接頭辞 `（US-<番号>）` が無い構成 (USER_STORIES.md を作らなかった場合) は接頭辞なしで写す |
  | なし (基盤系・クイックモード) | `確かめること (タスク説明から起こした)` | タスク説明から、受け入れ基準と同じ「どんなときに、何をすると、どうなるか」の 1 文を起こす。接頭辞は付けない |

  「対象 UC」に複数の UC を書いた機能設計書では、表の 1 列目の各行の先頭に `UC-<n>: ` を付け、どの UC の受け入れ基準かを示す (例: `UC-003: （US-005）未ログインで保存を押すと、ログイン画面へ移る`)。受け入れ基準の文面と照合するときは、この `UC-<n>: ` を除いた残りを比べる。`E2E 対象動線:` 行も表の行をそのまま (`UC-<n>: ` ごと) 再掲する。「対象 UC」が 1 件の機能設計書では付けない

- **UC の受け入れ基準を機能設計書に配る**: 1 つの UC を複数の機能設計書で分けるときは、UC の各行をちょうど 1 つの機能設計書に割り当てる (二重にも漏れにもしない)。担う行が 1 つも無い機能設計書は、表の代わりに「受け入れ基準の割り当てなし (<理由>)」と書く (例: 受け入れ基準が 1 行しかない UC を画面と API の 2 本に分けたとき、行は画面側に置き、API 側は「割り当てなし (画面側の E2E が API を通して検証する)」とする)
- **E2E は golden path の流れごとに 1 本**: レベルを E2E にするのは、壊れたら業務に致命傷になる流れ (golden path) の行だけにする。1 つの機能設計書が golden path を複数持つときは (例: 登録の流れと、別の画面への反映の流れ)、流れごとに 1 行を E2E にする。E2E にした行は、1 行ずつ表の外の `E2E 対象動線:` 行にもう一度書く (テストピラミッド。implementer と review-impl は E2E の対象を、/dev-impl の動作確認の証跡はスクリーンショットを撮る流れを、この行から読む)。書き忘れると、その流れの E2E が書かれず、PR の動作確認のスクリーンショットにも載らない。表の行とこの行は同じ行の再掲で、二重の割り当てではない。同じ流れをなぞる E2E の行を 2 つにしない (前提の状態が要るなら前提データで作る。`~/.claude/guidelines/core/testing.md`「E2E で確かめること」)。UI が無い機能 (cli モードを含む) は E2E を使わず、`E2E 対象動線:` 行を省く。UI 系の機能で E2E にする行が無いときは、行を省かずに `E2E 対象動線: なし (<理由>)` と書く (省くと、review-impl が書き忘れと区別できず設計の差し戻しとして報告する)。操作をせずに画面を開いて表示が出ることだけを述べる行は E2E にしない (理由と例は `~/.claude/guidelines/core/testing.md`「テストを書くかを先に決める」)。E2E にする行は、「どうなるか」に層をまたぐ結果 (画面の遷移・届いたメール・別の画面への反映) を含む行から選ぶ。表示の文言だけで結果を述べる行は、レベルを単体にする。選んだ行が文言を含むときの、E2E と画面の単体テストの分担は `~/.claude/guidelines/core/testing.md`「E2E で確かめること」に従う
- **エッジケースの観点リスト** (書くときに一巡すること): 空・最小データ / 上限・境界値 (件数・長さ・日付・数値の端) / エラー時に利用者へ見えるもの (未認証・失敗応答) / 並行操作・二重実行 (往復中の別操作、二重送信) / 再表示時の整合 (他画面から戻ったとき何を根拠に最新になるか)。観点ごとに、該当するなら決定を書き、検討して該当しないと判断したら「該当なし (<理由>)」を残す (例: `並行操作: 該当なし (読み取り専用で状態を変えない)`)。何も書かない観点を残さない — 検討したのか忘れたのかを、読み手が区別できないため
- **決めが要る点はその場で聞く**: プロダクト判断 (仕様の決め) が必要になったら、書き終えてからまとめて聞くのではなく、その場でユーザーに確認して決定を書き込む。変更コストの高い決定 (データの持ち方・API の外部契約・削除の扱い) を優先し、数時間で直せる細部 (UI 文言・並び順) は書き手が決めて明記する
- **横断事項を書かない**: テーブル定義・API 共通規約・エラー形式・認証は docs/design/DESIGN.md が正本。ここに重複させると改訂時に食い違う。本機能からの参照は「DESIGN.md「<節名>」参照」と書く
- **技術検証待ちの未確定要素**は `<!-- POC_NEEDED: id=<id>, scope=<検証対象>, risk=<high|medium|low>, blocker=<true|false> -->` マーカーで残す。書式・差し戻し・解決時の除去の規定は design-doc.md の記入基準と共通である: 機能単体の契約に属する未検証の `blocker=false` の PoC 計画は、上の「入力と転記」の転記規則でここに置き、設計中に blocker=true 相当の不確実性が見つかったらマーカーを `blocker=true` で残して dev-spec のフェーズ 5 へ差し戻し、解決後に本フェーズへ戻って結果を反映しマーカーを除去する。dev-impl は開始時に blocker=true の残存を検査する

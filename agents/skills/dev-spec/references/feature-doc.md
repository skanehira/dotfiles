# 機能設計書 (docs/design/features/) の書き方 (dev-spec フェーズ 7)

- 種別: テンプレート + 記入基準
- 生成者: dev-spec フェーズ 7。更新者: dev-impl (実装詳細レベルの乖離補正のみ。契約レベルは人間にエスカレーション)
- 消費者: issue の `## 設計` 節から参照される / dev-impl の implementer・review-impl が実装と突合する / 人間・AI が「この機能の設計はどうなっているか」をローカルで引く

## 単位と命名

**1 機能 = 1 ファイル、機能名で命名する** (例: `docs/design/features/export.md`、`docs/design/features/tag-search.md`)。UC 番号では命名しない — 人間にも AI にも機能名の方が引きやすい (`rg export docs/` で当たる)。UC との対応は冒頭メタ情報の 1 行で保つ。複数 issue が同じ機能設計書を参照してよい。

機能の切り方は UC を出発点にする (1 UC = 1〜2 機能が目安)。UC を持たない構成 (クイックモード) ではタスク説明から機能を切り出す。

| --- | --- | --- |

| 受け入れ基準 (docs/design/USECASES.md) | レベル |
| --- | --- |
| （US-<番号>）<受け入れ基準の 1 行をそのまま> | 単体 / 結合 / E2E |

## 記入基準

- **テスト方針は受け入れ基準から起こす**: 表の 1 行が、実装時にテストで pin する 1 つの振る舞いになる。implementer は表の行を割り当てたレベルのテストで pin し、review-impl は各行にテストがあるかを検査する。行の起こし方は「対象 UC」で分かれる

  | 「対象 UC」 | 表の 1 列目 | 書き方 |
  | --- | --- | --- |
  | UC 番号を書いた | `受け入れ基準 (docs/design/USECASES.md)` | その UC の受け入れ基準のうち、この機能が担う行を文面そのままで写す。接頭辞 `（US-<番号>）` が無い構成 (USER_STORIES.md を作らなかった場合) は接頭辞なしで写す |
  | なし (基盤系・クイックモード) | `確かめること (タスク説明から起こした)` | タスク説明から、受け入れ基準と同じ「どんなときに、何をすると、どうなるか」の 1 文を起こす。接頭辞は付けない |

- **UC の受け入れ基準を機能設計書に配る**: 1 つの UC を複数の機能設計書で分けるときは、UC の各行をちょうど 1 つの機能設計書に割り当てる (二重にも漏れにもしない)。担う行が 1 つも無い機能設計書は、表の代わりに「受け入れ基準の割り当てなし (<理由>)」と書く (例: 受け入れ基準が 1 行しかない UC を画面と API の 2 本に分けたとき、行は画面側に置き、API 側は「割り当てなし (画面側の E2E が API を通して検証する)」とする)
- **E2E は 1 本だけ**: レベルを E2E にするのは golden path の 1 行だけで、その行を表の外の `E2E 対象動線:` 行にもう一度書く (テストピラミッド。implementer と review-impl は E2E の対象をこの行から読む)。表の行とこの行は同じ行の再掲で、二重の割り当てではない。UI が無い機能 (cli モードを含む) は E2E を使わず、`E2E 対象動線:` 行を省く
- **エッジケースの観点リスト** (書くときに一巡すること): 空・最小データ / 上限・境界値 (件数・長さ・日付・数値の端) / エラー時に利用者へ見えるもの (未認証・失敗応答) / 並行操作・二重実行 (往復中の別操作、二重送信) / 再表示時の整合 (他画面から戻ったとき何を根拠に最新になるか)。該当するものだけ決定を書き、書かなかった観点は「検討して該当なし」とみなされる — 迷ったら「該当なし (<理由>)」を残す
- **決めが要る点はその場で聞く**: プロダクト判断 (仕様の決め) が必要になったら、書き終えてからまとめて聞くのではなく、その場で AskUserQuestion で確認して決定を書き込む。変更コストの高い決定 (データの持ち方・API の外部契約・削除の扱い) を優先し、数時間で直せる細部 (UI 文言・並び順) は書き手が決めて明記する
- **横断事項を書かない**: テーブル定義・API 共通規約・エラー形式・認証は docs/design/DESIGN.md が正本。ここに重複させると改訂時に食い違う。本機能からの参照は「DESIGN.md「<節名>」参照」と書く
- **技術検証待ちの未確定要素**は `<!-- POC_NEEDED: id=<id>, scope=<検証対象>, risk=<high|medium|low>, blocker=<true|false> -->` マーカーで残す (書式・解決時の除去規定とも docs/design/DESIGN.md = design-doc.md の記入基準と共通。dev-impl が開始時に blocker=true の残存を検査する)

# 機能設計書 (docs/design/features/) の書き方 (dev-spec のフェーズ 7)

- 種別: テンプレート + 記入基準
- 生成者: dev-spec のフェーズ 7。更新者: dev-impl (実装詳細レベルの乖離補正のみ。契約レベルは人間にエスカレーション)
- 消費者: 「何を作るか」は人が機能の概要を知るために読む。ほかの節は issue の `## 設計` 節から参照される / dev-impl の implementer・review-impl が実装と突合する / AI が「この機能の設計はどうなっているか」をローカルで引く

## 単位と命名

**1 機能 = 1 ファイル、機能名で命名する** (例: `docs/design/features/export.md`、`docs/design/features/tag-search.md`)。UC 番号では命名しない — 人間にも AI にも機能名の方が引きやすい (`rg export docs/` で当たる)。UC との対応は冒頭メタ情報の 1 行で保つ。複数 issue が同じ機能設計書を参照してよい。

機能の切り方は UC を出発点にする (1 UC = 1〜2 機能が目安)。UC を持たない構成 (クイックモード) ではタスク説明から機能を切り出す。

## 入力と転記

書き始める前に次を Read する。無いものは飛ばす。

| 入力 | 生成者 | 使い方 |
| --- | --- | --- |
| `docs/design/USECASES.md` | dev-spec のフェーズ 2 | 機能の切り方と「対象 UC」を決め、受け入れ基準を「テスト方針」の表へ写す |
| `docs/design/DESIGN.md` | dev-spec のフェーズ 6 | 横断事項 (スキーマ・API 規約・認証・横断規約) を参照する。ここに書かれたものは重複させない |
| `docs/design/FEASIBILITY.md` | dev-spec のフェーズ 4・5 | 下の転記規則で `POC_NEEDED` マーカーを置く |
| `docs/design/UI_SKETCH.html` | dev-spec のフェーズ 3 (webapp のみ) | UI 系の機能の「入出力と振る舞い」で該当画面を参照する |

転記規則: FEASIBILITY.md の PoC 計画のうち、POC_STATUS が `status=unresolved` かつ `blocker=false` で、機能単体の契約に属するものを、その機能の機能設計書に `POC_NEEDED` マーカーとして置く (design-doc.md「入力と転記」の規則 3 のうち本フェーズが受け持つ分)。置く前に `rg -n 'POC_NEEDED: id=<id>,' docs/design/` で同じ id が DESIGN.md や他の機能設計書に置かれていないことを確かめ、既にあれば置かない (二重に置くと、2 つの子 issue の DoD に同じ検証が載る)。

## 共有の契約と書く順

ほかの機能設計書が前提にする契約は、1 か所にだけ書く。そして、その契約を持つ文書を先に書き終えてから、残りの機能設計書を書く。

共有の契約とは、2 本以上の機能設計書が同じ前提で書く必要のある決定である。例は、プロセスの間でやりとりする操作、記録するイベントの形、列ごとの書き手、複数の機能が使う部品とその実装先ファイルである。

| 共有の契約の種類 | 置き場 |
| --- | --- |
| 横断事項 (スキーマ・API 規約・エラー形式・認証・横断規約) | DESIGN.md (`design-doc.md`) |
| 1 本の機能として書ける量のもの (例: プロセスの間のやりとり、会話の記録と配信) | それを担う機能設計書。「対象 UC」は「なし (タスク説明から起こした)」にする |

- **写さずに参照する**: ほかの機能設計書は、共有の契約を「features/<名前>.md「<節名>」参照」と書いて参照する。自分の機能に要る部分だけを要約して写すこともしない。写した文は正本を直しても追随せず、食い違いになる
- **共有の契約を持つ機能設計書を先に書く**: これを先に書き終え、残りはそれを Read してから書く。残りの機能設計書を subagent に分けて並列で書いてよいのは、この後だけである。残りの書き手が共有の契約を変えたくなったときは、自分で直さずに報告させ、親が直す
- **理由**: 共有の契約と、それを使う機能設計書を同時に書くと、使う側は契約を読めないまま、それぞれの前提で書く。前提のずれは書き手が自覚していないことが多く、後から書き手に前提を報告させて突き合わせても残る
- **採らなかった案**: 全部を並列で書き、後で突き合わせる (自覚していない前提のずれが残り、フェーズ 8 の high になる)。共有の契約をすべて DESIGN.md に置く (機能 1 本分の量の契約もあり、DESIGN.md が横断事項の一覧として読めなくなる)

## 記入基準

- **「何を作るか」は人が読む節、ほかの節は実装する AI が読む契約である**: 「何を作るか」だけを読んだ人が、その機能の概要をつかめるように書く。上限は 40 行 (空行を除く)・合計 4,000 バイト・1 行 450 バイト (日本語 1 字は 3 バイト。リンクの先は数えない) で、実装の語 (バッククォートで書く名前・パス) を書かない。流れ・決まりのうち要らないものは省き、種類や状態を比べるときは表を使ってよい。契約を変えたときは、この節に足すのではなく、いまの仕様の概要として書き直す。概要に要らない変更なら、この節は変えない。例外を落として言い切らない (`overview-doc.md` の記入基準と共通)。契約の文 (どの文書が正本か、判定の式、拒否のコードなど) はほかの節に書く
- **「変更履歴」のコメントを書かない**: git の履歴と PR が持つ
- **テスト方針は受け入れ基準から起こす**: 表の 1 行が、実装時にテストで pin する 1 つの振る舞いになる。implementer は表の行を割り当てたレベルのテストで pin し、review-impl は各行にテストがあるかを検査する。レベルを選ぶ前に、行ごとに `~/.claude/guidelines/core/testing.md`「テストを書くかを先に決める」でテストの要否を決める。テストしない行はレベルに `なし (<理由>)` と書き、implementer はその行のテストを書かない (review-impl は理由が同節の 2 つの軸に沿っているかを見る)。行の起こし方は「対象 UC」で分かれる

  | 「対象 UC」 | 表の 1 列目 | 書き方 |
  | --- | --- | --- |
  | UC 番号を書いた | `受け入れ基準 (docs/design/USECASES.md)` | その UC の受け入れ基準のうち、この機能が担う行を文面そのままで写す。接頭辞 `（US-<番号>）` が無い構成 (USER_STORIES.md を作らなかった場合) は接頭辞なしで写す |
  | なし (基盤系・クイックモード) | `確かめること (タスク説明から起こした)` | タスク説明から、受け入れ基準と同じ「どんなときに、何をすると、どうなるか」の 1 文を起こす。接頭辞は付けない |

  「対象 UC」に複数の UC を書いた機能設計書では、表の 1 列目の各行の先頭に `UC-<n>: ` を付け、どの UC の受け入れ基準かを示す (例: `UC-003: （US-005）未ログインで保存を押すと、ログイン画面へ移る`)。受け入れ基準の文面と照合するときは、この `UC-<n>: ` を除いた残りを比べる。`E2E 対象動線:` 行も表の行をそのまま (`UC-<n>: ` ごと) 再掲する。「対象 UC」が 1 件の機能設計書では付けない

- **表の外の箇条書きは 3 つに限る**: 書いてよいのは、テストの前提・E2E の流れ・仕様の表を 1 行ずつ確かめる指示である。前提とは、偽物に差し替えるもの・本物を使うもの・前提データ・時計の差し替えである。例は「結合は本物の SQLite と Agent SDK の偽物で確かめる」である。仕様の表を 1 行ずつ確かめてよいのは、表の行がそれぞれ別の同値クラスだからである。次の 2 つの形は書かない。1 つは、同じ振る舞いを複数のレベルで確かめる指示である (例: 「単体と結合の両方で固定する」)。もう 1 つは、入力を掛け合わせる指示である (例: 「条件表の各行を 8 種類の由来すべてで確かめる」)。何件・どのレベルで確かめるかは、実装のときに `~/.claude/guidelines/core/testing.md`「テストの数を決める」で決まる。2 つの形の指示を書くと、実装者がその指示に従って重複したテストを書く
- **UC の受け入れ基準を機能設計書に配る**: 1 つの UC を複数の機能設計書で分けるときは、UC の各行をちょうど 1 つの機能設計書に割り当てる (二重にも漏れにもしない)。担う行が 1 つも無い機能設計書は、表の代わりに「受け入れ基準の割り当てなし (<理由>)」と書く (例: 受け入れ基準が 1 行しかない UC を画面と API の 2 本に分けたとき、行は画面側に置き、API 側は「割り当てなし (画面側の E2E が API を通して検証する)」とする)
- **E2E は golden path の流れごとに 1 本**: レベルを E2E にするのは、壊れたら業務に致命傷になる流れ (golden path) の行だけにする。1 つの機能設計書が golden path を複数持つときは (例: 登録の流れと、別の画面への反映の流れ)、流れごとに 1 行を E2E にする。E2E にした行は、1 行ずつ表の外の `E2E 対象動線:` 行にもう一度書く (テストピラミッド。implementer と review-impl は E2E の対象を、/dev-impl の動作確認の証跡はスクリーンショットを撮る流れを、この行から読む)。書き忘れると、その流れの E2E が書かれず、PR の動作確認のスクリーンショットにも載らない。表の行とこの行は同じ行の再掲で、二重の割り当てではない。同じ流れをなぞる E2E の行を 2 つにしない (前提の状態が要るなら前提データで作る。`~/.claude/guidelines/core/testing.md`「E2E で確かめること」)。UI が無い機能 (cli モードを含む) は E2E を使わず、`E2E 対象動線:` 行を省く。UI 系の機能で E2E にする行が無いときは、行を省かずに `E2E 対象動線: なし (<理由>)` と書く (省くと、review-impl が書き忘れと区別できず設計の差し戻しとして報告する)。操作をせずに画面を開いて表示が出ることだけを述べる行は E2E にしない (理由と例は `~/.claude/guidelines/core/testing.md`「テストを書くかを先に決める」)。E2E にする行は、「どうなるか」に層をまたぐ結果 (画面の遷移・届いたメール・別の画面への反映) を含む行から選ぶ。表示の文言だけで結果を述べる行は、レベルを単体にする。選んだ行が文言を含むときの、E2E と画面の単体テストの分担は `~/.claude/guidelines/core/testing.md`「E2E で確かめること」に従う
- **エッジケースの観点リスト**: 書くときに、次の 11 個の観点を一巡する。観点ごとに、該当するなら決定を書き、検討して該当しないと判断したら「該当なし (<理由>)」を残す (例: `並行操作: 該当なし (読み取り専用で状態を変えない)`)。何も書かない観点を残さない。検討したのか忘れたのかを、読み手が区別できないためである。6 番以降は `behavior-policy.md`「挙動の観点」の観点で、例は同節にある
  1. 空・最小データ
  2. 上限・境界値 (件数・長さ・日付・数値の端)
  3. エラー時に利用者へ見えるもの (未認証・失敗応答)
  4. 並行操作・二重実行 (往復中の別操作、二重送信)
  5. 再表示時の整合 (他画面から戻ったとき何を根拠に最新になるか)
  6. 表示の寿命 (印・お知らせ・区切りがいつ消えるか)
  7. 送る前のデータ (下書き・選択中の項目をどこに置き、いつまで残すか)
  8. 状態の移り変わり (移るきっかけと移った先)
  9. 自動で進むこと (利用者の操作なしに実行する再試行・再開・送信)
  10. 端末と画面をまたぐこと (何を共有し、何を端末ごとに持つか)
  11. 並びと数え方 (並び順、件数、経過時間の起点)
- **細部は方針から導き、聞くものを絞る**: エッジケースの決定は、DESIGN.md「横断規約」の挙動の方針の項から導く。ユーザーに聞くのは 2 種類だけにする。どの方針からも決まらず、後から変えると作り直しが大きいもの (データの持ち方・API の外部契約・削除の扱い) と、書き手に決める権限が無いものである。基準と決める順は `behavior-policy.md`「細部を決める」にある。挙動の方針の項が無いプロジェクトでは、同節の決める順の 2 と 3 で決める。聞くと決めた点は、書き終えてからまとめて聞くのではなく、その場で確認して決定を書き込む。それ以外は書き手が決めて明記する。そのうち利用者から見える違いを生むものは、同「確認点」の形で、このフェーズの完了報告に並べる
- **横断事項と共有の契約を写さない**: テーブル定義・API 共通規約・エラー形式・認証は docs/design/DESIGN.md が正本。ほかの機能設計書が持つ共有の契約は、その機能設計書が正本 (上の「共有の契約と書く順」)。ここに重複させると改訂時に食い違う。本機能からの参照は「DESIGN.md「<節名>」参照」「features/<名前>.md「<節名>」参照」と書く
- **実装先ファイルの作り手を 1 本に決める**: 「実装の配置」の「作る / 足す」の列には、そのファイルを新しく作るなら「作る」と書く。ほかの機能設計書が作るファイルか、リポジトリに既にあるファイルに処理を加えるなら「足す」と書く。1 つのファイルを「作る」と書くのは 1 本の機能設計書だけにする。共有の契約に含まれる部品は、その契約を持つ機能設計書が作る。それ以外のファイルを複数の機能が使うときは、最初に要る機能の機能設計書が作る。「実装先ファイル」のセルには、リポジトリの最上位からのファイルのパスだけをバッククォートで囲んで書く (例: `` `src/server/git-cli.ts` ``)。1 つのセルに複数のパスを書いてよい。最上位に新しく作るファイルは `` `./vite.config.ts` `` のように `./` を付ける。関数名と補足は、バッククォートで囲まずに「処理」列に書く。ディレクトリやファイル名だけの略記は書かない。`placement-check.sh` は、作る機能設計書が 2 本以上あるファイルと、どこにも無いファイル、この書き方に合わないセルを挙げる。作り手が 2 つあると、issue に落としたときに 2 件の子が同じファイルを作り、作り手が無いと、どの子も作らない
- **技術検証待ちの未確定要素**は `<!-- POC_NEEDED: id=<id>, scope=<検証対象>, risk=<high|medium|low>, blocker=<true|false> -->` マーカーで残す。書式・差し戻し・解決時の除去の規定は design-doc.md の記入基準と共通である: 機能単体の契約に属する未検証の `blocker=false` の PoC 計画は、上の「入力と転記」の転記規則でここに置き、設計中に blocker=true 相当の不確実性が見つかったらマーカーを `blocker=true` で残して dev-spec のフェーズ 5 へ差し戻し、解決後に本フェーズへ戻って結果を反映しマーカーを除去する。dev-impl は開始時に blocker=true の残存を検査する

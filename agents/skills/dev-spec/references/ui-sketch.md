## 概要

dev-spec のフェーズ 3 で使う手順書。ユースケース記述 (dev-spec のフェーズ 2) のあとに行い、USECASES.md のフローを画面に写す。画面の流れをユースケースより先に決めない。ユースケースが無いまま画面を作ると、利用者の行動の流れを画面の側で推測することになり、触ってからの手戻りが大きい。本書の「手順 N」は本書の中の段階で、SKILL.md のフェーズ番号とは別である。dev-spec のフェーズを指すときは「dev-spec のフェーズ N」と書く。

**cli モードでは本フェーズは実行しない** (dev-spec/SKILL.md フェーズ一覧の cli モード列を参照)。CLI インターフェース仕様は dev-spec のフェーズ 6 が DESIGN.md の「CLI インターフェース」節で設計する (節の中身は `design-doc.md` のテンプレート)。

対話を通じてUIの方向性を整理し、成果物を **単一の `docs/design/UI_SKETCH.html` に集約**する。
この HTML 1ファイルに以下をすべて含める：
1. 画面一覧
2. ユーザーフロー図（HTML/SVG/CSS で描画。**Mermaid は使わない**）
3. クリッカブルなインタラクティブプロトタイプ（React + Tailwind CSS / CDN）
4. 各画面の要素・インタラクション

> **ASCII アートも別 Markdown（UI_SKETCH.md）も作らない。** 成果物は操作できる HTML 1ファイルに統一する。
> ASCII は全角・罫線（East Asian Width が曖昧幅）の表示幅差で崩れ、
> Mermaid/Markdown はプロトタイプとの二重管理になるため。

## ワークフロー

### 手順 1: コンテキストの確認

対象プロダクトと既存ドキュメントを確認する。

#### 1.1 前提ドキュメントの読み込み

次のファイルを読む:

- `docs/design/USER_STORIES.md`
- `docs/design/USECASES.md`
- `docs/PRODUCT_SPEC.md`

#### 1.2 コンテキストの活用

**ファイルが存在する場合**:
- USER_STORIES.md: ユーザーが行いたい操作を把握
- USECASES.md: 画面とフローの元。各ユースケースの正常系・代替・例外フローのステップから、必要な画面と画面遷移を起こす
- PRODUCT_SPEC.md: プロダクトのスコープを把握

これらの情報を元に、必要な画面を効率的に洗い出す。

**遷移条件**: 手順 2へ

**ファイルが存在しない場合**:
対象プロダクトをユーザーに確認する。

「どのプロダクト/機能のUIをスケッチしますか？」と聞き、自由入力で答えてもらう (目安: 対象のプロダクトや機能領域)。

**遷移条件**: コンテキストが把握できたら手順 2へ

### 手順 2: 画面の洗い出し

必要な画面を特定する。USECASES.md があるときは、各ユースケースのフローのステップを順にたどり、利用者が何かを見る・操作する箇所ごとに画面の案を作る。案を「画面 ← 使うユースケース」の対応で先に示し (例: `issue の一覧 ← UC-001, UC-007`)、過不足だけを聞く。どのユースケースにも使われない画面は作らない。下の質問は、USECASES.md が無いときと、案に漏れが無いかを確かめるときに使う。

**質問パターン**:
- 「ユーザーが最初に見る画面は？」
- 「主要な操作をする画面は？」
- 「設定や管理をする画面は？」
- 「エラーや確認のための画面は？」

「このプロダクトに必要な画面をすべて挙げてください」と聞き、自由入力で答えてもらう (例: ログイン、ダッシュボード、SQL入力、結果表示)。

#### 画面の分類

| 種類           | 説明                               | 例             |
| -------------- | ---------------------------------- | -------------- |
| **認証系**     | ログイン、登録、パスワードリセット | ログイン画面   |
| **メイン機能** | コア機能を実行する                 | SQL入力画面    |
| **結果表示**   | 処理結果を表示                     | 改善案一覧     |
| **設定系**     | ユーザー設定、プロフィール         | アカウント設定 |
| **管理系**     | 管理者向け                         | ユーザー管理   |
| **補助系**     | ヘルプ、エラー                     | 404ページ      |

**遷移条件**: 主要な画面が5-15個出たら手順 3へ

### 手順 3: ユーザーフローの整理

画面間の遷移を整理する。USECASES.md があるときは、ユースケース 1 件につき 1 つのフローとし、正常系・代替・例外フローのステップを画面遷移に写す。写した案を先に示し、下の質問は確認にだけ使う。

**質問パターン**:
- 「この画面から次にどこへ行けますか？」
- 「この操作が成功したらどの画面に遷移しますか？」
- 「エラーの場合はどうなりますか？」

次のように聞き、自由入力で答えてもらう (目安: 画面A → 画面B → 画面C)。

```
主要なユーザーフロー（画面遷移）を教えてください

例: ログイン → ダッシュボード → SQL入力 → 結果表示
```

#### フローの整理

ここではフローを**言語化して整理するだけ**にとどめる。
図は Mermaid で描かず、手順 5で `UI_SKETCH.html` 内に HTML/SVG/CSS のフロー図として作成する。

整理の例（テキスト）:
- ログイン → ダッシュボード → SQL入力 →（分析）→ 成功: 結果表示 ／ 失敗: エラー表示 → SQL入力

**遷移条件**: 主要フローが整理できたら手順 4へ

### 手順 4: 各画面の要素整理

各画面に必要な要素を洗い出す。

「[画面名]に必要な要素は何ですか？」と聞き、自由入力で答えてもらう (例: 入力欄、ボタン、テーブル、グラフ)。

#### 要素の種類

| 種類               | 説明                                 | 例             |
| ------------------ | ------------------------------------ | -------------- |
| **入力**           | テキスト、セレクト、チェックボックス | SQL入力欄      |
| **アクション**     | ボタン、リンク                       | 「分析」ボタン |
| **表示**           | テキスト、テーブル、リスト           | 改善案リスト   |
| **ナビ**           | メニュー、タブ、パンくず             | サイドバー     |
| **フィードバック** | アラート、トースト、モーダル         | 成功メッセージ |

**遷移条件**: 主要画面の要素が整理できたら手順 4.5へ

### 手順 4.5: アプリシェル設計 (必須)

個別画面とは別軸で、**全画面共通の骨格 (アプリシェル)** を必ず設計する。手順 2で洗い出した個別画面に上から被さる「全画面横断のレイヤ」と捉える。

これを設計しないと、各 UC を実装する subagent が「自分の画面だけ作って横断的 UX を後回し」にする。過去の実測では、その結果トップナビ無し / ErrorBoundary 無し / 404 デッドループ / ログアウトボタン無しとなり、MVP が「ブラウザで開いたら使えない」状態になった。

#### 必須の決定項目

| 項目 | 決めること |
|---|---|
| **グローバルレイアウト** | ヘッダー (ブランド表示 / 主要ナビ / ユーザーメニュー / ログアウト) / トップナビ or サイドナビ / フッター。認証時 / 未認証時で表示を切り替えるか |
| **認証ガード** | 未認証ユーザーが認証必須ルートに来た時のリダイレクト先 (通常 `/login`)。リダイレクト後に元の URL に戻すか (`?next=...`) |
| **404 / 権限なし / ネットワークエラー** | 該当画面のレイアウト + 「ホームへ戻る」「再読み込み」など必須アクション。**404 を `/` に silent redirect しない** (デッドループの原因) |
| **グローバルトースト / 通知** | 成功 / エラー / 情報の 3 種別、表示位置、自動消滅秒数、複数同時表示の上限 |
| **ErrorBoundary 配置方針** | React render エラー時のフォールバック画面。ルート単位 / レイアウト単位 / 個別画面単位のどこに置くか。「ホワイトアウトを絶対に出さない」 |
| **共通 loading 表示** | Suspense 境界の位置、Skeleton vs Spinner の使い分け |

#### 質問パターン

「アプリ全体の骨格 (アプリシェル) を決めます。ヘッダー・ナビ・フッターはどんな構成にしますか?」と聞き、次の 3 択から 1 つだけ選ばせる。

| 選択肢 | 意味 |
| --- | --- |
| ヘッダー + サイドナビ | 管理画面・SaaS 系の定番。ヘッダーにブランドとユーザーメニュー、サイドに主要セクション |
| トップナビのみ | シンプルなプロダクト・ランディング系。ヘッダー一段に主要リンク |
| ヘッダー + フッター (ナビ無し) | シングルページ的・チュートリアル系 |

残りの項目も 1 問ずつ聞き、次の候補 (2〜3 個) だけを選択肢に並べて 1 つだけ選ばせる。「その他」は選択肢に足さない (選択式の質問が 3 択までのランタイムで 4 択になるため)。プロダクトに合う候補が無いとユーザーが答えたら、どうしたいかを通常のメッセージで入力してもらい、その内容を採る。

| 項目 | 候補 |
| --- | --- |
| 認証ガード | 未ログインは `/login` へ遷移し、ログイン後に `?next` で元の URL へ戻す / `/login` へ遷移するだけで元の URL へは戻さない / 認証不要 (全画面を公開) |
| 404 / 権限なし / ネットワークエラー | それぞれ専用画面を出し「ホームへ戻る」「再読み込み」を置く / アプリシェルの `<main>` 内にエラー表示を出し「ホームへ戻る」を置く |
| グローバルトースト | 右上に表示し、成功・情報は 4 秒で自動消滅、エラーは手動で閉じる、同時 3 件まで / 下中央に表示し、全種別 5 秒で自動消滅、同時 1 件 / トーストを使わず各画面のインライン表示だけにする |
| ErrorBoundary | ルート単位とレイアウト単位の 2 段に置く / ルート単位だけに置く / 個別画面ごとに置く |
| 共通 loading 表示 | Suspense 境界をレイアウト単位に置き、一覧は Skeleton・操作中は Spinner / 画面遷移ごとに全画面 Spinner |

#### UI_SKETCH.html への反映と後段への受け渡し

手順 5でプロトタイプ HTML を作る際、**全画面共通のレイアウトコンポーネント (AppShell)** として実装する。各個別画面はこの AppShell の `<main>` 部分に流し込まれる構造にする。404 / 認証ガード / ErrorBoundary のフォールバック画面もそれぞれプロトタイプ化する。

ここで決めた 6 項目は UI_SKETCH.html の中だけに留めない。dev-spec のフェーズ 6 が DESIGN.md「横断規約」のアプリシェルの項へ写し、同じ項に検証の対象 (「テスト方針」の表と `E2E 対象動線:` 行) を起こす (design-doc.md「入力と転記」の規則 4)。dev-spec のフェーズ 9 が AppShell の実装を、その項を「設計」節に書いた基盤親の子 issue として切る (issue-template.md「親 issue テンプレート」)。

**遷移条件**: 上記 6 項目が決まり、UI_SKETCH.html に反映できる粒度になったら手順 5へ

### 手順 5: インタラクティブプロトタイプ作成

ワイヤーフレームは「React + Tailwind CSS を CDN で読み込んだ単一 HTML の
クリッカブル・プロトタイプ」として作成する。ASCII アートは使わない。

**理由**:
- ASCII は全角／半角・罫線の表示幅差で崩れる（環境依存）
- 操作できるプロトタイプの方が画面遷移・フローが正確に伝わる
- React + Tailwind を CDN で使えば、本番実装（React + Tailwind）へそのまま流用できる

手順 5 は次の順に進める。

| 段階 | すること |
| --- | --- |
| 5.0 | 既存の UI 語彙の取り込み |
| 5.1 | 骨組みの作成 |
| 5.2 | 方向性を代表画面で決める |
| 5.3 | frontend-design による作り込み |
| 5.4 | 自分で確かめる (撮影と操作) |
| 5.5 | 別のコンテキストの批評 |
| 5.6 | ユーザーの確認 |

ユーザーに渡すのは 5.6 で、5.4 と 5.5 を通る前のスケッチは渡さない。ユーザーの指摘は、欠陥ではなく好みと使い心地の判断に使う。作り込みの土台になる `docs/design/UI_SKETCH.html` は 5.1 で作る。

#### 5.0 既存の UI 語彙の取り込み（着手前・必須／既存プロジェクトのみ）

**「そのまま流用できる」は、スケッチと実装が同じ語彙で書かれている場合にだけ成り立つ。**
実装者はスケッチを**逐語で写す**ため、同じ名前で違う値を定義すると、構造だけ正しく写って
見た目が壊れる。

既にコードがあるプロジェクトでは、着手前に次を行う:

1. **既存の UI 語彙を Read する**（`src/**/ui-primitives.tsx` / `components/ui/*` /
   `theme.ts` / `tailwind.config.*` / semantic トークンを定義する CSS など。
   `rg -l 'inputCls|buttonCls|const Button' src` で探す）
2. **スケッチのクラス定義は、そこから写す。名前も値も揃える。**
   `inputCls` は `inputCls` のまま同じ文字列にする
3. **同じ名前で違う値を定義しない。** 名前が同じで中身が違うのが最悪で、実装者は正しく
   写したつもりで壊す
4. 語彙に無い見た目が要るときは、スケッチで新設したうえで
   **「実装時にプリミティブへ昇格させる」** をスケッチ内のコメントに残す

> 過去の実例: スケッチの `inputCls` は `w-full` を持ち、実装の `inputCls` は持たなかった。
> `<label>` の中でラベル文字と `<select>` を並べる同じ JSX でも、幅があれば必ず折り返して
> ラベルが上に載り、無ければ内容幅になって**選択肢の文言の長さで見え方が決まる**。
> 絞り込み行の 1 つだけがずれて見え、原因の特定に時間がかかった。
> 同様に `Btn` の `ghost` はスケッチが「枠つき」、実装が「枠なし・透明」で**意味が逆**だった。

新規プロジェクト（コードがまだ無い）では 5.0 を飛ばし、スケッチで定義した語彙を
**実装時にプリミティブへ移す**前提で進める。

#### 5.1 骨組みの作成

手順 2〜4.5 で整理した内容から、`docs/design/UI_SKETCH.html` の骨組みを書き出す。この段階ではビジュアルを作り込まず、構造とフローが操作で確かめられる状態にする。配色・フォント・影・角丸は指定せず、Tailwind の既定 (グレーと system フォント) のままにする。骨組みの段階で見た目まで整えると、5.3 の作り込みが要らないように見えてしまうため。UI_SKETCH.html が既にある (途中で中断したフェーズを再開した) ときは上書きせず、既存の骨組みに足りない部分を足す。

- **単一 HTML ファイル `docs/design/UI_SKETCH.html`** に設計書のすべてを集約・自己完結させる
- **React 19 + Tailwind CSS を CDN で読み込む**
  - React 19 は UMD ビルドを廃止しているため、`importmap` + `esm.sh`（ESM）で読み込む
  - JSX は Babel standalone（`<script type="text/babel" data-type="module">`）で変換、Tailwind は Play CDN
- **次のセクション（タブ/ページ）をHTML内に持たせる**:
  - 概要: 画面一覧テーブル
  - ユーザーフロー図: 画面遷移の俯瞰図を HTML/SVG/CSS で描く（**Mermaid 不使用**）
  - 各フローのクリッカブルプロトタイプ: 画面内のボタンで実際に遷移する
  - 各画面の要素・インタラクション: プロトタイプ内の注釈、または一覧として併記
- 各フローに**説明文**（何のフローか・ステップ・関連 UC・関連 US）を併記する
- 全画面を手順 4.5 の AppShell の `<main>` に流し込む構造にし、404 / 認証ガード / ErrorBoundary のフォールバック画面も置く
- **どの画面も URL から直接開ける口を作る。** 口が無いと、全画面を撮ることも、再読み込みで同じ画面に戻ることもできない。次の 4 つを骨組みの段階で入れる
  1. `#screen=<画面 ID>` で開くと、その画面を描く
  2. 描いた画面を包む要素に `data-sketch-screen="<描いた画面の ID>"` を付ける (1 と 2 の書き方は `~/.claude/skills/dev-feat-spec/references/sketch-capture.md`「スケッチの口」)
  3. `window.SKETCH_SCREENS` に、全画面の ID の配列を入れる。スマートフォン向けの画面は `{ id: "<画面 ID>", width: 390 }` と書く。5.4 の撮影はこの配列を読む
  4. 画面を移るたびに `location.hash` を `#screen=<移った先の画面 ID>` に書き換える。再読み込みしても、見ていた画面に戻る
- **操作で出る状態も、画面 ID として持つ。** モーダルを開いた状態、エラーの出た状態、0 件の状態、入力の途中、右の補助ウィンドウを開いた状態などは、`<画面 ID>--<状態>` の画面として `SKETCH_SCREENS` に入れ、その状態を最初から描く。状態を持たない画面は、5.4 の撮影にも 5.5 の批評にも写らない。入力欄を開いた状態のように、フォーカスの位置で表示が変わる状態は、フォーカスもその状態に含めて描く

#### 5.2 方向性を代表画面で決める（作り込み前・必須）

ビジュアルを作り込む前に、方向性をユーザーと決める。言葉で聞くだけで終えず、代表の 1 画面を実際に描いて見せ、その 1 画面への指摘が出なくなってから全画面に広げる。全画面を作ってから方向の違いが分かると、全画面を直すことになる。

##### 言葉で聞く

次の 5 項目を、1 問ずつ選択式で聞く。プロダクトの文脈から推せる項目は、推した案を先頭に置く。

| 項目 | 候補の例 |
| --- | --- |
| トーン | 開発者向けの道具 / 国内向けのカジュアル / 外資系のラグジュアリー |
| 明るさ | ライト / ダーク / 両方 (OS に合わせる) |
| 密度 | 詰める (一覧の 1 行が 24〜32px) / 標準 (40px 前後) / ゆったり (56px 以上) |
| 主な入力手段 | マウス / キーボード / タッチ |
| 手本にしたい製品 | 1〜2 個を自由入力で聞く (例: Linear、GitHub、Neovim) |

主な入力手段がキーボードのときは、キーの割り当ての表 (キー・動作・使える場所) を先に作り、ユーザーに見せて合意する。割り当ては、手本の製品の慣習 (Vim、OS、ブラウザ) と衝突しないものを選び、衝突するものは理由を添える。

##### 代表画面を描いて選ぶ

1. 代表画面を 1 つ選ぶ。最もよく使う画面のうち、情報の多いもの (一覧、主要な作業の画面) にする
2. 聞いた方向性の中で振れ幅のある 2〜3 案を、実際の HTML で描く。画面 ID は `direction--a` / `direction--b` / `direction--c` とし、`SKETCH_SCREENS` に入れる。案は、密度・見出しの形・強弱の付け方のように、後から全画面に効く点で違いを付ける。色だけを変えた案は並べない
3. 5.4 の撮影のスクリプトで撮り、画像を Read で開いて、崩れが無いことを自分で確かめる
4. ユーザーにブラウザで開いてもらい、案を選ばせる。選んだ案に指摘があれば直し、指摘が出なくなるまで、この 1 画面だけを直す
5. 決まった値を「デザイン方針」(手順 7) の節に書く。書くのは、文字の大きさ、行の高さ、余白、配色、見出しと列の見出しの形、状態の色、ボタンの形である。残りの画面は、この値だけを使って作る
6. `direction--*` の画面を消し、選んだ案を代表画面として残す

> 方向性を言葉だけで決めて全画面を作り込むと、密度や見出しの形のような「見れば分かる」好みが、全画面ができてから指摘になる。
> 過去の実例では、一覧の行の高さ・列の見出し・見出しと本文の区別への指摘が、全画面を作った後に出て、全画面を直した。

ここで決めた方針は、次の 5.3 の作り込みの入力になる。

#### 5.3 frontend-design による作り込み（必須、skip 不可）

5.2 で方向性が決まったら、**必ず frontend-design スキルを起動して**ビジュアルを作り込む。「ジェネリック AI UI のまま終わらせない」ためのゲート。起動は下の「frontend-design の起動のしかた」に従う。

skip 選択肢は提供しない。過去に、このスキルを起動せずにジェネリックな UI のまま実装へ進んだことがある。プロダクトの規模や時間が限られていても、まず 1 周作り込むこと。ユーザーの指摘の反映は 5.6 で往復できる。

##### frontend-design の起動のしかた

- **対象**: dev-spec で UI_SKETCH.html を最初に作るときの作り込み (5.2 の代表画面と 5.3) と、その修正の往復 (5.4〜5.6)。途中で中断して再開した場合も、UI_SKETCH.html に下の痕跡の行が無ければ最初の作成として扱う。既に完成したスケッチ (完了の印 `<!-- ui-sketch: finalized -->` がある) に画面を足す・直すときは起動しない。既存の見た目と「デザイン方針」の節 (手順 7) に従って書く
- **起動するスキル**: Skill ツールで呼べるスキルの一覧のうち、名前が `frontend-design` で終わるもの (例: `frontend-design:frontend-design`)。短縮形 `frontend-design` が一覧にあればそちらでもよい。一覧に無い名前は Skill ツールで呼べないので、裸の `frontend-design` が無いからといって「見つからない」とは判断しない
- **起動のしかた**: Skill ツールで起動する。スキルの SKILL.md を Read して代えること、記憶にあるデザインの知識で代えることは起動に当たらない。frontend-design のガイダンスは、起動したときにだけコンテキストに入る。起動したあと `docs/design/UI_SKETCH.html` を編集するのは実行中のエージェント自身で、スキルがファイルを書き換えて結果を返すわけではない
- **痕跡**: 作り込みを終えたら、UI_SKETCH.html の `<head>` の中に `<!-- frontend-design: <起動したスキル名> -->` を 1 行書く (例: `<!-- frontend-design: frontend-design:frontend-design -->`)。手順 8 と dev-spec の再開判定がこの行を読む
- **見つからないとき**: 名前が `frontend-design` で終わるスキルが一覧に 1 つも無い環境もある (プラグインの導入に失敗したマシンなど)。そのときは作り込みを始めず、見つからないことをユーザーに伝え、「スキルを導入してから続ける / 別のデザインガイダンスを指定して作り込む」の 2 択から選ばせる。見つからないまま黙ってジェネリックな作り込みに進まない。後者を選んだときは、痕跡の行を `<!-- frontend-design: unavailable (<選んだガイダンス>) -->` とする

作り込みに入る前に、方向性を最終確認する。

「5.2 で合意した方向性 (<トーン / カラー / 雰囲気>) で作り込みます。最終確認: この方向性で進めて問題ないですか?」と聞き、次の 2 択から 1 つだけ選ばせる。

| 選択肢 | 意味 |
| --- | --- |
| 進める | 5.2 で合意した方向性で作り込む |
| 方向性を修正してから | 5.2 に戻って方向性を再ヒアリング |

「進める」が選ばれたら、「frontend-design の起動のしかた」に従って frontend-design スキルを起動し、そのガイダンスに従って次の要求どおりに `docs/design/UI_SKETCH.html` を自分で作り込む:

```
方向性 (5.2 でユーザーと合意):
- トーン: <例: 外資系ラグジュアリー / 国内カジュアル / 開発者向け>
- 雰囲気: <例: ミニマル / エディトリアル / ポップ>、ライト / ダーク
- 主要フォント候補: <例: Inter + Noto Sans JP / Geist / system-ui>
- 主要配色: <例: ニュートラル + 1 アクセントカラー (具体的な hex か Tailwind 名)>
- スペーシング: <例: 8px ベース / 詰め気味 / 余白広め>

要求:
- AppShell (ヘッダー / ナビ / フッター / 404 / トースト / ErrorBoundary フォールバック画面。手順 4.5 で設計済) すべてに方向性を反映する
- 各個別画面のプロトタイプにも方向性を反映する
- 5.1 で作った画面構造・フロー・要素は壊さない (構造維持 + ビジュアル適用)
- 単一 HTML ファイル (docs/design/UI_SKETCH.html) を直接上書きする
- 5.2 で決めた「デザイン方針」の値だけを使う。画面ごとに新しい大きさや余白を足さない
```

作り込みでは、次の形を全画面で守る。5.5 の批評が同じ点を見る (`sketch-critique.md`「見た目の観点」)。

- 列に並べた情報には列の見出しを付け、桁は空白の数ではなくレイアウトで揃える
- キーと説明、項目と値のような組は、1 行に 1 組だけ書く
- 見出しは、中身とはっきり違う見た目にする
- 状態・進み具合・選択の有無は、色・形・部品で表す。罫線の文字で描いた木や、`[x]` のような文字のままの部品を置かない
- 次にできる操作と、その方法 (ボタン、キー) を、その画面に出す
- 見本データは、同じ対象の名前・件数・状態を、全画面で一致させる

作り込みが終わったら、痕跡の行を書き、5.4 に進む。

#### 5.4 自分で確かめる（撮影と操作・必須）

ユーザーに渡す前に、描画結果を自分で見て、実際のブラウザで操作する。ここを飛ばすと、ユーザーが最初の検査者になり、押しても動かないキーや崩れた画面が、そのまま指摘になる。

1. **全画面を撮る。** ライトとダークの両方を持つスケッチは 2 回撮る

   ```bash
   ~/.claude/skills/dev-spec/scripts/sketch-shots.sh docs/design/UI_SKETCH.html <SCRATCH>/sketch-shots
   ~/.claude/skills/dev-spec/scripts/sketch-shots.sh docs/design/UI_SKETCH.html <SCRATCH>/sketch-shots --scheme dark
   ```

   終了コードが 0 でなければ、`FAIL <画面 ID>: <理由>` の行を直す。`page error` はスケッチの JavaScript かコンソールのエラー、`Timeout` は口が無いか、その画面 ID を描けていないことを示す。`Executable doesn't exist` が出たら `npx playwright@1.65.1 install chromium` を実行する
2. **撮った画像を全部 Read で開く。** 崩れ (重なり、はみ出し、切れ、桁のずれ) と、5.3 の「全画面で守る形」から外れた画面を直す
3. **主要フローを実際のブラウザで操作する。** 手順 3 で整理したフローごとに、開始から終了までを操作するスクリプトを `<SCRATCH>` に書いて実行する。入力・送信・選択・取り消し・戻るのように、状態を変える操作を必ず含める。主な入力手段がキーボードなら、キーだけで操作する。操作のたびに、画面に出るはずの文言を確かめる

   ```bash
   NODE_PATH="${XDG_CACHE_HOME:-$HOME/.cache}/dev-feat-spec/playwright/node_modules" node <SCRATCH>/sketch-check.cjs
   ```

   スクリプトは `require("playwright")` の `chromium` でスケッチを開き、`page.keyboard` と `page.getByRole` で操作する。jsdom のような代わりの環境では確かめない (フォーカス、縦の移動、IME のように、実際のブラウザでしか再現しない動きがある)
4. 直したら 1 から繰り返し、撮影が終了コード 0、画像に崩れなし、操作のスクリプトが全件通過、の 3 つが揃ったら 5.5 に進む

#### 5.5 別のコンテキストの批評（必須）

作ったエージェントは意図を知っているので、見出しの無い列や行き止まりの画面に気付かない。別のコンテキストの subagent に、スクリーンショットを見せて指摘させる。

1. `general-purpose` の subagent を **モデル: opus を明示**して、`~/.claude/skills/dev-spec/references/sketch-critique.md` の「担当」の数だけ並行で起動する。指示文には、同書を Read して従うこと、担当、同書の「入力」の 5 つ (スクリーンショットのディレクトリ、スケッチ、ユースケース、5.2 で合意した方向性、ユーザーが決めたこと) を書く。自分の考えた直し方や、気になっている点は書かない (批評が、渡した見立てをなぞるため)
2. 返った指摘のうち high をすべて直す。medium と low は直すかどうかを決め、直さないものは理由を控える。ユーザーの決定 (5.2 の合意、キーの割り当て) と食い違う指摘は採らない
3. 5.4 をやり直し、新しい subagent 1 本に、撮り直した画像で同じ手順書の全観点を見させる。前の批評の結果は渡さない
4. 2 周しても high が残ったら、残った指摘をユーザーに見せて扱いを決めてもらう

#### 5.6 ユーザーの確認

ここで初めてユーザーに渡す。ユーザーに頼むのは、好みと使い心地の判断である。欠陥は 5.4 と 5.5 で除いてある。

「docs/design/UI_SKETCH.html をブラウザで開いて、触ってみてください。直したい点はありますか?」と聞き、次の 2 択から 1 つだけ選ばせる。質問には、5.5 の指摘のうち直していないもの (あれば) と、自分で決めた点 (キーの割り当てなど) を 1 行ずつ添える。

| 選択肢 | 意味 |
| --- | --- |
| 直したい点なし | 次の手順へ進む |
| 直したい点あり | 具体的な内容を自由入力で受け取る |

**指摘は、言われた 1 か所だけでなく、同じ形の全箇所に当てる。** 「この一覧の行間が広い」は、すべての一覧の行間への指摘である。「この見出しが分かりづらい」は、すべての見出しへの指摘である。直したら「デザイン方針」の該当する値も書き換え、5.4 の撮影と操作をやり直してから、もう一度確認を頼む。指摘を受けた画面だけを直すと、同じ指摘が画面の数だけ繰り返される。

直したい点があれば frontend-design のガイダンスに沿って自分で反映し、再度ユーザーに確認を依頼する。直したい点なしになるまで繰り返す。このセッションでまだ frontend-design を起動していないときは、ガイダンスがコンテキストに無い。中断したフェーズを再開したときや、会話が要約されたときがこれに当たる。そのときは「frontend-design の起動のしかた」に従って起動してから反映する。

ユーザーの確認で流れそのものを変えることになったとき (ステップの追加・削除・順序の入れ替え、分岐や失敗時の扱いの変更) は、画面だけを直さない。先に USECASES.md の該当するフロー・ビジネスルール・受け入れ基準を直す。続けて usecase-description.md の手順 9 (書き戻しと被覆チェック) を実行し、そのあとでスケッチを直す。受け入れ基準は機能設計書のテスト方針と issue の元になるので、スケッチだけを直すと、実装が古い流れのまま進む。

**遷移条件**: 5.4 の撮影と操作が通り、5.5 の批評の high が解消し、ユーザーの確認で「直したい点なし」となり、流れの変更が USECASES.md に反映されたら手順 6へ

### 手順 6: インタラクションの整理

画面上のインタラクションを定義する。

「この画面でユーザーが行う主要な操作と、その結果を教えてください」と聞き、自由入力で答えてもらう (例: ボタンクリック → モーダル表示)。

#### インタラクション定義

| トリガー                  | アクション          | 結果                    |
| ------------------------- | ------------------- | ----------------------- |
| 「分析」ボタンクリック    | API呼び出し         | ローディング → 結果表示 |
| SQL入力欄フォーカスアウト | バリデーション      | エラー表示 or 正常      |
| 履歴項目クリック          | SQLを入力欄にロード | 入力欄が更新される      |

#### スケッチが決めた挙動の書き出し

スケッチを作る途中で、エージェントが USECASES.md に無い挙動を埋めていることがある。例は、「5 秒のあいだ取り消せる」という秒数、「時間が来たら自動で再開する」という自動の動き、割り込んだときに待たせていた入力を捨てるかどうかである。埋めたままにすると、スケッチとユースケースが食い違い、どちらが正しいかを誰も決めていない状態になる。

1. スケッチのソースと画面の文言を、[behavior-policy.md](behavior-policy.md)「挙動の観点」の 6 つの観点で一巡し、USECASES.md のフローにもビジネスルールにも無い挙動を洗い出す
2. 洗い出した挙動を、USECASES.md「挙動の方針」と照らす。方針から導ける挙動は、方針に合う形に直してから、該当するユースケースのビジネスルールに書く。方針と食い違うスケッチは、スケッチを直す
3. 方針から導けない挙動は、behavior-policy.md「細部を決める」に従って決め、ビジネスルールに書く。ユーザーに聞くのは、同節の表に当たるものだけにする
4. ビジネスルールを足したら、usecase-description.md の手順 9 (書き戻しと被覆チェック) を実行する
5. 決めた挙動を、behavior-policy.md「確認点」の形で、このフェーズの完了報告に並べる

**遷移条件**: 主要なインタラクションが定義でき、スケッチが決めた挙動が USECASES.md のビジネスルールに戻ったら手順 7へ

### 手順 7: UI_SKETCH.html への集約（最終化）

別 Markdown（`UI_SKETCH.md`）は作らない。手順 2〜6で整理した内容を
`docs/design/UI_SKETCH.html` の各セクションに反映し、**1ファイルで完結**させる。

最終的に HTML 内に含めるセクション:
- 画面一覧（テーブル）
- ユーザーフロー図（HTML/SVG/CSS。Mermaid 不使用）
- 各フローのクリッカブルプロトタイプ
- 各画面の要素・インタラクション
- アプリシェルの決定（手順 4.5 の 6 項目）
- デザイン方針（手順 5.2 で決めたトーン・フォント・配色・密度・主な入力手段と、代表画面で決めた文字の大きさ・行の高さ・余白・見出しの形）

### 手順 8: セルフレビュー（サブエージェント）

生成したドキュメントのレビューをサブエージェントに委譲する。

サブエージェント `general-purpose` を起動する (モデル: opus を明示)。

- 説明: `UI/UXスケッチレビュー`
- 次の指示文を渡す:

```
以下のUI/UXスケッチドキュメントをレビューし、問題があれば修正してください。

## レビュー対象ファイル
- docs/design/UI_SKETCH.html

## レビュー観点

1. **画面の網羅性**: 必要な画面がすべてリストアップされているか
2. **フローの完全性**: ユーザーフローに抜け漏れがないか
3. **プロトタイプの明確さ**: 各画面の要素が明確に配置され、フローが操作で遷移するか
4. **インタラクションの定義**: 主要な操作と結果が定義されているか
5. **一貫性**: 画面間でUI要素やナビゲーションが一貫しているか
6. **撮影できること**: `~/.claude/skills/dev-spec/scripts/sketch-shots.sh docs/design/UI_SKETCH.html <一時ディレクトリ>` が終了コード 0 で終わるか
   (全画面を口から開け、ページのエラーが無い)。見た目と使い勝手は手順 5.5 の批評が見るので、ここでは判定しない
7. **既存語彙との一致**（既存プロジェクトのみ / 手順 5.0 の確認）:
   スケッチのクラス定義が実装の UI 語彙と**名前も値も一致**しているか。
   とくに**同じ名前で違う値**になっていないか（実装者は逐語で写すため、これが最も壊れる）。
   確認は目視ではなく、両者の定義を取り出して**文字列比較**する
8. **作り込みの痕跡と反映**: `<head>` の中に `<!-- frontend-design: ` で始まる行があるか。
   「デザイン方針」の節の配色とフォントが全画面に出ているか。Tailwind の既定 (グレーと system フォント) の
   骨組みのままの画面が残っていないか。この観点の問題は修正せず、「残った問題」として返す
   (痕跡の行を書き足すと、作り込みを飛ばしたことが分からなくなるため)

9. **ユースケースの走破**: docs/design/USECASES.md を Read し、各ユースケースの正常系・代替・例外フローの
   全ステップを、プロトタイプの画面と操作で最後までたどれるか。たどれないステップ、ユースケースに無い流れを
   持つ画面、どのユースケースにも使われない画面が無いか。USECASES.md は修正せず、流れの食い違いは
   「残った問題」として返す (どちらを正とするかはユーザーが決めるため)

## 出力形式

1. 発見した問題のリスト（問題がない場合は「問題なし」）
2. 各問題の修正内容
3. 修正後のファイル更新（ファイルを直接修正する）

レビューと修正は最大 2 周とする。2 周で解消しなかった問題は修正せず、「残った問題」として列挙して返すこと。
```

サブエージェントが「残った問題」を返したら、ユーザーに提示して扱いを決めてもらう。ただし観点 8 の問題は、手順 5.3 を飛ばしたか、作り込みが一部の画面に届いていないことを示す。ユーザーに提示する前に、「frontend-design の起動のしかた」に従って 5.3 (痕跡の行が無いとき) か 5.6 の反映をやり直す。

セルフレビューが終わり、残った問題の扱いも決まったら、次の 2 つのコマンドが成功する (終了コード 0) ことを確かめる。1 つ目が失敗したら手順 5.3 に、2 つ目が失敗したら手順 5.4 に戻る。

```bash
rg -q '<!-- frontend-design: ' docs/design/UI_SKETCH.html
~/.claude/skills/dev-spec/scripts/sketch-shots.sh docs/design/UI_SKETCH.html <SCRATCH>/sketch-shots
```

成功したら、`docs/design/UI_SKETCH.html` の末尾 (`</html>` の後) に次の 1 行を書く。

```html
<!-- ui-sketch: finalized -->
```

UI_SKETCH.html は 5.1 で作るので、ファイルがあるだけでは本フェーズが終わったかが分からない。dev-spec の再開判定 (SKILL.md の 0.2) はこの印の有無で、UI スケッチの途中で中断したか完了したかを分ける。印は本フェーズの最後にだけ書き、途中では書かない。

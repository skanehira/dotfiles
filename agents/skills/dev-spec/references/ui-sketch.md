## 概要

dev-spec のフェーズ 2 で使う手順書。本書の「手順 N」は本書の中の段階で、SKILL.md のフェーズ番号とは別である。dev-spec のフェーズを指すときは「dev-spec のフェーズ N」と書く。

**cli モードでは本フェーズは実行しない** (dev-spec/SKILL.md フェーズ一覧の cli モード列を参照)。CLI インターフェース仕様は dev-spec のフェーズ 6 が DESIGN.md の「CLI インターフェース」節で設計する (節の中身は `design-doc.md` のテンプレート)。

対話を通じてUIの方向性を整理し、成果物を **単一の `docs/design/UI_SKETCH.html` に集約**する。
この HTML 1ファイルに以下をすべて含める：
1. 画面一覧
2. ユーザーフロー図（HTML/SVG/CSS で描画。**Mermaid は使わない**）
3. クリッカブルなインタラクティブプロトタイプ（React + Tailwind CSS / CDN）
4. 各画面の要素・インタラクション

> **ASCII アートも別 Markdown（UI_SKETCH.md）も作らない。** 成果物は操作できる HTML 1ファイルに統一する。
> ASCII は全角・罫線（East Asian Width が曖昧幅）の表示幅差で崩れ、
> Mermaid/Markdown はプロトタイプとの二重管理になるため。

## ワークフロー

### 手順 1: コンテキストの確認

対象プロダクトと既存ドキュメントを確認する。

#### 1.1 前提ドキュメントの読み込み

次のファイルを読む:

- `docs/design/USER_STORIES.md`
- `docs/PRODUCT_SPEC.md`

#### 1.2 コンテキストの活用

**ファイルが存在する場合**:
- USER_STORIES.md: ユーザーが行いたい操作を把握
- PRODUCT_SPEC.md: プロダクトのスコープを把握

これらの情報を元に、必要な画面を効率的に洗い出す。

**遷移条件**: 手順 2へ

**ファイルが存在しない場合**:
対象プロダクトをユーザーに確認する。

「どのプロダクト/機能のUIをスケッチしますか？」と聞き、自由入力で答えてもらう (目安: 対象のプロダクトや機能領域)。

**遷移条件**: コンテキストが把握できたら手順 2へ

### 手順 2: 画面の洗い出し

必要な画面を特定する。

**質問パターン**:
- 「ユーザーが最初に見る画面は？」
- 「主要な操作をする画面は？」
- 「設定や管理をする画面は？」
- 「エラーや確認のための画面は？」

「このプロダクトに必要な画面をすべて挙げてください」と聞き、自由入力で答えてもらう (例: ログイン、ダッシュボード、SQL入力、結果表示)。

#### 画面の分類

| 種類           | 説明                               | 例             |
| -------------- | ---------------------------------- | -------------- |
| **認証系**     | ログイン、登録、パスワードリセット | ログイン画面   |
| **メイン機能** | コア機能を実行する                 | SQL入力画面    |
| **結果表示**   | 処理結果を表示                     | 改善案一覧     |
| **設定系**     | ユーザー設定、プロフィール         | アカウント設定 |
| **管理系**     | 管理者向け                         | ユーザー管理   |
| **補助系**     | ヘルプ、エラー                     | 404ページ      |

**遷移条件**: 主要な画面が5-15個出たら手順 3へ

### 手順 3: ユーザーフローの整理

画面間の遷移を整理する。

**質問パターン**:
- 「この画面から次にどこへ行けますか？」
- 「この操作が成功したらどの画面に遷移しますか？」
- 「エラーの場合はどうなりますか？」

次のように聞き、自由入力で答えてもらう (目安: 画面A → 画面B → 画面C)。

```
主要なユーザーフロー（画面遷移）を教えてください

例: ログイン → ダッシュボード → SQL入力 → 結果表示
```

#### フローの整理

ここではフローを**言語化して整理するだけ**にとどめる。
図は Mermaid で描かず、手順 5で `UI_SKETCH.html` 内に HTML/SVG/CSS のフロー図として作成する。

整理の例（テキスト）:
- ログイン → ダッシュボード → SQL入力 →（分析）→ 成功: 結果表示 ／ 失敗: エラー表示 → SQL入力

**遷移条件**: 主要フローが整理できたら手順 4へ

### 手順 4: 各画面の要素整理

各画面に必要な要素を洗い出す。

「[画面名]に必要な要素は何ですか？」と聞き、自由入力で答えてもらう (例: 入力欄、ボタン、テーブル、グラフ)。

#### 要素の種類

| 種類               | 説明                                 | 例             |
| ------------------ | ------------------------------------ | -------------- |
| **入力**           | テキスト、セレクト、チェックボックス | SQL入力欄      |
| **アクション**     | ボタン、リンク                       | 「分析」ボタン |
| **表示**           | テキスト、テーブル、リスト           | 改善案リスト   |
| **ナビ**           | メニュー、タブ、パンくず             | サイドバー     |
| **フィードバック** | アラート、トースト、モーダル         | 成功メッセージ |

**遷移条件**: 主要画面の要素が整理できたら手順 4.5へ

### 手順 4.5: アプリシェル設計 (必須)

個別画面とは別軸で、**全画面共通の骨格 (アプリシェル)** を必ず設計する。手順 2で洗い出した個別画面に上から被さる「全画面横断のレイヤ」と捉える。

これを設計しないと、各 UC を実装する subagent が「自分の画面だけ作って横断的 UX を後回し」にする。過去の実測では、その結果トップナビ無し / ErrorBoundary 無し / 404 デッドループ / ログアウトボタン無しとなり、MVP が「ブラウザで開いたら使えない」状態になった。

#### 必須の決定項目

| 項目 | 決めること |
|---|---|
| **グローバルレイアウト** | ヘッダー (ブランド表示 / 主要ナビ / ユーザーメニュー / ログアウト) / トップナビ or サイドナビ / フッター。認証時 / 未認証時で表示を切り替えるか |
| **認証ガード** | 未認証ユーザーが認証必須ルートに来た時のリダイレクト先 (通常 `/login`)。リダイレクト後に元の URL に戻すか (`?next=...`) |
| **404 / 権限なし / ネットワークエラー** | 該当画面のレイアウト + 「ホームへ戻る」「再読み込み」など必須アクション。**404 を `/` に silent redirect しない** (デッドループの原因) |
| **グローバルトースト / 通知** | 成功 / エラー / 情報の 3 種別、表示位置、自動消滅秒数、複数同時表示の上限 |
| **ErrorBoundary 配置方針** | React render エラー時のフォールバック画面。ルート単位 / レイアウト単位 / 個別画面単位のどこに置くか。「ホワイトアウトを絶対に出さない」 |
| **共通 loading 表示** | Suspense 境界の位置、Skeleton vs Spinner の使い分け |

#### 質問パターン

「アプリ全体の骨格 (アプリシェル) を決めます。ヘッダー・ナビ・フッターはどんな構成にしますか?」と聞き、次の 3 択から 1 つだけ選ばせる。

| 選択肢 | 意味 |
| --- | --- |
| ヘッダー + サイドナビ | 管理画面・SaaS 系の定番。ヘッダーにブランドとユーザーメニュー、サイドに主要セクション |
| トップナビのみ | シンプルなプロダクト・ランディング系。ヘッダー一段に主要リンク |
| ヘッダー + フッター (ナビ無し) | シングルページ的・チュートリアル系 |

残りの項目も 1 問ずつ聞き、次の候補 (2〜3 個) だけを選択肢に並べて 1 つだけ選ばせる。「その他」は選択肢に足さない (選択式の質問が 3 択までのランタイムで 4 択になるため)。プロダクトに合う候補が無いとユーザーが答えたら、どうしたいかを通常のメッセージで入力してもらい、その内容を採る。

| 項目 | 候補 |
| --- | --- |
| 認証ガード | 未ログインは `/login` へ遷移し、ログイン後に `?next` で元の URL へ戻す / `/login` へ遷移するだけで元の URL へは戻さない / 認証不要 (全画面を公開) |
| 404 / 権限なし / ネットワークエラー | それぞれ専用画面を出し「ホームへ戻る」「再読み込み」を置く / アプリシェルの `<main>` 内にエラー表示を出し「ホームへ戻る」を置く |
| グローバルトースト | 右上に表示し、成功・情報は 4 秒で自動消滅、エラーは手動で閉じる、同時 3 件まで / 下中央に表示し、全種別 5 秒で自動消滅、同時 1 件 / トーストを使わず各画面のインライン表示だけにする |
| ErrorBoundary | ルート単位とレイアウト単位の 2 段に置く / ルート単位だけに置く / 個別画面ごとに置く |
| 共通 loading 表示 | Suspense 境界をレイアウト単位に置き、一覧は Skeleton・操作中は Spinner / 画面遷移ごとに全画面 Spinner |

#### UI_SKETCH.html への反映と後段への受け渡し

手順 5でプロトタイプ HTML を作る際、**全画面共通のレイアウトコンポーネント (AppShell)** として実装する。各個別画面はこの AppShell の `<main>` 部分に流し込まれる構造にする。404 / 認証ガード / ErrorBoundary のフォールバック画面もそれぞれプロトタイプ化する。

ここで決めた 6 項目は UI_SKETCH.html の中だけに留めない。dev-spec のフェーズ 6 が DESIGN.md「横断規約」のアプリシェルの項へ写し、同じ項に検証の対象 (「テスト方針」の表と `E2E 対象動線:` 行) を起こす (design-doc.md「入力と転記」の規則 4)。dev-spec のフェーズ 9 が AppShell の実装を、その項を「設計」節に書いた基盤親の子 issue として切る (issue-template.md「親 issue テンプレート」)。

**遷移条件**: 上記 6 項目が決まり、UI_SKETCH.html に反映できる粒度になったら手順 5へ

### 手順 5: インタラクティブプロトタイプ作成

ワイヤーフレームは「React + Tailwind CSS を CDN で読み込んだ単一 HTML の
クリッカブル・プロトタイプ」として作成する。ASCII アートは使わない。

**理由**:
- ASCII は全角／半角・罫線の表示幅差で崩れる（環境依存）
- 操作できるプロトタイプの方が画面遷移・フローが正確に伝わる
- React + Tailwind を CDN で使えば、本番実装（React + Tailwind）へそのまま流用できる

手順 5は「5.0 既存語彙の取り込み → 5.1 骨組みの作成 → 5.2 デザイン方向性のヒアリング → 5.3 frontend-design による作り込み → 5.4 動作確認」の順に進める。作り込みの土台になる `docs/design/UI_SKETCH.html` は 5.1 で作る。

#### 5.0 既存の UI 語彙の取り込み（着手前・必須／既存プロジェクトのみ）

**「そのまま流用できる」は、スケッチと実装が同じ語彙で書かれている場合にだけ成り立つ。**
実装者はスケッチを**逐語で写す**ため、同じ名前で違う値を定義すると、構造だけ正しく写って
見た目が壊れる。

既にコードがあるプロジェクトでは、着手前に次を行う:

1. **既存の UI 語彙を Read する**（`src/**/ui-primitives.tsx` / `components/ui/*` /
   `theme.ts` / `tailwind.config.*` / semantic トークンを定義する CSS など。
   `rg -l 'inputCls|buttonCls|const Button' src` で探す）
2. **スケッチのクラス定義は、そこから写す。名前も値も揃える。**
   `inputCls` は `inputCls` のまま同じ文字列にする
3. **同じ名前で違う値を定義しない。** 名前が同じで中身が違うのが最悪で、実装者は正しく
   写したつもりで壊す
4. 語彙に無い見た目が要るときは、スケッチで新設したうえで
   **「実装時にプリミティブへ昇格させる」** をスケッチ内のコメントに残す

> 過去の実例: スケッチの `inputCls` は `w-full` を持ち、実装の `inputCls` は持たなかった。
> `<label>` の中でラベル文字と `<select>` を並べる同じ JSX でも、幅があれば必ず折り返して
> ラベルが上に載り、無ければ内容幅になって**選択肢の文言の長さで見え方が決まる**。
> 絞り込み行の 1 つだけがずれて見え、原因の特定に時間がかかった。
> 同様に `Btn` の `ghost` はスケッチが「枠つき」、実装が「枠なし・透明」で**意味が逆**だった。

新規プロジェクト（コードがまだ無い）では 5.0 を飛ばし、スケッチで定義した語彙を
**実装時にプリミティブへ移す**前提で進める。

#### 5.1 骨組みの作成

手順 2〜4.5 で整理した内容から、`docs/design/UI_SKETCH.html` の骨組みを書き出す。この段階ではビジュアルを作り込まず、構造とフローが操作で確かめられる状態にする。UI_SKETCH.html が既にある (途中で中断したフェーズを再開した) ときは上書きせず、既存の骨組みに足りない部分を足す。

- **単一 HTML ファイル `docs/design/UI_SKETCH.html`** に設計書のすべてを集約・自己完結させる
- **React 19 + Tailwind CSS を CDN で読み込む**
  - React 19 は UMD ビルドを廃止しているため、`importmap` + `esm.sh`（ESM）で読み込む
  - JSX は Babel standalone（`<script type="text/babel" data-type="module">`）で変換、Tailwind は Play CDN
- **次のセクション（タブ/ページ）をHTML内に持たせる**:
  - 概要: 画面一覧テーブル
  - ユーザーフロー図: 画面遷移の俯瞰図を HTML/SVG/CSS で描く（**Mermaid 不使用**）
  - 各フローのクリッカブルプロトタイプ: 画面内のボタンで実際に遷移する
  - 各画面の要素・インタラクション: プロトタイプ内の注釈、または一覧として併記
- 各フローに**説明文**（何のフローか・ステップ・関連 US）を併記する
- 全画面を手順 4.5 の AppShell の `<main>` に流し込む構造にし、404 / 認証ガード / ErrorBoundary のフォールバック画面も置く

#### 5.2 デザイン方向性のヒアリング（作り込み前・必須）

ビジュアルを作り込む前に、**必ずデザインの方向性をユーザに確認する。**

2〜3案を選択式で提示し、ユーザーに選んでもらってから着手する。観点:
- プロダクトのブランド文脈に合うトーンか（例: 外資系ラグジュアリー／国内カジュアル／開発者向け 等）
- 全体の雰囲気（ミニマル／エディトリアル／ポップ 等）、ライト／ダーク
- 主要フォント・配色の方向性

> 方向性を確認せずに作り込むと、ブランド不一致で手戻りになる
> （例: 外資系ホテルのプロダクトを和風デザインで作ってしまう、など）。

ここで合意した方向性は、次の 5.3 の作り込みの入力になる。

#### 5.3 frontend-design による作り込み（必須、skip 不可）

5.2 で方向性が決まったら、**必ず frontend-design スキルを使って**ビジュアルを作り込む。「ジェネリック AI UI のまま終わらせない」ためのゲート。

frontend-design はデザインのガイダンスを読み込むスキルである。スキルを読み込んだあと、`docs/design/UI_SKETCH.html` を編集するのは実行中のエージェント自身で、スキルが別にファイルを書き換えて結果を返すわけではない。

skip 選択肢は提供しない。過去に、このスキルの読み込みを忘れてジェネリックな UI のまま実装へ進んだことがある。プロダクトの規模や時間が限られていても、まず 1 周作り込むこと。フィードバックの反映は 5.4 で往復できる。

frontend-design スキルが見つからない環境もある (プラグインの導入に失敗したマシンなど)。見つからないときは作り込みを始めず、見つからないことをユーザーに伝えて「スキルを導入してから続ける / 別のデザインガイダンスを指定して作り込む」の 2 択から選ばせる。見つからないまま黙ってジェネリックな作り込みに進まない。

作り込みに入る前に、方向性を最終確認する。

「5.2 で合意した方向性 (<トーン / カラー / 雰囲気>) で作り込みます。最終確認: この方向性で進めて問題ないですか?」と聞き、次の 2 択から 1 つだけ選ばせる。

| 選択肢 | 意味 |
| --- | --- |
| 進める | 5.2 で合意した方向性で作り込む |
| 方向性を修正してから | 5.2 に戻って方向性を再ヒアリング |

「進める」が選ばれたら、frontend-design スキルを読み込み、そのガイダンスに従って次の要求どおりに `docs/design/UI_SKETCH.html` を自分で作り込む:

```
方向性 (5.2 でユーザーと合意):
- トーン: <例: 外資系ラグジュアリー / 国内カジュアル / 開発者向け>
- 雰囲気: <例: ミニマル / エディトリアル / ポップ>、ライト / ダーク
- 主要フォント候補: <例: Inter + Noto Sans JP / Geist / system-ui>
- 主要配色: <例: ニュートラル + 1 アクセントカラー (具体的な hex か Tailwind 名)>
- スペーシング: <例: 8px ベース / 詰め気味 / 余白広め>

要求:
- AppShell (ヘッダー / ナビ / フッター / 404 / トースト / ErrorBoundary フォールバック画面。手順 4.5 で設計済) すべてに方向性を反映する
- 各個別画面のプロトタイプにも方向性を反映する
- 5.1 で作った画面構造・フロー・要素は壊さない (構造維持 + ビジュアル適用)
- 単一 HTML ファイル (docs/design/UI_SKETCH.html) を直接上書きする
- 動作確認はブラウザ・chrome-devtools 等で行わない (5.4 でユーザーが手動で確認する)
```

作り込みが終わったら、5.4 の手順でユーザーに手動での動作確認を依頼する。

#### 5.4 動作確認（ユーザー手動）

chrome-devtools 等での自動確認は行わない。ユーザーに `docs/design/UI_SKETCH.html` をブラウザで開いてもらい（macOS なら `open docs/design/UI_SKETCH.html`）、以下を手動で確認してもらう:

- 各フローがボタン操作で遷移するか
- 表示崩れがないか
- ブラウザのコンソールにエラーが出ていないか

「docs/design/UI_SKETCH.html をブラウザで開いて確認してください（フローの遷移 / 表示崩れ / コンソールエラー）。問題はありましたか?」と聞き、次の 2 択から 1 つだけ選ばせる。

| 選択肢 | 意味 |
| --- | --- |
| 問題なし | 次の手順へ進む |
| 修正点あり | 具体的な修正内容を自由入力で受け取る |

修正点があれば frontend-design のガイダンスに沿って自分で反映し、再度ユーザーに確認を依頼する（問題なしになるまで繰り返す）。

**遷移条件**: 主要フローのプロトタイプが作成され、ユーザーの手動確認で「問題なし」となったら手順 6へ

### 手順 6: インタラクションの整理

画面上のインタラクションを定義する。

「この画面でユーザーが行う主要な操作と、その結果を教えてください」と聞き、自由入力で答えてもらう (例: ボタンクリック → モーダル表示)。

#### インタラクション定義

| トリガー                  | アクション          | 結果                    |
| ------------------------- | ------------------- | ----------------------- |
| 「分析」ボタンクリック    | API呼び出し         | ローディング → 結果表示 |
| SQL入力欄フォーカスアウト | バリデーション      | エラー表示 or 正常      |
| 履歴項目クリック          | SQLを入力欄にロード | 入力欄が更新される      |

**遷移条件**: 主要なインタラクションが定義できたら手順 7へ

### 手順 7: UI_SKETCH.html への集約（最終化）

別 Markdown（`UI_SKETCH.md`）は作らない。手順 2〜6で整理した内容を
`docs/design/UI_SKETCH.html` の各セクションに反映し、**1ファイルで完結**させる。

最終的に HTML 内に含めるセクション:
- 画面一覧（テーブル）
- ユーザーフロー図（HTML/SVG/CSS。Mermaid 不使用）
- 各フローのクリッカブルプロトタイプ
- 各画面の要素・インタラクション
- アプリシェルの決定（手順 4.5 の 6 項目）
- デザイン方針（手順 5.2 で合意したトーン・フォント・配色）

### 手順 8: セルフレビュー（サブエージェント）

生成したドキュメントのレビューをサブエージェントに委譲する。

サブエージェント `general-purpose` を起動する (モデル: opus を明示)。

- 説明: `UI/UXスケッチレビュー`
- 次の指示文を渡す:

```
以下のUI/UXスケッチドキュメントをレビューし、問題があれば修正してください。

## レビュー対象ファイル
- docs/design/UI_SKETCH.html

## レビュー観点

1. **画面の網羅性**: 必要な画面がすべてリストアップされているか
2. **フローの完全性**: ユーザーフローに抜け漏れがないか
3. **プロトタイプの明確さ**: 各画面の要素が明確に配置され、フローが操作で遷移するか
4. **インタラクションの定義**: 主要な操作と結果が定義されているか
5. **一貫性**: 画面間でUI要素やナビゲーションが一貫しているか
6. **ユーザビリティ**: 直感的で使いやすい設計になっているか
7. **既存語彙との一致**（既存プロジェクトのみ / 手順 5.0 の確認）:
   スケッチのクラス定義が実装の UI 語彙と**名前も値も一致**しているか。
   とくに**同じ名前で違う値**になっていないか（実装者は逐語で写すため、これが最も壊れる）。
   確認は目視ではなく、両者の定義を取り出して**文字列比較**する

## 出力形式

1. 発見した問題のリスト（問題がない場合は「問題なし」）
2. 各問題の修正内容
3. 修正後のファイル更新（ファイルを直接修正する）

レビューと修正は最大 2 周とする。2 周で解消しなかった問題は修正せず、「残った問題」として列挙して返すこと。
```

サブエージェントが「残った問題」を返したら、ユーザーに提示して扱いを決めてもらう。

セルフレビューが終わり、残った問題の扱いも決まったら、`docs/design/UI_SKETCH.html` の末尾 (`</html>` の後) に次の 1 行を書く。

```html
<!-- ui-sketch: finalized -->
```

UI_SKETCH.html は 5.1 で作るので、ファイルがあるだけでは本フェーズが終わったかが分からない。dev-spec の再開判定 (SKILL.md の 0.2) はこの印の有無で、UI スケッチの途中で中断したか完了したかを分ける。印は本フェーズの最後にだけ書き、途中では書かない。

- [ ] ユーザーフロー図が HTML で描かれている（Mermaid 不使用）

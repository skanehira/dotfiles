# issue テンプレートと作成手順 (dev-spec のフェーズ 9〜10)

- 種別: テンプレート + 手順書
- 定めるもの: issue のドラフト (dev-spec のフェーズ 9 が書く) と、GitHub の issue (dev-spec のフェーズ 10 が作る)
- issue の読み手: dev-spec のフェーズ 9 (ドラフトチェック)・フェーズ 10 (issue 作成)、`/dev-impl` (子 issue を読んで実装・親 issue を close)、人間 (「ゴール」を読んで内容を理解し、承認する)

**issue の情報設計の基準は 2 つある。** (1) 人が「ゴール」だけを読んで、issue の内容を理解できる。(2) 実装者が本文と参照 docs だけで着手できる。(1) を先頭に置き、(2) のための節は折りたたむ。

## issue の階層 (2 階層)

```
UC-001: マスタと据置端末を整備する          ← 親 (tracking)。ユースケース 1 つ = 1 件
├─ マスタと据置端末の API・ドメインを実装する   ← 子 (ready)。実装の作業単位
└─ マスタ管理と据置端末管理の画面を実装する
基盤: UC に属さない共通実装                  ← 親 (tracking)。UC に属さない子の受け皿
├─ データスキーマと D1 マイグレーションを整備する
└─ 監査ログの追記基盤を作る
```

- **親 = ユースケース**。「どの UC がどこまで進んだか」を GitHub の Sub-issues セクション (進捗バー) で読めるのが存在意義
- **子 = 実装の作業単位**。1 issue = 独立して検証可能な 1 単位。`/dev-impl` が実装して close し、その親の子が全 closed になった時点で `/dev-impl` が親も close する
- 親は open のまま複数 run にまたがってよい (UC に子が後から足されることがある)
- run 全体を束ねる親は作らない。**例外は USECASES.md が無いクイックモード構成だけ** (下記「クイックモード構成」)

## ラベル (4 種)

| ラベル | 意味 | 付与者 |
| --- | --- | --- |
| `ready` | 着手可能 (子 issue の作成時の既定) | dev-spec のフェーズ 10 |
| `in-progress` | dev-impl が実装中 | dev-impl (着手時) |
| `needs-human` | 人間の判断待ちで駐車中 | dev-impl (エスカレーション時)・dev-triage |
| `tracking` | 親 issue (トラッキング)。実装対象ではない | dev-spec のフェーズ 10・dev-triage |

親 issue にライフサイクルラベル (`ready` / `in-progress` / `needs-human`) を付けない — 親は実装されないので、付けるとラベルが状態を偽り、ラベルによる集計や再開の判定が誤る。

### ラベルの用意

dev-spec のフェーズ 10 (`create-issues.sh` の手順 3) と dev-impl の Step 0 が、次の 4 行で用意する。`--force` なので、既にあっても何度実行してもよい (`REPO_SLUG` は `gh repo view --json nameWithOwner -q .nameWithOwner` で得る):

```bash
gh label create ready       --repo "$REPO_SLUG" --force --color 0E8A16 --description "着手可能"
gh label create in-progress --repo "$REPO_SLUG" --force --color 1D76DB --description "dev-impl が実装中"
gh label create needs-human --repo "$REPO_SLUG" --force --color D93F0B --description "人間の判断待ちで駐車中"
gh label create tracking    --repo "$REPO_SLUG" --force --color 5319E7 --description "親 issue (トラッキング)。実装対象ではない"
```

## 子 issue テンプレート

タイトルは作業内容が分かる平叙文 (例: `エクスポート機能の書き出し API を実装する`)。再実行の突き合わせがタイトル一致で行われるため、作成後に整形して変えない。

**再実行では既存の子のタイトルを引き継ぐ。** ドラフトは毎回 docs から作り直すので、同じ作業単位でも言い回しがずれうる。ずれたまま dev-spec のフェーズ 10 に渡すと、タイトルの突き合わせが外れて同じ作業の子が二重に作られる。closed の子なら、実装済みの作業が `ready` で作り直され、dev-impl が再実装する。これを防ぐため、dev-spec のフェーズ 9 は子のドラフトを書いたあと、既存の issue を本文ごと取得してタイトルを決める (`REPO_SLUG` は `gh repo view --json nameWithOwner -q .nameWithOwner` で得る。取得件数が limit に達したら limit を上げて再取得する。`gh` が未認証で取得できないときは、認証が済んでから dev-spec のフェーズ 10 の作成同意を取る前に行う):

```bash
gh issue list --repo "$REPO_SLUG" --state all --limit 1000 --json number,title,state,labels,body
```

1. `tracking` ラベルが無く、本文に「対応 UC:」行を持つ issue を既存の子とする (open / closed の両方)
2. ドラフトの子と既存の子を、次の 2 つの組 (鍵) で突き合わせる。(a) 「対応 UC」行の UC 番号の集合 (`基盤` はそのまま 1 つの値)。(b) 「設計」節が参照する `docs/design/features/<機能名>.md` のパスの集合。機能設計書を参照しない子 (アプリシェルなどの基盤の子) では、代わりに「設計」節が名指しする DESIGN.md の節名の集合を使う
3. 同じ鍵を持つ既存の子が複数あるときは、「担う受け入れ基準」行の一致で 1 件に絞る
4. ちょうど 1 件に絞れたら、その既存の子のタイトルをドラフトのタイトルにする。既存の子が closed でも引き継ぐ。closed の子と同じタイトルになったドラフトは、dev-spec のフェーズ 10 の `create-issues.sh` がタイトルの一致でその closed の子に対応づけ、作り直さない (**closed の子を `ready` で作り直さない**)
5. 一致する既存の子が無いドラフトは、新しい作業単位として新しいタイトルを付ける。1 件に絞れないとき、または 1 件の既存の子に複数のドラフトが当たるときは、候補を番号付きでメッセージに並べ、どれを引き継ぐかを人間に答えてもらう (勝手に選ばない)

どのドラフトにも当たらなかった open の既存の子は、docs の改訂で消えた作業単位の可能性がある。dev-spec のフェーズ 10 の `create-issues.sh` が最終報告に挙げるので、扱いを人間に聞く (下記「issue 作成手順」の「最終報告」)。

```markdown
## ゴール
<だれが、どこで、何をできるようになるかの 1 文>

**いま困っていること**: <1〜3 文>

**こうなる**: <1〜3 文か箇条書き>

**例**: <だれかが操作して何が起きるかの手順。5 段まで>

**変わらないこと**: <利用者から見て変わらないもののうち、変わると思われそうなもの>

**関係する機能**: [<機能名>](https://github.com/<owner>/<repo>/blob/<デフォルトブランチ>/docs/design/features/<機能名>.md#何を作るか)

<details>
<summary>実装用 (AI が読む。上のゴールだけで内容は分かる)</summary>

## 設計
対応 UC: <UC-001: <名前> か 基盤>
担う受け入れ基準: <機能設計書「テスト方針」の表の行>

docs/design/features/<機能名>.md 参照

## DoD
- <実行可能なコマンドと期待結果>

## 非スコープ
<隣接するがこの issue ではやらないこと>

## 依存
Depends on #<番号>

</details>
```

「ゴール」は、issue を読む人 (承認する人・状況を知りたい人) が、設計書を開かずに内容を理解するための節である。折りたたんだ 4 節は実装する AI が読む。`## 優先度` は `dev-triage` が折りたたみの外 (末尾) に書く。

書いたら `sh ~/.claude/skills/dev-spec/scripts/issue-check.sh <本文のファイル>...` を実行し、何も出力しなくなるまで直す。「ゴール」の上限は 25 行 (空行を除く)・合計 2,500 バイト・1 行 300 バイトである (日本語 1 字は 3 バイト。リンクの先は数えない)。`<summary>` の次の空行は消さない (消すと中の Markdown が表示されない)。

各節の書き方:

| 節 | 書き方 |
| --- | --- |
| 設計 の「対応 UC」 | `UC-001: <名前>` の形。統合親が覆う 2 件の UC にまたがるときだけ `, ` 区切りで列挙する。どの UC にも属さない子は `基盤` と書く |
| 設計 の「担う受け入れ基準」 | 参照する機能設計書「テスト方針」の表のうち、この issue が満たす行を文面そのままで列挙する。1 つの機能設計書の表を複数の子で分けるときだけ書き、この子が表を全行担うときは行ごと省く |
| ゴール | 1 文に 1 つのことを、利用者の言葉で書く。利用者から見えない開発基盤の issue では、開発者の言葉で書く。バッククォートで書く名前・API のパス・受け入れ基準の ID は書かない。設計書の変更が要らない issue では、直し方も「こうなる」に書く。「例」は、起きることが文だけで伝わるなら省く。「関係する機能」は、人が読む時点でデフォルトブランチに無い機能設計書 (設計 PR で新設したものなど) なら省く。先頭の 1 文・「いま困っていること」・「こうなる」・「変わらないこと」は省かない |
| 設計 | 機能設計書を参照する。横断事項 (スキーマ・API 規約・認証など) に触れる場合は `docs/design/DESIGN.md「<節名>」` も併記する。設計本文は転記しない (正本は docs 側で、issue は参照のみ)。DESIGN.md「既知の制約」に、この issue が触れる範囲の制約 (クエリ上限・ID の順序・時刻の基準など) があれば必ず併記する。実装者は issue が名指しした docs しか読まないため、併記しなければ制約は実装に届かない |
| DoD | 実行可能なコマンドと期待結果 (例: `deno test src/export/` が green、`npm run lint` が warning 0)。実行方法の前提 (セットアップ・起動) は DESIGN.md「開発・検証コマンド」に置き、ここでは繰り返さない。未検証の `POC_NEEDED` マーカーの扱いは下記 |
| 非スコープ | 隣接するがこの issue ではやらないこと |
| 依存 | 依存が無ければ「依存なし」と書く。dev-impl はこの行で着手順を決める。依存が複数あるときは 1 件につき 1 行書き、カンマ区切りで 1 行に並べない (例: `Depends on #12` の次の行に `Depends on #15`)。依存先は別の親に属する子でもよい (親をまたぐ依存は許容する)。**書く基準は「この issue の DoD 実行に、依存先が merge した成果物が無ければ失敗するか」だけ** (下記「依存の段数」)。**dev-spec のフェーズ 9 のドラフトでは GitHub の番号がまだ無いので `Depends on issue-<連番>` と書き** (連番はドラフトのファイル名 `issue-<連番>.md` のもの)、dev-spec のフェーズ 10 の作成時に `#<番号>` へ置き換える |

**DoD の `POC_NEEDED` マーカー**: 「設計」節が参照する docs の該当範囲に未検証の `POC_NEEDED` マーカー (`blocker=false`) が残っていれば、その検証項目を確かめて結果を docs に反映し、マーカーを除去することを DoD に含める。あわせて FEASIBILITY.md の同じ id の POC_STATUS 行を検証結果の status に更新し、「PoC 結果」に項を足す (書式は FEASIBILITY.md の既存の「PoC 結果」に倣う)。更新しないと、設計ループを流し直したときにその計画が未検証として再び拾われ、マーカーが復活する。1 つのマーカーはちょうど 1 つの子の DoD に載せる。どの子の「設計」節も名指ししない節にあるマーカーは、その要素を実装する子の「設計」節にその節を併記して載せる。DoD の例:

- `rg -n 'POC_NEEDED: id=<id>,' docs/design/` が 0 件 (検証結果は docs/design/features/<機能名>.md に反映済み)
- `rg -n 'POC_STATUS: id=<id>,.*status=unresolved' docs/design/FEASIBILITY.md` が 0 件

**「対応 UC」行は省略しない。** この行が子と親の対応づけの正本で、dev-spec のフェーズ 10 の紐付けとドラフトチェック観点 6 の照合がこれに依存する。複数列挙してよいのは、それらの UC を覆う統合親がある場合だけである。統合親が無い組み合わせ (3 件以上の UC、または統合しなかった 2 件の UC) にまたがる作業は、UC ごとに子を分割する。1 件の子は 1 つの親にしか紐付かないので、分割しないと残りの UC の親が、この子の完了を待たずに close されうる。

## 親 issue テンプレート (ユースケース単位)

USECASES.md の UC 1 件につき親 1 件を作る。ドラフトのファイル名は `parent-UC-<番号>.md` (例: `parent-UC-001.md`)。**タイトルは USECASES.md の見出し表記をそのまま使う** (`## UC-001: マスタと据置端末を整備する` という見出しなら `UC-001: マスタと据置端末を整備する`)。突き合わせがタイトル一致なので、作成後に整形して変えない。

```markdown
## ユースケース
docs/design/USECASES.md「<UC の見出し>」参照

## 設計
docs/design/features/<機能名>.md 参照
<この UC を実現する機能設計書を列挙する。横断事項に触れるなら docs/design/DESIGN.md「<節名>」も併記>

## 受け入れ基準
docs/design/USECASES.md「<UC の見出し>」の受け入れ基準を参照。検証は子 issue の DoD と、機能設計書「テスト方針」が割り当てたテストで行う。本 issue には転記しない。

## 完了の定義
この親の Sub-issues がすべて close されること。進捗バーと子の一覧は本 issue の Sub-issues セクションを見る。子 issue の close と、全子完了時の本 issue の close は /dev-impl が行う。
```

例外的に立てる親は 2 種類:

| 親 | ドラフトのファイル名 | タイトル | 立てる条件 |
| --- | --- | --- | --- |
| 基盤 | `parent-kiban.md` | `基盤: UC に属さない共通実装` (固定文字列) | どの UC にも属さない子 (スキーマ整備・監査ログ基盤・CI 整備など) が 1 件以上ある |
| UC 統合 | `parent-UC-<番号 1>-<番号 2>.md` (例: `parent-UC-004-005.md`。番号の昇順) | `<UC 番号 1> / <UC 番号 2>: <見出し本文 1> と <見出し本文 2>` (例: `UC-004 / UC-005: カートに入れる と 数量を変える`) | 2 つの UC が密結合で、子を分けても実装・検証の単位が分かれない |

基盤親の「ユースケース」節と「受け入れ基準」節は `該当なし (UC に属さない共通実装)` と書く。UC 統合親の「ユースケース」節と「受け入れ基準」節には両方の見出しを列挙する。**統合は 2 件までとし、3 件以上は統合せず親を分ける** (3 件以上の UC にまたがる作業は UC ごとに子を分割する)。

**webapp ではアプリシェル (AppShell) を基盤親の子として切る。** UI_SKETCH.html で決めたアプリシェル (グローバルレイアウト・認証ガード・404 / 権限なし / ネットワークエラー画面・グローバルトースト・ErrorBoundary・共通 loading 表示) は、どの UC にも属さない共通実装なので、1 件の子にして基盤親に紐付ける。この子の「対応 UC」は `基盤`、「設計」節は `docs/design/DESIGN.md「横断規約」のアプリシェルの項 参照` と書く (機能設計書が無いので `docs/design/features/` は書かない)。アプリシェルの決定は dev-spec のフェーズ 6 がその項へ写しており、その項は機能設計書と同じ形の「テスト方針」の表と `E2E 対象動線:` 行を持つ (design-doc.md「入力と転記」の規則 4)。implementer と review-impl は、この子では機能設計書の代わりにその項から検証の対象を読む。DoD は、その表の各行 (レベルが `なし` の行を除く) を割り当てたレベルのテストが green になることと、`E2E 対象動線:` 行の E2E が通ることにする (`E2E 対象動線: なし` のときは E2E の項を書かない)。「担う受け入れ基準」行は書かない (表の全行をこの子が担う)。画面を持つ子の DoD がアプリシェルを前提にする (例: 画面の E2E が認証ガードを通る) ときは、その子に `Depends on` を書く。

**統合親のタイトルは上記の合成規則で機械的に導出する** (自由な要約名を付けない)。再実行の突き合わせがタイトル完全一致なので、名前が揺れると同じ UC 群に親が二重に作られる。合成規則の詳細: 「見出し本文」は USECASES.md の見出しから `UC-<番号>: ` を除いた部分、**並び順は UC 番号の昇順**。

### クイックモード構成 (USECASES.md が無い)

UC が存在しないため、親は `<タスク名> トラッキング` 1 件にフォールバックし、全子をそこに紐付ける。ドラフトのファイル名は `parent-quick.md`。本文の「ユースケース」節と「受け入れ基準」節は省き、「設計」節に DESIGN.md を書く。子の「対応 UC」行は `基盤` と書く (`parent-quick.md` が `基盤` のキーを受け持つ。下記「issue 作成手順」の「スクリプトが行うこと」の手順 1)。

USECASES.md があるのに、全部の子を 1 件の「<タスク名> トラッキング」の親で束ねている構成を**旧構成**と呼ぶ。今の dev-spec は UC ごとに親を作るので、旧構成は UC ごとの親へ移行する (下記「スクリプトが行うこと」の手順 7)。

## タイトル一覧ファイル

ドラフトのファイルは本文だけで、`--body-file` でそのまま GitHub に渡すので、タイトルを中に書けない。dev-spec のフェーズ 9 は全ドラフト (親と子) のタイトルを `<scratchpad>/titles.tsv` に 1 件 1 行で書き出す。1 列目がドラフトのファイル名、2 列目がタイトルで、間はタブ 1 つにする。

```
parent-UC-001.md	UC-001: マスタと据置端末を整備する
issue-1.md	マスタと据置端末の API・ドメインを実装する
```

ドラフトチェックの検査 subagent はこのファイルでタイトルを読む。dev-spec のフェーズ 10 の `create-issues.sh` は、既存の issue との突き合わせと、issue の作成のタイトルをここから引く。

## ドラフトチェックのチェックリスト (dev-spec のフェーズ 9 のドラフトチェック)

fresh context の検査 subagent に、親 + 子の全ドラフトを一括で渡して検査させる観点:

1. **自己完結性**: 実装者が issue 本文と参照 docs だけで着手できるか。会話の文脈にしか無い前提が紛れていないか
2. **DoD の実行可能性と空虚性**: DoD が実行可能なコマンドか。対象が未実装でも通る DoD (存在チェックだけ・恒真の grep 等) になっていないか
3. **依存の整合と段数**: 「依存なし」の issue が実は他 issue の成果物を前提にしていないか。書かれた `Depends on` が、下記「依存の段数」の「書く基準」に合っているか。段数と実行バッチ数は `dep-depth.sh` の出力で渡すので、検査側は数え直さない。`<b>` が `<m>` を超えていれば、段ごとの子の一覧から、削れる可能性のある `Depends on` 行を `[medium]` で列挙する (循環とドラフトに無い連番への依存は、`dep-depth.sh` が先に止めるので、検査に届かない)
4. **相互の重複・漏れ**: 同じ作業が複数 issue に跨っていないか。機能設計書の「実装の配置」に現れるファイルがどの issue にも属さず漏れていないか。機能設計書「テスト方針」の表の各行が、ちょうど 1 つの子に担われているか (「担う受け入れ基準」行を持つ子はその行、持たない子は参照する機能設計書の全行を担う。webapp では DESIGN.md「横断規約」のアプリシェルの項の表を、アプリシェルの子が全行担う)。docs に残る `blocker=false` の `POC_NEEDED` マーカーの各 id が、ちょうど 1 つの子の DoD に現れるか (どの子にも載らないマーカーは検証されずに残り、複数の子に載ると検証が重複する)
5. **参照の実在**: 参照する docs パス・節名・UC 名が実在するか。`titles.tsv` に全ドラフトの行があり、子のタイトルが重複していないか
6. **UC 帰属の整合**: 親ドラフトが USECASES.md の UC を過不足なく覆っているか。各子の「設計」に「対応 UC」行があり、その UC を覆う親ドラフトが存在するか。`基盤` の子が基盤親に集約されているか。「対応 UC」に複数の UC を書いた子が、それらを覆う統合親を持つか (統合親の無い組み合わせ、とくに 3 件以上の UC を書いた子は分割漏れ)。webapp でアプリシェルの子が基盤親の下にあるか。**次の 2 つは違反ではない**: `基盤: UC に属さない共通実装` 親 (USECASES.md に対応する UC が無くてよい)、複数 UC をまとめた統合親 (タイトルが単一の UC 見出しと一致しなくてよい)
7. **人が読む文章**: 各子の「ゴール」だけを読んだ人が、何に困っていて、何がどう変わるかを説明できるか。「こうなる」「例」「変わらないこと」が、参照する機能設計書・「担う受け入れ基準」・「非スコープ」に合っているか (食い違いは high、分からない箇所は medium)

dev-spec のフェーズ 9 は上記 7 項目を検査 subagent の指示文に転記するので、**例外の但し書き (項目 6 の末尾) と、下記「依存の段数」の書く基準・閾値、`dep-depth.sh` の出力 (全行) も一緒に転記する** — 転記しないと検査側は例外表も段数の基準も見ておらず、基盤親・統合親に対して必ず high を上げ、削れる依存も挙げられない。

## 依存の段数

`/dev-impl` は、依存先がすべて close された issue (着手できる issue) を最大 3 件まで並列に実装する。依存の連なりは前の issue の merge を待たないと先へ進めないので、run の所要時間の下限は**依存の段数** (最も長い依存の連なり) で決まる (実測: 子 22 件を 10 段に割った run で、段ごとの最長サイクルの和 375 分に対し、実経過は 386 分だった)。段を浅く割ることが、実装ループの所要時間に最も効く。

**`Depends on` を書く基準**: その issue の DoD 実行に、依存先が merge した成果物が無ければ失敗する場合だけ書く。書かない例:

- 依存先が作る型やヘルパーを**参照するだけ**で、この issue の DoD が通る (参照先を自分で用意できる、またはインタフェースが docs で確定している)
- 同じ機能設計書に属する / 画面と API が対になっている、という理由だけの並び
- 順に作ると人間には自然、という理由だけの並び

**算出**: スクリプト `scripts/dep-depth.sh` が、ドラフトの連番 (`issue-<連番>.md`) と `Depends on issue-<連番>` の対応から計算する (GitHub の issue 番号はドラフト段階でまだ無い)。依存が無い issue を L0、それ以外は「依存先のレベルの最大値 + 1」とする。実行するコマンドは SKILL.md「フェーズ 9」にある。出力の 1 行目が次の行で、2 行目以降が段ごとの子 (`L<段>: issue-<連番> ...`) である。終了コードは次のとおり。

| 終了コード | 意味 | 扱い |
| --- | --- | --- |
| 0 | 計算できた | 出力を検査 subagent に渡す |
| 1 | 使い方の誤り、または `issue-*.md` が無い | 引数とドラフトのディレクトリを見直す |
| 2 | ドラフトに無い連番への依存がある | 標準エラーに挙がった行に従ってドラフトを直し、実行し直す |
| 3 | 依存が循環している | 同上 |
| 4 | 依存の行の形が違う (1 行に複数並べたなど)、またはファイル名の連番が数でない | 同上 |

フェーズ 10 を走らせた後のドラフトでは、段数を計算し直さない。依存が `Depends on #<番号>` に置き換わっていて、段に数えられないため。計算し直すときは、フェーズ 9 からドラフトを作り直す。

```
依存段数: L0..L<k> (<k+1> 段、実行バッチ <b> / 下限 <m>)
```

**比較するのは段数ではなく実行バッチ数**である。段数 (`<k+1>`) は依存の深さ、`<b>` は「各段を 3 件ずつに分けて流したときの総バッチ数」= `Σ ceil(|L_i| / 3)` (`|L_i|` は段 i に属する子の件数)、`<m>` は下限 `ceil(子 issue 件数 / 3)`。段数と下限は単位が違うので、直接比べない (子 22 件を全て L0 に置くと、段は 1 でも 3 並列なら 8 バッチ要る)。

`<b>` が `<m>` を超える場合は `[medium]` の finding として、**削れる可能性のある `Depends on` 行を列挙する** (どれを削るかは設計判断なので、指摘に留めて修正はしない)。超過分 `<b> - <m>` が、依存を浅く割れば取り戻せるバッチ数の見積もりである。`/dev-impl` は段をまたいで空いた枠に次の issue を入れるので、`<b>` は実際のバッチ数の上限の見積もりで、超えても依存を削る必要があるとは限らない。指摘の本文にもそう書く。

この比較が意味を持つのは **`/dev-impl` が並列実行を許すプロジェクトだけ**である。満たさない repo は並列度 1 で回り、段数を減らしても所要時間は縮まらない。その場合は比較を行わず、行に「(並列前提を満たさないため閾値判定なし)」と添える (`dep-depth.sh` に `--serial` を渡すと、この但し書きを付けて出す)。並列を許す条件の正本は dev-impl の SKILL.md (`~/.claude/skills/dev-impl/SKILL.md`)「2.0 並列実行の可否と枠組み」にある。dev-spec のフェーズ 9 はそれを Read して、対象のリポジトリが条件 (3 つの箇条) を満たすかを判定し、満たさなければ `dep-depth.sh` に `--serial` を渡す。ここに条件を写さないのは、dev-impl 側の改訂と食い違わないようにするためである。

## issue 作成手順 (dev-spec のフェーズ 10)

issue の作成と紐付けは、スクリプト `scripts/create-issues.sh` が行う。実行するコマンドは SKILL.md「フェーズ 10」にある。エージェントが `gh` のコマンドを組み立てて書き下ろすと、シェルの違い (macOS の zsh と Ubuntu の bash) や書き間違いで途中から止まり、親だけ、または子の一部だけが作られたまま残る。スクリプトは POSIX の sh と awk だけで書いてあり、何度実行しても同じ結果になる (冪等)。途中で止まったら、原因を直して同じコマンドを再実行すれば続きから進む。

入力は、フェーズ 9 が scratchpad に書いた `titles.tsv`・`parent-<識別子>.md`・`issue-<連番>.md` である。カレントディレクトリの GitHub リポジトリに作る。

### 終了コードと扱い

| 終了コード | 意味 | エージェントの扱い |
| --- | --- | --- |
| 0 | 作成と紐付けを終えた。標準出力が最終報告 | 最終報告を人間に示す (下記「最終報告」) |
| 1 | 使い方の誤り、既存の issue が上限 (環境変数 `ISSUE_LIST_LIMIT`、既定 1000 件) 以上、`gh` の失敗のどれかで止まった。標準エラーに理由を出す (作成と紐付けの失敗では、作成済みの番号の置き場 `<scratchpad>/numbers.tsv` も出す) | 上限なら `ISSUE_LIST_LIMIT` を今の上限より大きくして再実行する。それ以外は状態を人間に伝え、原因 (認証・ネットワーク・権限など) を直してから、同じコマンド (同じ `--keep` を含む) を再実行する |
| 3 | 人間の判断が要る。`NEEDS_HUMAN:` で始まる行を出す。GitHub には何もしていない | 行をそのまま提示して決めてもらい、下の表の操作をしてから再実行する |
| 4 | ドラフトの誤り。標準エラーに挙げる。GitHub には何もしていない | ドラフトを直し、フェーズ 9 のドラフトチェックからやり直す |

終了コード 2 は使わない。表に無い終了コード (`sh` が見つからない 127 など) が出たら、標準エラーを添えて人間に伝える。

`NEEDS_HUMAN:` の行と、決まった後の操作:

| 出力の行 (先頭) | 起きる場面 | 決まった後の操作 |
| --- | --- | --- |
| `NEEDS_HUMAN: 同じタイトルの issue が複数あり、どれに当たるか決められない:` | 人が同じタイトルの issue を作った | 当てない方のタイトルを変えるか close して、タイトルを一意にする |
| `NEEDS_HUMAN: 「<タスク名> トラッキング」の親が複数ある。どれを流用するかを選ぶ:` | クイックモードで、タスク名の違う前回の open の親が複数残っている | 流用する親を 1 つ選んでもらい、それ以外の番号を `--keep` に渡して再実行する |
| `NEEDS_HUMAN: 旧構成の「<タスク名> トラッキング」の親が複数ある。どれから移行するかを選ぶ:` | UC ごとの親で、旧構成の open の親が複数残っている | 移行する親を 1 つ選んでもらい、それ以外の番号を `--keep` に渡して再実行する |
| `NEEDS_HUMAN: どの親のドラフトとも一致しない tracking の親が子を持つ。どの新しい親へ貼り替えるか、旧親のまま残すかを決める:` | UC ごとの親で、UC の見出しが改訂されて親のタイトルが変わった。または、dev-spec と別の作業の親 (dev-triage が付けた `tracking` など) がある | 新しい親へ貼り替えるなら、旧親のタイトルを新しい親のドラフトのタイトルに変える (`gh issue edit <番号> --title "<タイトル>"`。同じ親として流用され、本文が貼り直される)。旧親のまま残すなら、その番号を `--keep` に渡して再実行する |

`--keep <番号>` に渡した親は、突き合わせ・流用・移行の対象から外れる。その親に付いている子がドラフトに一致しても、紐付けは変えずに最終報告に挙げる。番号が複数あるときは `--keep 12 --keep 15` か `--keep 12,15` と渡す。決めた `--keep` は、その後の再実行 (終了コード 1 の後など) にも毎回付ける。`--keep` の決定はどこにも保存されないので、次に dev-spec を回したときは同じ `NEEDS_HUMAN:` がまた出る。そのときは前回の判断を添えて人間に聞き直す。

### スクリプトが行うこと

規則の正本はこの節で、`create-issues.sh` はこれに従う。

1. **ドラフトを確かめる** (GitHub には触らない)。次の条件のうち 1 つでも満たさないものがあれば、終了コード 4 で止まる
   - `titles.tsv` に、全ドラフトのタイトルがあり、同じタイトルが 2 つ無い (形式は上記「タイトル一覧ファイル」)
   - 子に「対応 UC:」の行があり、その UC が 1 つの親のドラフトにまとまる。親のキーはファイル名から決める: `parent-UC-001.md` は `UC-001`、統合親 `parent-UC-004-005.md` は `UC-004` と `UC-005`、`parent-kiban.md` と `parent-quick.md` は `基盤`
   - 依存の行が 1 行に 1 件で (`Depends on issue-<連番>` か `Depends on #<番号>`)、循環せず、ドラフトに無い連番を指さない
2. **既存の issue と突き合わせる**。`gh issue list --state all` で全件を読み (上限は環境変数 `ISSUE_LIST_LIMIT`、既定 1000 件。上限以上あれば取りこぼすので終了コード 1 で止まる)、ドラフトと既存の issue をタイトルの完全一致で対応づける。人間の判断が要る場合 (上の表) は、ここで何もせずに止まる。どの親のドラフトとも一致しない `tracking` の親は、open で `--keep` に渡されていないものだけを扱う (closed の親は終わった別の作業の親なので、流用も移行もしない)。クイックモードでは、親のドラフトのタイトルに一致する親が無く、その「<タスク名> トラッキング」の親が 1 件だけなら、タイトルが違っても流用する (タスク名が変わっただけのため。本文は手順 6 で貼り直す)
3. **ラベル 4 種を用意する** (上記「ラベルの用意」の 4 行)
4. **親を用意する**。一致した既存の親はそのまま使い、無ければ `tracking` を付けて作る。親は子より先に作る (親の本文は子の番号を含まないので、子を作った後に親の本文を作り直す工程は無い)
5. **子を依存の上流から 1 件ずつ用意する**。作る直前に、ドラフトの `Depends on issue-<連番>` を `Depends on #<番号>` に置き換える (ドラフトのファイルを書き換える)。上流から順に作るので、置き換えに要る番号は常に決まっている。一致した既存の子は作らない。全件の後で、行頭の `Depends on issue-` の置き換え残しが無いことを確かめる (行の途中の「Depends on issue-<連番>」は依存ではないので置き換えない)。ドラフトのファイル名と番号の対応は `<scratchpad>/numbers.tsv` (`<ファイル名><TAB><番号>`) に、実行のたびに書き直す。人が作成済みの番号を見るためのもので、再実行では読まない (続きはタイトルの一致で決まる)
6. **既存の issue の本文を比べる**。一致した既存の issue (親と子) の本文を、依存を置き換えた後のドラフトと比べる。比べる前に、両方から CR と末尾の空行を落とす。open なら、違えば貼り直す。closed なら書き換えず、違う番号を最終報告に挙げる (完了済みの issue に改訂が届かないことを人間が把握できるように)
7. **旧構成から移行する** (UC ごとの親のとき、手順 2 で扱う open の「<タスク名> トラッキング」の親が 1 件ある場合)。旧親の子を、その子の本文の「対応 UC」の親へ貼り替える。「対応 UC」が読めない子は貼り替えずに旧親に残し、最終報告に挙げる。旧親の子が 0 件になったときだけ、旧親を close する
8. **子を親に紐付ける**。各親に紐付け済みの子を先に読み (`--paginate` と `per_page=100`。既定の 1 ページ 30 件では 31 件目以降が見えず、二重紐付けの HTTP 422 を踏む)、まだ紐付いていない子だけを紐付ける。別の親に付いている子 (`--keep` で残した親の子など) は紐付けを変えず、最終報告に挙げる。closed の親に紐付けるときは、先に reopen する。ドラフトに無い open の既存の子 (`tracking` が無く、本文に「対応 UC:」行を持つ issue) は、親が無ければ本文の「対応 UC」の親へ紐付け、決められなければ最終報告に挙げる。closed の子は紐付けない
9. **最終報告を出す** (下記)

### 親への紐付け (GitHub sub-issues API)

スクリプトと dev-impl (親の close の判定) が依拠する、GitHub の実測の挙動 (2026-08-27 時点、gh 2.97.0・業務のリポジトリおよび使い捨てリポジトリで確認。本文の保存は 2026-11-14、gh 2.103.3 で確認):

| 項目 | 挙動 |
| --- | --- |
| パラメータの型 | `-F` (typed) が必須。`-f` (文字列) は `is not of type integer` で HTTP 422。id は `gh api repos/.../issues/<番号> --jq .id` の numeric id (`gh issue view --json id` が返す `I_kwDO...` 形式の node ID は使えない) |
| 二重紐付け | HTTP 422。メッセージが単一親制約の違反と共通なので、事後に握りつぶさず seed による事前判定で避ける |
| 単一親制約 | 子は同時に 1 つの親にしか紐付かない。別の親に紐付いている子は `-F replace_parent=true` を追加して貼り替える |
| 親の逆引き | `gh api "repos/$REPO_SLUG/issues/<子番号>/parent"` が親の `number` / `state` / `sub_issues_summary` (`total` / `completed` / `percent_completed`) を返す。親が無い子では HTTP 404 (dev-impl が close 判定に使う) |
| 親からの進捗取得 | `gh api "repos/$REPO_SLUG/issues/<親番号>" --jq .sub_issues_summary` でも同じ `total` / `completed` が引ける (子を自前で列挙して数えなくてよい) |
| `state` の大小文字 | `gh api` (REST) は小文字 `open` / `closed`、`gh issue list --json` / `gh issue view --json` は大文字 `OPEN` / `CLOSED`。混ぜない |
| 本文の保存 | 本文は受け取ったとおり (末尾の改行も含めて) 保存される。`gh issue view --json body -q .body` は、その末尾にさらに改行を 1 つ足して出す。Web の画面で編集された本文は CRLF になる |

### 最終報告

スクリプトは、成功すると標準出力に次の形で報告する。該当が無い行は出ない。

```
親 issue: 新規 <a> / 既存 <b>
  #<番号> <タイトル>
子 issue: 新規 <c> / 本文更新 <d> / 変更なし <e>
旧構成からの移行: 貼り替え <n> 件、close した旧親 #<番号>
旧構成からの移行: 貼り替え <n> 件。旧親 #<番号> には子が残るので open のまま
対応 UC 不明で紐付けなかった子: #<番号> ...
別の親に付いているので紐付けを変えなかった子: #<番号> (親 #<番号>) / ...
closed だが本文が現ドラフトと違う issue: #<番号> ...
どのドラフトとも一致しない open の既存の子 (close するかを人間に確認する): #<番号> <タイトル> / ...
```

「旧構成からの移行」の 2 行は、どちらか 1 行だけが出る。親に紐付いておらず「対応 UC」も読めない、ドラフトに無い open の既存の子は、「対応 UC 不明」と「どのドラフトとも一致しない」の両方の行に出る。そのときは close の確認を先にする (消えた作業単位なら、紐付ける必要が無い)。各行を受けてエージェントがすることは次のとおり:

| 行 | すること |
| --- | --- |
| 旧親には子が残るので open のまま | 残った子は「対応 UC 不明」の行に出るので、その行と同じに扱う |
| 対応 UC 不明で紐付けなかった子 | 番号とタイトルを人間に示し、どの UC の作業かを聞く。答えに合わせてその issue の本文の「対応 UC:」行を直し、同じコマンドを再実行する (再実行で紐付く) |
| 別の親に付いているので紐付けを変えなかった子 | `--keep` で残すと決めた親の子なら、何もしない。そうでなければ番号を人間に示し、貼り替えるかを聞く |

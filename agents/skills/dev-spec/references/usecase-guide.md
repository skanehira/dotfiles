## ユースケースの構成要素

### 必須要素

| 要素 | 説明 | 例 |
|------|------|-----|
| **ユースケース名** | 動詞で始まる簡潔な名前 | SQLを分析して改善案を得る |
| **主アクター** | ユースケースを開始する人/システム | 開発者 |
| **事前条件** | 開始に必要な状態 | ログイン済み |
| **事後条件** | 成功時の状態 | 改善案が保存されている |
| **正常系フロー** | 基本シナリオ | 1. 入力 → 2. 送信 → 3. 表示 |
| **受け入れ基準** | 終わったと言える条件。先頭に満たすストーリーの番号を付ける | （US-001）SQLを送信すると改善案が3つ以上表示される |

### オプション要素

| 要素 | 説明 |
|------|------|
| **副アクター** | 処理に協力するシステム（AIエンジン、外部API等） |
| **トリガー** | ユースケースを開始するきっかけ |
| **代替フロー** | 正常系から分岐する別パス |
| **例外フロー** | エラーや異常時の処理 |
| **ビジネスルール** | 適用される制約やルール |

## フロー記述のルール

### 基本フォーマット

```
番号. [アクター] が [アクション] する
```

### 良い記述

```
1. 開発者がSQL入力欄にクエリを入力する
2. 開発者が「分析」ボタンをクリックする
3. システムがAIエンジンに改善案を要求する
4. AIエンジンが改善案を3つ返す
5. システムが改善案を一覧表示する
```

### 悪い記述

```
❌ 抽象的すぎる
1. ユーザーが操作する
2. システムが処理する

❌ 実装詳細に踏み込みすぎ
1. ユーザーがPOST /api/v1/analyze を呼び出す
2. システムがRedisキャッシュを確認する
```

### アクターの書き方

| 良い例 | 悪い例 |
|--------|--------|
| 開発者 | ユーザー（曖昧） |
| 管理者 | 人（曖昧） |
| システム | サーバー（実装詳細） |
| AIエンジン | GPT-4（製品名） |

## 代替フローと例外フロー

### 代替フロー（Alternative Flow）

正常系の**別の選択肢**。ユーザーが意図的に選ぶパス。

```
正常系: ステップ2でスキーマを手動入力する

代替フロー A: ステップ2でスキーマをファイルからインポート
2a. 開発者が「インポート」ボタンをクリックする
2b. システムがファイル選択ダイアログを表示する
2c. 開発者がDDLファイルを選択する
2d. システムがスキーマをパースして入力欄に反映する
→ ステップ3に戻る
```

### 例外フロー（Exception Flow）

**エラーや異常**が発生した場合の処理。

```
例外フロー E1: ステップ4でAIエンジンがタイムアウト
条件: 30秒以内にAIから応答がない場合
4a. システムが「処理に時間がかかっています」と表示する
4b. システムがバックグラウンドで処理を継続する
4c. 完了したらメールで通知する
```

### 違いのまとめ

| 種類 | 発生条件 | 例 |
|------|----------|-----|
| **代替フロー** | ユーザーの選択 | ファイルからインポート、Googleでログイン |
| **例外フロー** | エラー・異常 | タイムアウト、バリデーションエラー |

## ビジネスルールの抽出

### ビジネスルールとは

システムの振る舞いを規定する**制約や条件**。

### 見つけるための質問

- 「〇〇できる条件は何ですか？」
- 「上限や下限はありますか？」
- 「〇〇と△△の関係にルールはありますか？」
- 「自動的に行われる処理はありますか？」

### ビジネスルールの種類

| 種類 | 説明 | 例 |
|------|------|-----|
| **制約** | 値の範囲や形式 | SQLは最大10クエリまで |
| **計算** | 導出値の算出方法 | 改善率 = (旧-新)/旧 × 100 |
| **推論** | 条件に基づく判断 | 改善率30%以上で「効果大」 |
| **アクション** | 条件によるトリガー | 分析完了後にSlack通知 |

### 記述フォーマット

```
BR-001: [ルール名]
条件: [いつ適用されるか]
内容: [具体的なルール]
```

例:
```
BR-001: SQL入力上限
条件: SQL入力時
内容: 1回の分析で入力できるSQLは最大10クエリまで

BR-002: 改善案生成数
条件: 分析実行時
内容: 改善案は最低3つ、最大10個生成する

BR-003: 無料プラン制限
条件: 無料プランユーザーの場合
内容: 1日5回まで分析可能。超過時はアップグレード案内を表示
```

## 受け入れ基準

受け入れ基準は「どんなときに、何をすると、どうなるか」を 1 文で書き、チェックリストに並べる。各行の先頭には、その基準が満たすストーリーの番号を `（US-<番号>）` の形で付ける。すべてに印が付いたら、そのユースケースは終わったとみなす。

前提条件・操作・期待結果を別々の行に分けない。3 つの要素が 1 文に収まらないときは、ユースケースかストーリーが大きすぎる合図なので分割を検討する。

### 例

```
UC-001: SQLを分析して改善案を得る

受け入れ基準:
- [ ] （US-001）ログイン済みの状態でダッシュボードの入力欄にSELECTクエリを入力して送信すると、5秒以内に改善案が3つ以上表示される
- [ ] （US-001）入力欄が空のまま送信すると、「SQLを入力してください」とエラーが表示される
- [ ] （US-001）構文エラーのあるSQLを送信すると、エラーの箇所がハイライトされる
```

### 書けているかの確認

各項目について、次の 3 つを読み取れること。

| 要素         | 例の該当箇所                                       |
| ------------ | -------------------------------------------------- |
| どんなときに | ログイン済みの状態で                               |
| 何をすると   | ダッシュボードの入力欄にSELECTクエリを入力して送信すると |
| どうなるか   | 5秒以内に改善案が3つ以上表示される                 |

「SQLを入力できる」のように操作だけを書いた項目は、どうなれば成功かが読めないので不合格。期待結果まで書く。

### フローとビジネスルールからの起こし方

受け入れ基準は新しく考えるのではなく、同じユースケースのフローとビジネスルールから起こす。

| 起こす元 | 受け入れ基準にするもの | 例 |
| -------- | ---------------------- | -- |
| 正常系フロー | 最後のステップで利用者に見える結果 | 改善案が 3 つ以上一覧表示される |
| 代替フロー | 分岐を選んだときの結果 | DDL をインポートすると入力欄に反映される |
| 例外フロー（E1, E2 …） | 1 つの例外フローにつき 1 行 | 30 秒以内に応答がないと処理中と表示される |
| ビジネスルール | 上限・下限・区分の境界で起きること | 11 件目のクエリは受け付けない |

フローにも BR にも無い基準を書きたくなったら、フローか BR の方が欠けている。先にそちらへ足してから基準を書く。

### 接頭辞の規則

- 括弧は全角の `（）` を使い、番号は USER_STORIES.md の見出しと同じ `US-<3 桁>` にする
- 1 行に付ける番号は 1 つだけにする。複数のストーリーに効く基準は、ストーリーごとに行を分ける
- USER_STORIES.md が無い構成（ストーリーを会話で受け取った場合）では接頭辞を付けない

### 被覆の確認

USER_STORIES.md の `#### US-<番号>` 見出しがすべて、USECASES.md の受け入れ基準の行（`- [ ] （US-<番号>）` で始まる行）に少なくとも 1 回現れること。フローの表や出典の列に番号が書かれていても被覆には数えない。確認のコマンドは [usecase-description.md](usecase-description.md) フェーズ11の観点 8 にある。

この確認は、Won't のストーリーが `#### US-` 見出しを持たないことを前提にしている（Won't は USER_STORIES.md で表に並べる。→ [user-story.md](user-story.md) フェーズ5）。

## よくある間違い

### 1. UIの詳細を書きすぎ

```
❌ 「青い送信ボタン（#0066CC）を右下に配置」
✅ 「開発者が送信ボタンをクリックする」
```

### 2. 実装詳細に踏み込む

```
❌ 「システムがPostgreSQLにINSERTクエリを実行する」
✅ 「システムが改善案を保存する」
```

### 3. 事前条件の欠落

```
❌ 事前条件なしで「改善案を表示する」を開始
✅ 事前条件: ログイン済み、SQLを入力済み
```

### 4. 曖昧なアクター

```
❌ 「ユーザーが操作する」
✅ 「開発者がSQLを入力する」
```

### 5. 例外フローの欠落

```
❌ 正常系だけで「システムが改善案を表示する」
✅ 例外: タイムアウト時、エラー時の処理も記述
```

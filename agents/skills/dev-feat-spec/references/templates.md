# dev-feat-spec の雛形

- 種別: テンプレート
- 生成者: dev-feat-spec の設計モード (手順 5・7) と直しのモード
- 消費者: 設計 PR をレビューする人、直しのモードで起動したセッション (設計時の判断を引き継ぐ)、GitHub Actions `design-approved.yml` (`Design-for:` の行)

## 人が読む文章の書き方

設計 PR の本文と issue の「ゴール」の説明は、PR をレビューする人と issue を承認する人が読む。この人たちは設計書を読んでおらず、AI が設計の中で考えた場面も知らない。書き手は設計書を書いた直後なので、設計書の言葉と前提のまま要約しがちである。次の決まりで書く。

- **1 文に 1 つのことを書く**。条件や結果が 3 つ以上つながる文は、文を分けるか箇条書きにする。目安は 1 文 60 字・読点 2 つまで
- **利用者から見た動きを、画面の表示語とふだんの言葉で書く**。API のパス、関数や変数の名前、テーブルや列の名前、設計書の中だけで使う言い回し (例: 注文を「確定へ回す」、商品とカテゴリの「紐付け」) は使わない。言い回しが要るときは、初出で「管理画面で登録した、カテゴリごとの商品の一覧」のように中身を言う
- **規則には具体例を添える**。「〜のときは〜する」と書いたら、誰が何をしたときに何が起きるかを 1 つ書く
- **判断に要らない経緯を書かない**。議事録の時刻、閉じた issue の経緯、検査の周回の内訳は書かない。要望の出どころは「A 社の要望 (要望一覧 No.3)」のように 1 句で足りる

実装の言葉を使ってよいのは、実装する人と直しのモードのセッションが読む節だけである: PR の「変えた設計書」「仮定」「採らなかった案」、issue の「設計」「DoD」「非スコープ」。issue の「担う受け入れ基準」の行は機能設計書の表の写しなので、書き換えない。

## 設計 PR の本文

PR のタイトルは `📝 docs: [BEHAVIORAL] <issue のタイトルを要約した平叙文>` にする。

```markdown
Design-for: #<issue 番号。issue を分けたときはこの行を書かず、子の番号を 1 件につき 1 行書く (親に ready を付けないため)>

## 何を決めたか
<この設計で、利用者から見て何がどう変わるかを 2〜5 行。誰の要望で、誰がどの画面で何をできるようになるかを書く>

## 画面の変化
<画面が変わるときだけ。変わる画面ごとに、変更前と変更後をテキストの簡単な図で並べる。画面が変わらなければ節ごと省く>

## 変えた設計書
- `docs/design/features/<機能名>.md`: <何を足したか・変えたか>
- `docs/design/USECASES.md`: <足した・変えた受け入れ基準の ID>
- `docs/design/DESIGN.md「<節名>」`: <あれば>

## 確認点
人の判断で変わりうる点。上ほど、変えたときの影響が大きい。
- [ ] **<決めたことを、利用者から見た動きで 1 文>**
  - 起きる場面: <この決定が効く場面を、利用者の操作の順に具体的に>
  - この設計での動き: <その場面で利用者に何が起きるか。なぜそうしたか>
  - 別の案: <採らなかった案と、それを選ぶと利用者に何が変わるか>

## 仮定
設計の前提にしたが、issue にも設計書にも書かれていなかったこと。
- <仮定>。<そう置いた根拠 (コードや設計書の場所)>

## 採らなかった案
- <案>: <採らなかった理由。実装の都合による理由もここに書く>

## 実装の分け方
<issue を分けなければ「#<番号> の 1 件で実装する」。分けたら子の番号と、それぞれの作業、依存を並べる>

## 検査
別のコンテキストの検査: high <n> 件 (直した) / medium <n> 件 (<直した、または直さない理由>)

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

- `Design-for:` の行は、行の先頭から `Design-for: #<番号>` だけを書く (`design-approved.yml` は 1 行に 1 件の番号だけを読む)
- 「確認点」はチェックボックスにする。人がレビューで 1 つずつ確かめた印になる
- 「何を決めたか」「画面の変化」「確認点」は、上の「人が読む文章の書き方」に従う
- 「確認点」は、設計書を読んでいない人が、その項目だけを読んで判断できるように書く
  - 利用者 (画面を使う人、出力したファイルを受け取る人) から見た動きで書く。設計書の場所を示すときは、項目の末尾に `(<機能名>.md「<節名>」)` を添える
  - 理由が実装の都合だけのとき (コードの書き方の規約、作る API が増える、など) は、確認点に書かず「採らなかった案」に書く。別の案で作る量が大きく増えるときは、「別の案」の欄に「作る量が増える (採らなかった案を参照)」と 1 句だけ添える
  - 例 (絞り込みで選んでいるカテゴリが、選択肢から消えたときの決定):

    ```markdown
    - [ ] **選んでいるカテゴリが選択肢から消えても、そのカテゴリを選んだままの表示にする**
      - 起きる場面: 商品一覧の画面で「カテゴリ B」で絞り込んだ後、別のタブの管理画面でそのカテゴリを消し、商品一覧の画面に戻る
      - この設計での動き: プルダウンの末尾に「カテゴリ B」が残り、選ばれたまま表示される。何もしないと表示だけが「すべて」に戻り、全商品のつもりでカテゴリ B の分だけの CSV を書き出してしまうため
      - 別の案: 自動で「すべて」に戻す。表示と中身は合うが、選んだカテゴリが気付かないうちに外れる。作る量が増える (採らなかった案を参照)
    ```
- 「仮定」と「採らなかった案」は、直しのモードのセッションが設計時の判断を引き継ぐための記録なので、省かない。無ければ「なし」と書く

## 修正方針

issue の本文の「設計」節に書く。

```markdown
## 設計
設計書の変更は要らない。修正方針:
- 直す場所: `<ファイル>` の `<関数や部品>`
- 直し方: <何をどう変えるか。なぜそれで直るか>
- 直さないこと: <隣接するが触らないこと>
<参照する設計書: docs/design/features/<機能名>.md「<節名>」、docs/design/DESIGN.md「既知の制約」の「<制約>」>
```

## 判断を求めるコメント

`needs-human` を足すときに issue へ書く。読む人は、この issue のことを覚えていない前提で書く (`~/.claude/rules/core/collaboration.md`「質問・提案の形式」)。

```markdown
**<何を決めてほしいかを 1 文で>**

<なぜ AI が決められないかを 1〜3 文。何と何が食い違っているか、誰の判断が要るか>

- A (推奨): <案>。<選んだときに起きること>
- B: <案>。<選んだときに起きること>

回答をこの issue に書いて `needs-human` を外すと、次の dev-feat-spec の起動で設計を進めます。

<!-- dev-feat-spec -->
```

判断が複数あるときは **Q1. / Q2.** と番号を振る。検査で high が残って止めたときは、残った high をそのまま並べ、どう直すかを聞く。

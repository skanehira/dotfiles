# dev-feat-spec の雛形

- 種別: テンプレート
- 生成者: dev-feat-spec の設計モード (手順 5・7) と直しのモード
- 消費者: 設計 PR をレビューする人、直しのモードで起動したセッション (設計時の判断を引き継ぐ)、GitHub Actions `design-approved.yml` (`Design-for:` の行)

## 設計 PR の本文

PR のタイトルは `📝 docs: [BEHAVIORAL] <issue のタイトルを要約した平叙文>` にする。

```markdown
Design-for: #<issue 番号。issue を分けたときはこの行を書かず、子の番号を 1 件につき 1 行書く (親に ready を付けないため)>

## 何を決めたか
<この設計で、利用者から見て何がどう変わるかを 2〜5 行。設計書を読まなくても分かるように書く>

## 画面の変化
<画面が変わるときだけ。変わる画面ごとに、変更前と変更後をテキストの簡単な図で並べる。画面が変わらなければ節ごと省く>

## 変えた設計書
- `docs/design/features/<機能名>.md`: <何を足したか・変えたか>
- `docs/design/USECASES.md`: <足した・変えた受け入れ基準の ID>
- `docs/design/DESIGN.md「<節名>」`: <あれば>

## 確認点
人の判断で変わりうる点。上ほど、変えたときの影響が大きい。
- [ ] <AI が決めたこと>。<そう決めた理由>。<別の案にすると何が変わるか>

## 仮定
設計の前提にしたが、issue にも設計書にも書かれていなかったこと。
- <仮定>。<そう置いた根拠 (コードや設計書の場所)>

## 採らなかった案
- <案>: <採らなかった理由>

## 実装の分け方
<issue を分けなければ「#<番号> の 1 件で実装する」。分けたら子の番号と、それぞれの作業、依存を並べる>

## 検査
別のコンテキストの検査: high <n> 件 (直した) / medium <n> 件 (<直した、または直さない理由>)

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

- `Design-for:` の行は、行の先頭から `Design-for: #<番号>` だけを書く (`design-approved.yml` は 1 行に 1 件の番号だけを読む)
- 「確認点」はチェックボックスにする。人がレビューで 1 つずつ確かめた印になる
- 「仮定」と「採らなかった案」は、直しのモードのセッションが設計時の判断を引き継ぐための記録なので、省かない。無ければ「なし」と書く

## 修正方針

issue の本文の「設計」節に書く。

```markdown
## 設計
設計書の変更は要らない。修正方針:
- 直す場所: `<ファイル>` の `<関数や部品>`
- 直し方: <何をどう変えるか。なぜそれで直るか>
- 直さないこと: <隣接するが触らないこと>
<参照する設計書: docs/design/features/<機能名>.md「<節名>」、docs/design/DESIGN.md「既知の制約」の「<制約>」>
```

## 判断を求めるコメント

`needs-human` を足すときに issue へ書く。読む人は、この issue のことを覚えていない前提で書く (`~/.claude/rules/core/collaboration.md`「質問・提案の形式」)。

```markdown
**<何を決めてほしいかを 1 文で>**

<なぜ AI が決められないかを 1〜3 文。何と何が食い違っているか、誰の判断が要るか>

- A (推奨): <案>。<選んだときに起きること>
- B: <案>。<選んだときに起きること>

回答をこの issue に書いて `needs-human` を外すと、次の dev-feat-spec の起動で設計を進めます。

<!-- dev-feat-spec -->
```

判断が複数あるときは **Q1. / Q2.** と番号を振る。検査で high が残って止めたときは、残った high をそのまま並べ、どう直すかを聞く。

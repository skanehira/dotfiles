# Stripe CLIによる月額カード自動決済

- 種別: スキル手順書

対象は、1顧客・1契約につき固定月額をカードで前払いする運用。登録確認を人が依頼し、その後エージェントが予約する。Webhookや毎月の独自決済ジョブは作らない。顧客名・金額・税率・日付・解約条件は案件ごとの入力とし、過去の案件から流用しない。

## 着手時に決めること

会話・契約書・既存の作業記録から値を拾い、不足する項目だけ尋ねる。契約書と依頼が食い違う場合は差分を提示し、請求対象期間が確定するまで書き込みを進めない。

以下の金額・日付は説明用の架空の例であり、顧客の実際の契約条件ではない。

| 入力 | 確認する内容・例 |
| --- | --- |
| 操作 | `prepare`（準備とURL発行）、`reissue`（URL再発行）、`activate`（登録確認と開始予約） |
| 対象環境 | 請求元Stripeアカウント、CLIプロファイル、`test` / `live`。不明なら読み取り調査のみ |
| 顧客・契約 | 正式名称、請求メールアドレス、既存Customer ID、同じ顧客のどの契約か |
| 商品・料金 | 顧客に表示する商品名、通貨、月額、税込 / 税別、数量（通常1） |
| 税 | 適用が確認された税率・内税 / 外税・免税等。例: JPY 48,000円＋外税10%＝52,800円 |
| 日時・期間 | 請求期間の開始日時とタイムゾーン、初回決済予定日、初回の対象期間、毎月の更新日、既払い期間。例: 2030-07-08 00:00 Asia/Tokyo開始、7/8決済予定、7/8〜8/7分 |
| 継続・解約 | 無期限継続か、契約上の終了日・事前通知・日割り・返金例外の有無 |
| カード登録 | 登録後の遷移先`success_url`、登録期限、継続課金の同意。実在し利用が認められたHTTPS URLを使う |

日付しかない場合はタイムゾーンと開始時刻を確定する。29〜31日の更新は短い月での扱いを確認する。開始日時が既に過ぎていたら`now`や過去日へ置き換えない。後払い、従量課金、複数商品、期限付き契約の自動終了はこの手順の定型外として、条件を整理してから別途設計する。

Scheduleの開始日時は請求期間の境界であり、決済完了時刻ではない。初回Invoiceはdraftで作成され、通常は約1時間後に確定して非同期に決済されるため、開始時刻ちょうどの決済を保証しない。

## CLIと権限

1. `stripe --version`と`stripe post --help`でCLIと利用可能なフラグを確認する。認証状態は`stripe whoami --format json`で確認する。未対応なら秘密値を表示せず、ログイン状況をユーザーに確認する。設定ファイルや`stripe config --list`を出力しない。
2. 読み取りAPIで請求元アカウントIDを照合する。全API呼び出しで同じプロファイル・環境を使い、本番は明示的な`--live`を付ける。`STRIPE_API_KEY`等の既存オーバーライドの有無を値を表示せず確認し、実際のアカウントと応答の`livemode`を優先する。テストIDを本番に持ち込まない。
3. 現在のAPI仕様を[CLI/API対応表](references/stripe-api.md)から確認する。`stripe docs`が使えれば優先し、未導入・接続不可ならStripe公式ドキュメントを読む。プラグイン導入やMCPへの切替を前提にしない。
4. 書き込み前に、顧客・金額と税・開始日時・対象期間・環境・今回作るものを提示する。既にその内容の実行が許可されていれば進める。説明・計画・スキル作成の依頼だけではStripeを書き換えない。未許可の本番操作は具体的な内容を示して許可を得る。

prepare/activateの前に、その段階で使うAPIの読取・書込権限を対応表と照合する。権限確認のために実請求を作らない。403等の権限不足は必要なリソースと再開条件を報告し、そのAPIに依存する処理を止める。プレビューがAPI仕様上未対応の場合と権限不足を混同しない。

認証キー、カード番号、CVCを受け取ったり文書に記録したりしない。必要な新規キーは制限付きキーを優先し、秘密ストアからCLIへ渡す。API応答は必要なID・状態・金額だけを抽出し、`client_secret`や個人情報を含む全文を会話やリポジトリに出さない。

## 再開と重複防止

最初にランダムなUUIDを`job_id`として発行し、`~/.local/state/stripe-recurring-billing/<job_id>/state.json`を作る。ディレクトリは所有者のみアクセス可能、ファイルは所有者のみ読み書き可能とする。エージェントが各API成功直後に原子的に更新し、次のエージェントが再開時に読む。スキル正本やGitには顧客別の記録を保存しない。

記録するのは次の値。未作成のIDはnullにする。

- `job_id`、`stage`（`preparing` / `awaiting_card` / `scheduled`）、アカウントID、CLIプロファイル、環境、使用APIバージョン。
- 合意した顧客識別情報・契約識別子・料金・税・日時・解約条件・`success_url`、許可された操作範囲。業務上のカード登録期限、登録状況・初回決済を確認する担当と予定日時。
- Customer / Product / Price / TaxRate / PaymentMethodConfiguration / Checkout Session / SetupIntent / PaymentMethod / Subscription Schedule / Subscriptionの各ID、Sessionの失効日時。過去のSession IDも残す。
- 各書き込みの操作名・リクエスト内容（秘密値を除く）・idempotency key・結果ID。URLそのものやAPI応答全文は保存しない。

同じ契約を再開するときは既存の`job_id`を使う。記録が不明なら、状態ディレクトリとStripeの顧客・契約情報を照合する。顧客名だけで選ばず、複数候補ならユーザーに確認する。新規作成するCustomer・Session・ScheduleとScheduleのphaseには`metadata[billing_job_id]`を付ける。共有Product・Price・TaxRateのmetadataは上書きしない。

書き込みの直前に操作と入力を記録し、同じ操作の通信再試行では同じidempotency keyを使う。応答が不明ならまずGETで作成済みか照合する。24時間を超えたキーの再送だけに頼らない。既存の有効なSubscriptionと未開始・有効なScheduleをページ末尾まで確認し、同一契約の請求が存在すれば新規作成しない。別契約の請求を勝手に変更しない。二重起動が疑われたら片方を止め、同一jobの書き込みは直列にする。

## prepare: 準備とカード登録URL

1. 初回請求対象を既払い期間と照合する。例えば既払いが7/7までで前払いなら、7/8の決済は7/8〜8/7分。空白・重複があれば書き込み前に解消する。
2. 顧客、商品、月額の継続料金を照合して再利用する。見つからなければ作成する。単発のInvoiceItemを月額料金の代わりに作らない。既存料金を変更せず、条件が異なるなら別Priceにする。
3. 税抜・税込の設定とは別に税率を適用する。単一税率の案件は合意した手動TaxRateを使う。税率、内外税、国・地域、activeを照合して再利用し、手動税率と`automatic_tax`を併用しない。Stripe Taxが指定された案件は、有効な税登録・所在地等の前提を公式手順で確認してから使う。税率を無断で10%と決めない。
4. カードだけが提示される支払い方法設定を確認する。既存の専用PaymentMethodConfigurationを優先し、なければ作成の必要性を示して今回の許可範囲を確認する。アカウント全体の決済方法を無断変更しない。Checkoutの`payment_method_types`は指定せず、確認した`payment_method_configuration`を使う。
5. Customerを明示したCheckout Sessionを`mode=setup`で作成する。通貨・`success_url`・継続課金の説明を設定する。Checkoutの公開パラメータにないSetupIntentの属性を`setup_intent_data`へ転記しない。料金の`line_items`を渡さず、登録時の請求は行わない。
6. GETでCustomer・mode・環境・`status=open`・`expires_at`を確認する。登録URLは結果から取得し、依頼者にだけ提示する。標準24時間、最大24時間の有効期限を現地時刻で伝える。
7. 案内文に「登録時の料金請求なし」「税込額と税の扱い」「初回日・毎月の決済日・対象期間」「継続と解約条件」「URLの失効日時」を含める。顧客への送信は明示的に依頼された場合だけ行う。

ここで`stage=awaiting_card`。完了報告は「URL発行済み・カード登録待ち・定期請求予約は未作成」とする。顧客の操作を待って止まり、作業記録のパスと再開方法を渡す。

業務上の登録期限とURLの有効期限は別に管理する。URLにも短い期限が指定され、発行後30分〜24時間の範囲内なら`expires_at`へ変換して設定する。範囲外なら別の時刻へ丸めず、発行時期・再発行の扱いを合意する。登録期限が数か月先でもURLは最大24時間なので、案内直前に発行する。業務上の期限を過ぎた再発行は、期限変更の許可を確認する。

## reissue: 登録URLの再発行

同じjobのSessionを再取得する。登録済みなら新しいURLを作らず、`activate`が許可範囲なら進む。URL発行のみの依頼なら登録完了を報告して止める。未登録でまだ有効なら既存URLを使う。失効していれば同じCustomerで新Sessionを作り、新しい操作番号とidempotency keyを記録する。顧客・料金・Scheduleは増やさない。有効な旧Sessionを置き換える依頼では旧Sessionを失効させ、古いリンクで登録が競合しないようにする。

## activate: 登録確認と開始予約

1. 作業記録とStripeを再照合し、同一job・契約の既存Schedule/Subscriptionがあれば下記「既存予約の復旧」へ進む。新規予約の場合は、顧客が「登録済み」と言ったことや成功ページへの到達だけで完了としない。Sessionの`status=complete`、SetupIntentの`status=succeeded`と`usage=off_session`、PaymentMethodのCustomer一致・`type=card`・環境一致をGETで確認する。
2. 未登録、追加認証待ち、後日決済用ではないカード、別顧客のカードなら予約しない。状態と必要な対応を伝える。未作成のまま開始日時が過ぎていた場合は、自動で即時課金へ切り替えない。
3. 顧客の未請求InvoiceItem、残高・クレジット、割引、免税設定など、想定額を変える項目を確認する。対応するAPIでは予定構成の請求プレビューを作成前に取得する。影響や想定額との差があればユーザーと扱いを決め、他契約の項目を消して金額を合わせない。
4. 同一契約の既存Subscription / Scheduleがないことを再確認し、将来開始のScheduleを作る。開始日時をタイムゾーン付き日時からUnix秒へ変換する。`charge_automatically`、数量、料金、税を明示する。登録カードをScheduleの`default_settings.default_payment_method`に指定し、顧客全体の既定カードは不用意に変更しない。
5. 無期限継続は1か月のphaseと`end_behavior=release`で構成する。phase終了後も同じSubscriptionを継続させる。`cancel`にしない。開始前を無料トライアルとして扱わない。
6. ScheduleをGETして、`status=not_started`、開始日時、料金・数量・税、カードID、回収方法、`end_behavior=release`を照合する。将来開始前はSubscription IDがnullでも正常。利用APIが対応する請求プレビューで初回・次回の期間と税込額を照合し、請求書確定や決済を検証代わりに実行しない。プレビュー不能なら構成検証と金額の算術検算までを報告し、実決済は未検証とする。
7. `stage=scheduled`にして、開始日時・初回対象期間・税込額・月次継続・Schedule ID・作業記録パスを報告する。「予約済み」と「決済成功」を区別する。継続時のSubscription IDはScheduleの`subscription`、release後は`released_subscription`から取得する。

### 既存予約の復旧

POST応答消失や記録更新前の中断では、StripeからIDを回収して再作成をスキップする。job・契約・顧客・環境・料金・税・開始日時が記録と一致することを先に確認する。不一致や複数候補は自動修正しない。

- `not_started`: 手順6の構成検証へ合流して記録を復元する。
- `active`: Scheduleと`subscription`を取得し、設定・現在の期間・実際の支払い状態を確認する。
- `released`: `released_subscription`を取得して同様に確認する。Scheduleが終了していても継続中の請求を再作成しない。
- `canceled` / `completed`、またはSubscriptionが終了済み: 終了状態を報告し、再契約の明示依頼なしに再作成しない。

`active` / `released`で意図した請求が継続していれば`stage=scheduled`を復元し、実状態も記録する。このstageは予約設定済みを意味し、決済成功を意味しない。支払い失敗や未検証の期間があればそのまま報告する。

## 運用への引き渡し

通常解約を日割りなしと合意している案件では、契約期間の境界で終了し、次の期間を請求しない運用を記録する。例: 11/7まで提供なら最後は10/8〜11/7分、11/8分は請求しない。通知を受けた時点で即時解約しない。契約上の返金例外を通常の「日割りなし」で消さない。解約・返金の実操作は別途の依頼を受けて行う。

支払い失敗の通知・再試行・振込による代替回収の担当と契約期限を引き渡す。アカウント全体の再試行や自動解約設定を変更する場合は影響範囲を確認する。既存設定が契約に適合するか未確認ならその状態を明示する。

## 検証の境界

スキル自体の検証は[検証シナリオ](references/stripe-api.md#検証シナリオ)を使う。ドライランはリクエストの組み立て確認であり、Stripe側の受理・登録画面・将来決済の証明にはならない。実カードで試験しない。テスト環境への書き込みも依頼範囲に含まれる場合だけ行い、本番と別のjobとして扱う。
